# 医疗信息系统AI需求分析

本技能提供完整的TFS需求到代码实现的分析流程，结合业务知识库、代码搜索和业务领域验证，生成可直接用于AI编码的需求分析文档。适用于公司多个产品条线的需求分析工作。

## 核心原则

1. **代码搜索优先**：分析前必须先验证代码是否已实现（Rule 6）
2. **参数驱动设计**：优先使用现有参数，避免直接修改代码逻辑
3. **兼容性优先**：不能直接改写原逻辑，必须保证兼容
4. **业务准确性**：验证业务定义准确性，质疑可疑描述
5. **以代码为准**：代码与文档冲突时，信任代码实现

## 分析工作流

### 阶段1：需求获取与理解

#### 1.1 获取TFS需求 ⭐含附件/图片强制处理规则
```
输入：TFS需求号
操作：

**步骤1：获取原始需求**
- 使用 get_work_item(需求号) 获取原始需求
- 使用 list_attachments(需求号) 检查附件
- 如有附件，使用 download_attachments(需求号) 下载并理解

**步骤2：强制检查需求说明字段中的附件/图片** ⭐新增

⚠️ **强制要求**：若需求说明字段（System.Description）内容存在"附件"或"图片"，必须下载并分析解读！

**检测与处理场景**：

| 场景 | 检测条件 | 处理方式 |
|------|----------|----------|
| 场景1 | TFS附件列表有附件 | 使用 download_attachments() 下载到 analysis.result/<需求号>/ |
| 场景2 | 说明中存在 `<附件>` 链接（文件集） | 使用 download_attachments() 逐个下载 |
| 场景3 | 说明中存在图片链接（Ctrl+点击查看） | 提取URL并下载图片到本地 |
| 场景4 | 说明中嵌入 `<img>` 标签 | ⭐**提取src属性并下载图片** |

**⚠️ 重要：场景4（HTML嵌入图片）处理规则**

很多需求的图片是嵌入在HTML富文本中，而非TFS附件：
- `list_attachments()` 返回0个附件 ❌
- 但 `System.Description` 中包含 `<img src="...">` ✅

**场景4实现方式**：
```bash
# 步骤1：创建输出目录
mkdir -p "analysis.result/<需求号>"

# 步骤2：获取需求说明字段HTML内容
description_html = get_work_item(需求号).fields.System.Description ?? ""

# 步骤3：使用正则表达式提取 <img> 标签的 src 属性
# 匹配模式：<img[^>]+src=["']([^"']+)["']
img_urls = extract_image_urls(description_html)

# 步骤4：遍历所有图片URL，下载到本地
for url in img_urls:
    # 从URL中提取文件名，或生成唯一文件名
    filename = extract_filename(url) or generate_unique_name()
    
    # 使用curl下载图片
    curl -L -o "analysis.result/<需求号>/<filename>" "<url>"
    
    # 验证下载成功
    if file_exists("analysis.result/<需求号>/<filename>"):
        print("图片下载成功: <filename>")

# 步骤5：使用Read工具或analyze_image工具分析图片内容
# 图片路径：analysis.result/<需求号>/<图片文件名>
```

**输出目录**：
```
analysis.result/<需求号>/
├── 图片文件1.png
├── 图片文件2.jpg
└── ...
```

**分析要求**：
- 发现任何附件/图片时，**强制要求**下载分析
- 将图片内容解读作为下一步分析的重要参考
- 如需求包含图片，必须理解图片内容（Rule 5）

**重要说明**：
- 需求说明中的图片可能包含界面原型、流程图、业务规则等关键信息
- 忽略图片可能导致遗漏重要需求细节
- 图片解读结果将作为业务分析和代码分析的重要参考依据

**重要说明**：
- 需求说明中的图片可能包含界面原型、流程图、业务规则等关键信息
- 忽略图片可能导致遗漏重要需求细节
- 图片解读结果将作为业务分析和代码分析的重要参考依据
```

```
**操作流程**：
1. 查阅 references/knowledge-integration.md 了解知识检索规则
2. 根据产品类型查阅 /Knowledge/ 中的功能清单
3. 发现业务术语时，查阅 /Term/ 术语表验证定义
4. 理解现有配置参数，查阅 /Param/ 参数文档
5. 确定产品类型和业务背景

**知识文件结构**（根据使用者负责的产品条线而定）：

业务知识路径：
- /Knowledge/ → 根据TFS需求智能识别的功能清单（自动缩小范围）
- /Param/ → 使用者放入的配置参数文档
- /Entity/ → 使用者放入的实体属性明细
- /Term/ → 使用者放入的术语概念域映射
- /Rule/ → 使用者放入的分析规则和约束

**使用说明**：
- **Knowledge/**：根据TFS需求的"产品名称"、"迭代路径"、"区域路径"智能识别对应功能清单
- **其他目录**：使用者将自己负责的产品线相关文件放入对应目录
- 无关文件不纳入分析范围

**Rule目录说明**：
Rule目录存放不同产品条线特有的分析规则和约束，包括：
- 代码规范和命名规则
- 产品条线特有的分析要求
- 固定的分析约束和限制
- 特殊的业务规则
- 分析流程的特殊要求
- 数据字典和值域引用规则
- 兼容性要求和迁移规则

代码查询路径（Code/）：
- /Code/ → 源代码目录（符号链接指向实际代码仓库）
  ├── ⚠️ **重要**：动态检测Code目录实际内容
  ├── 执行 `ls -la Code/` 查看实际目录结构
  └── 根据实际存在的目录进行代码搜索
2. 不同产品条线的代码仓库位置可能不同
3. 使用 `ls -la Code/` 或 `dir Code/` 查看Code目录的实际内容
4. Code目录可能是符号链接，指向实际的代码仓库位置

**⚠️ 重要：知识目录符号链接兼容性处理**

部分知识目录（Knowledge/, Param/, Entity/, Term/）可能是符号链接（快捷方式），需要使用 Bash 命令而不是 Glob 工具进行检测：

```bash
# 步骤1：检测知识目录是否存在和类型
ls -la Knowledge/ Param/ Entity/ Term/ 2>&1 | head -50

# 步骤2：查找Markdown文件
# 如果是实际目录，直接查找
find Knowledge/ -type f -name "*.md" 2>&1 | head -20
find Param/ -type f -name "*.md" 2>&1 | head -20
find Entity/ -type f -name "*.md" 2>&1 | head -20
find Term/ -type f -name "*.md" 2>&1 | head -20

# 步骤3：如果目录为空，报告状态
# 不影响后续分析，继续执行代码验证
```

**兼容性处理原则**：
- 优先使用 Bash 命令（find, ls）而非 Glob 工具
- 符号链接和实际目录都需要支持
- 知识目录为空时不阻塞分析流程
- 检测失败时记录警告但继续分析

**详细使用指南**：见 [references/knowledge-integration.md](references/knowledge-integration.md)
```

### 阶段1.5：分支信息记录 ⭐新增

#### 1.5.1 检测代码分支
```
输入：无
操作：

**优先级顺序**：

1️⃣ **优先**：从TFS需求获取（推荐）⭐重要
   - 从 get_work_item 返回的 _fields["Winning.Prod.Version"] 获取
   - 示例值："250815"、"250225"、"250212"等，格式化为"v250815"
   - **重要说明**：
     - ❌ "分支类型"字段（Winning.Prod.Branch）无法具体到哪个分支，不应使用
     - ✅ "版本号"字段（Winning.Prod.Version）能准确标识开发分支
   - 分支命名规则：版本号前加"v"前缀，如"v250815"
   - 这是需求的目标分支，最准确

2️⃣ **备选**：从Code目录获取git分支
   - 命令：git -C Code branch --show-current
   - 当TFS需求中没有 Winning.Prod.Branch 字段时使用
   - 如果命令被中断或失败，进入下一步

3️⃣ **默认**：使用默认值
   - 如果前两种方式都失败，使用"未检测到Git分支"

**保存分支名称到变量**，供后续模板替换使用

**注意**：
- Code/ 目录是相对于AI-Analysis-Plus项目根目录的符号链接
- 不要在文档中标注信息来源，直接显示分支名称即可
```

#### 1.5.2 错误处理
```
如果git命令执行失败：
- 使用默认值："未检测到Git分支"
- 开发提示更改为："请确认当前工作分支"
```

在两份分析文档的开头显示分支信息：

### 阶段2：代码验证（最关键！⭐⭐⭐⭐⭐）

#### 2.1 代码搜索优先级（Rule 6）
```
重要：许多需求是移植需求，功能可能已存在！

⚠️ **重要**：Code目录的代码路径会根据产品条线和迭代分支不同而变化！

**步骤1：确认Code目录的实际内容**
```bash
# 查看Code目录的实际内容
ls -la Code/          # Linux/Mac
dir Code/             # Windows

# 查看Code目录是否是符号链接
ls -l Code | grep "^l"  # Linux/Mac
```

**步骤2：根据Code目录实际内容确定代码路径**

⚠️ **重要**：动态检测Code目录的实际内容

使用 `ls -la Code/` 查看实际的代码目录结构，根据实际目录内容进行搜索：

- 后端代码：搜索Code目录下的所有Java源码目录
- 前端代码：搜索Code目录下的所有Vue前端项目（winning-webui-*）
- 参数文档：搜索 /Param/ 目录下是否存在对应的参数文档

**实际操作步骤**：
1. 执行 `ls -la Code/` 查看Code目录的实际内容
2. 根据实际目录结构确定后端和前端代码位置
3. 在实际存在的代码目录中进行代码搜索
4. 检查 /Param/ 目录下是否存在对应的参数文档

**步骤3：执行代码搜索**
搜索顺序（动态检测Code目录）：
1. 执行 `ls -la Code/` 查看Code目录的实际内容
2. 后端业务逻辑层：搜索Code目录下所有winning-business-*目录
3. 前端主应用：搜索Code目录下所有winning-webui-*目录
4. 参数文档：搜索 /Param/ 目录下对应的参数文档

**注意事项**：
- 不同产品条线的代码仓库位置和结构可能不同
- 迭代分支不同，代码内容也会不同
- 如果Code目录是符号链接，实际路径可能指向其他位置
- 移植需求需要搜索历史分支的代码
```

#### 2.3 发现已实现功能的处理
```

2. 向用户报告：

   - 后端：[文件路径]:[行号]
   - 前端：[文件路径]:[行号]

   - 否：结束分析，仅报告代码位置
   - 是：生成移植方案分析文档（适用于移植需求）

3. 根据用户响应执行：

   - 如果用户选择"是" → 继续阶段3，重点分析移植方案、数据传递、界面展示等

```

#### 2.4 实体字段验证 ⭐新增（Rule 10）
```
**操作流程**（在设计任何新字段前必须执行）：
1. 检查PO类（数据库实体文件）：
   - 搜索所有以PO结尾的Java类：Glob("**/*PO.java", "Code/")
   - 或使用Grep搜索：Grep("class.*PO.*extends", "Code/", type="java")

2. 检查/Entity/目录下的实体文档：
   - 使用Bash命令：ls -la Entity/ 检查目录内容
   - 搜索相关实体定义文档
   - 参考已有字段定义

3. 字段比对与确认：
   - 需求字段 vs PO类字段
   - 需求字段 vs Entity文档字段
   - 发现已有字段 → 直接复用，停止设计新字段
   - 发现相似字段 → 向用户确认是否可复用
   - 无相关字段 → 确认后设计新字段

**重要**：
- 这是强制检查步骤，不能跳过（Rule 10）
- 如果字段已存在，必须在分析中说明复用关系
- 如果不确定，必须向用户确认
```

#### 2.5 参数配置验证 ⭐增强（Rule 11）
```
**操作流程**（在设计任何新参数前必须执行）：
1. 检查/Param/目录下的配置参数文档：
   - 使用Bash命令：ls -la Param/ 检查目录内容

   - 无相关参数 → 确认后设计新参数

4. 优先复用现有参数（Rule 1：兼容性原则）

**重要**：
- 这是强制检查步骤，不能跳过（Rule 11）
- 如果参数已存在，必须在分析中说明复用关系
- 代码实现优先于文档说明（Rule 8）
- 发现参数冲突时向用户确认
```

### 阶段3：产品业务分析

#### 3.1 业务分析（可选使用brainstorming辅助）

**⚠️ 重要说明**：
- 本步骤的目标是理解业务需求，为生成产品业务分析文档做准备
- **最终输出必须按照3.2节的模板要求生成文档**
- brainstorming 只是辅助工具，不是必须调用的技能

**判断是否需要使用 brainstorming**：

✅ **需要使用 brainstorming 的场景**：
- 业务流程复杂，需要系统梳理
- 技术方案不明确，需要讨论对比
- 需求模糊，需要通过对话澄清
- 有多个实现方案，需要权衡选择

❌ **不需要使用 brainstorming 的场景**：
- 需求简单明确，业务清晰
- 纯数据展示优化（如本案例：显示实际完成时间）
- 已有参考实现，直接套用
- 代码验证阶段已找到实现方案

**如果需要使用 brainstorming**：

1. **明确告知 brainstorming 的作用范围**：
   ```
   调用 brainstorming 技能时说明：
   "我需要你帮助我理解这个需求的业务流程和技术方案，
    但我最终会按照自己的模板生成产品业务分析文档。
    你只需要提供分析思路和关键信息点即可，不需要生成完整文档。"
   ```

2. **从 brainstorming 提取信息而非使用输出**：
   ```
   ✅ 提取：业务流程、技术方案、风险点、关键决策
   ❌ 使用：brainstorming 的文档结构、输出格式
   ```

## 重要规则

### Rule 1: 兼容性原则
- 针对原逻辑的变更，要注意兼容
- 不能直接改写原来设计的逻辑（除非明确告知改写）
- 优先扫描是否已存在对应的参数或配置
- 可以优先检查是否已经存在对应的参数或者配置来保持兼容

### Rule 4: 前后端代码都要扫描
- 需求分析时要前端、后端代码都扫描
- 有些需求只是移植需求（代码分支很多）
- 提出需求的客户用的是历史代码分支
- 你现在能读取的是最新的代码分支

### Rule 5: 理解需求中的图片
- 如果原始需求中存在图片，要理解图片内容
- 图片可能包含界面原型、流程图等关键信息

### Rule 6: 代码搜索优先（最终权威）
- 优先分析当前需求是不是在代码中存在
- 如果发现代码中已实现（无论是代码实现还是通过参数配置）
- 立刻停止分析，并告诉用户需求在哪些代码中已实现

### Rule 7: 前置/参见需求处理
- 如果需要分析的需求中有写明前置需求或者参见需求
- 要从TFS上重新获取前置或参见需求的"需求分析"内容
- 如果前置或参见需求的"需求分析"内容中有图片，也要解析

### Rule 8: 以代码为准
- 如果发现代码中的实现和文档不一致
- 要直接询问确认后，再进行工作
- **以代码为准**：代码与文档冲突时，信任代码

### Rule 9: 不能改代码
- 严禁创建分支
- 严禁改代码
- 只生成分析文件

### Rule 10: 实体字段检查 ⭐新增
- 在设计任何新字段之前，必须先检查PO类（数据库实体文件）
- 遍历类名以PO结尾的Java类，查找是否已存在相同或相似字段
- 必须遍历阅读/Entity目录下的实体文档，参考已有字段
- 如果字段已存在 → 直接复用，在分析中说明
- 如果字段相似 → 向用户确认是否可复用
- 如果不存在 → 确认后设计新字段

### Rule 11: 参数配置检查 ⭐新增
- 在设计任何新参数之前，必须先检查/Param目录下的配置参数文档
- 必须遍历阅读/Param目录，查找是否已存在相关参数
- 如果参数已存在 → 直接复用，在分析中说明
- 如果参数相似 → 向用户确认是否可复用
- 如果不存在 → 确认后设计新参数

## 常见问题

### Q1: 需求在多个集合中存在怎么办？
使用 `collectionHint` 参数指定项目关键词（如"60项目"、"5x项目"、"卫数项目"）

### Q2: 如何判断需求是否已实现？
按照"阶段2：代码验证"的流程进行前后端代码搜索

### Q3: 用户输入映射表为什么重要？
这是开发人员进行编码的基础，告诉开发"用户填什么，系统存什么"

### Q4: 如何处理移植需求？
- 搜索历史分支代码
- 发现已有实现后，分析移植方案
- 说明移植差异和测试要点

### Q5: 代码与文档冲突怎么办？
以代码为准，记录冲突点，向用户确认后再继续

### Q6: Rule目录应该存放哪些内容？
Rule目录存放产品条线特有的分析规则和约束，包括：
- **代码规范和命名规则**：I/II/III/IV型命名规则、编码规范
- **数据字典和值域引用规则**：Code类型必须引用标准数据元和值域
- **兼容性要求和迁移规则**：针对原逻辑的变更兼容策略
- **产品条线特有的分析要求**：特定的分析流程和格式要求
- **固定的分析约束和限制**：技术约束、业务约束
- **特殊的业务规则**：行业特定的规则和限制
- **分析流程的特殊要求**：必须遵循的步骤和检查点

## 输出要求

### 文档格式
- 格式：Markdown (.md)
- 编码：UTF-8
- 路径：`analysis.result/{需求号}/{需求号}-产品业务分析.md`

- 开发人员能直接根据文档编码
- 包含所有必要的映射表和规则说明
- 提供清晰的代码示例
- 包含完整的测试要点

### 分析风格
1. 严谨为主，不说废话
2. 所有的分析都基于事实，不胡编乱造
3. 工科思维加上用户体验
4. 有质疑的精神，验证医学定义准确性
5. 所有对话以中文简体输出
