# SPEC 编码重命名技能 (v1.0)

将存量 SPEC 知识库迁移到规范四层编码。核心原则：**语义决策（人/Claude）与机械执行（脚本）分离**——编码映射表必须经用户确认后再执行批量重命名，任何自动替换都基于已确认的映射，不猜。

## 输入

| 参数 | 必需 | 说明 |
|---|---|---|
| SPEC 根目录 | 是 | 如 `E:\37结构性问题治理\01WiNEX 病历管理v0.1` |
| 编码规则文档 | 否 | 默认取根目录下 `SPEC编码规则说明.md`；若根目录没有则向用户索要路径 |
| 代码仓库区 | 否 | 默认 `E:\39EMR\sr-next`；用于核实 FeatName 术语真实性 |
| 涉及范围 | 否 | 用户可能只要求重编码个别模块；默认全库扫描、只动确认过的模块 |

## 流程

### Phase 1 — 盘点（只读）

1. 读规则文档，提取关键约束：编码正则、产品码合法值、长度限制（推荐 18~40、硬上限 55）、命名禁令（拼音缩写/数字后缀/全大写缩写仅限 ModCode）。
2. `find` 全库列出所有目录/文件，识别**旧编码模式**（常见：拼音前缀 + 序号 + 下划线中文名，如 `JZBL-06-BLCX-001_急诊病历综合查询`）。注意旧模式变体：文件分隔符 `_PM-spec` 与 `-PM-spec` 可能混用。
3. `grep -c` 统计旧编码在文档内的引用形态：完整引用（编码_中文名）、子功能编号（编码-001-01、编码-001-01-02）、裸模块引用（编码）、跨文档关联引用。**跨模块引用**（其他模块的编码，如 `JZBL-01-BLSX`）只记录、不替换——本技能只动目标模块。
4. 对每个功能点，从其文档中提取它自己声明的代码术语（`grep -Eoh "\b(Emg|Emr)[A-Za-z]+(Service|Controller|AppService|RpcService)\b"` 按实际产品调整前缀），再到代码仓库区 `grep -rEoh ... | sort -u` 验证实名存在。

### Phase 2 — 设计映射（语义，需用户确认）

对每个层级给出新编码候选及**代码依据**：

- **ProductCode**：对齐仓库命名（如 `winning-emr-*` → `Emr`）。若规则文档产品表未收录该产品码，标注"需在规则文档备案"。
- **ModCode**：对齐仓库/前端工程名缩写（2~10 字符，首字母大写；OP/IP 类行业缩写全大写）。
- **SSS**：沿用原序号（重编码不是重新发号；若原号段违反十位预留制则提示用户决策）。
- **FeatName**：取文档内出现且在代码仓库中验证存在的 Service/Controller 核心词，PascalCase，6~25 字符。多个候选时选与功能点主体查询/操作最贴近的。

产出映射表给用户确认，格式：

```
| 旧编码 | 旧中文名 | 新编码 | 代码依据（已验证存在的命名） |
```

**必须等用户确认后才进入 Phase 3。**

### Phase 3 — 机械执行（脚本）

将确认后的映射写入 JSON，运行捆绑脚本：

```bash
uv run python <技能目录>/scripts/rename_spec_codes.py \
  --root <SPEC根目录> --mapping mapping.json --dry-run   # 先预演
uv run python <技能目录>/scripts/rename_spec_codes.py \
  --root <SPEC根目录> --mapping mapping.json              # 确认无误后实跑
```

mapping.json 结构见脚本头部注释；`features[].services` 填代码依据（写入注册表用）。

脚本自动完成：目录迁移到 `{ProductCode}/{ModCode}/`、三件套文件重命名（`_PM-spec`→`-PM-spec` 规范化）、文档内四类引用替换（按 完整引用→子编号→裸模块码 的优先级）、YAML front matter 注入（spec-id/title/type/repo/status）、`_SPEC注册表.md` 生成或追加、残留扫描、路径长度校验。

**先 dry-run 看预演输出，确认替换计数合理再实跑。** 实跑后脚本会打印残留清单——残留的跨模块编码（如 `JZBL-01-BLSX`）属于其他模块，保留并在汇报中说明，待那些模块重编码时统一处理。

### Phase 4 — 验证与汇报

1. `find` 展示新目录树；`grep` 确认目标模块旧编码零残留（跨模块残留单列）。
2. 抽查 1~2 个文件的 front matter 与正文引用是否连贯（子编号如 `Emr-EmgQry-001-EmrSetQuery-01-02`）。
3. 向用户汇报：编码映射表、目录树、引用替换计数、注册表位置、需备案事项（如新产品码）、跨模块残留建议。

## 红线

- 未经确认的映射不执行；dry-run 计数与盘点阶段统计量级不符时停下排查（常见原因：旧编码存在盘点时漏掉的变体拼写）。
- 不改 `SPEC编码规则说明.md` 本身；产品码不在规则文档合法值中时先提示备案，不擅自扩表。
- 替换只锚定目标模块编码前缀，绝不波及跨模块编码；`keep_refs` 中登记的编码在残留报告中标记为"有意保留"。
- Windows 路径：新编码超 55 字符即报错拒绝（为目录层级留余量）。
