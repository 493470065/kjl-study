# 02 — Spec 编写指南

本指南覆盖 Phase 1 功能点Spec 和 Phase 2 三件套的编写规范，聚焦于每个章节"写什么、怎么写、常见错误"。

---

## 1. Phase 1：功能点Spec 编写要点

### 1.1 第2章：一句话描述

**公式**：`<模块名称>是<在什么系统/流程中的定位>，承载<核心数据/能力列表>，是<业务价值/下游依赖>的重要数据源。`

**常见错误**：
- ❌ 写成了功能列表（应留给第5章）
- ❌ 超过 3 句话（应是"一句话"）
- ✅ 30 秒可读完，说清"是什么、管什么、为什么重要"

### 1.2 第3章：业务背景

**公式**：编号列表，每句格式为 `<动作者> + <动作> + <对象> + <结果>`

**示例**：
```
1. 系统自动获取患者基本信息、入院信息、医护信息
2. 完整录入入院、门诊、出院、病理四类诊断并规范编码
```

**常见错误**：
- ❌ 展开了 Given/When/Then 细节（应留给 Phase 2 Analyst-Spec）
- ❌ 句与句之间有逻辑跳跃（缺中间步骤）
- ✅ 读一遍能在脑中跑通完整业务链路

### 1.3 第5章：功能点清单

这是 Phase 1 核心产出，质量决定 Phase 2 的顺利程度。

**公式**：`角色 + 时机 + 系统动作 + 数据来源/去向 + 目的/效果`

**功能点中文名称**：必须遵循 `references/conventions.md` 第10节命名规则（动宾短语 / 单动词 / 反向对例外 / 一句话展开 / 避开基线词 / 统一词表 / 名实相符唯一 / 4~16 字），命名后按第10.9节自检清单逐项核对。违反规则的名称需修正后再定稿。

**粒度判断**：
- ✅ 合适的粒度："患者基本信息管理"——一个独立的能力域，对应一组需求
- ❌ 太粗："病案首页管理"——这是模块名，不是功能点
- ❌ 太细："患者姓名字段显示"——这是基线能力，不构成功能点

**拆分依据**：
- 功能清单 md 中已列出的功能点 → 直接采纳
- 功能清单 md 中未列出但需求 xlsx 中大量出现且独立的主题 → 咨询用户是否纳入
- 字段调整/界面微调 → 归入第6章基线能力

**功能点清单表结构**（模板 5.1 节）：每行功能点除编号/名称/等级/C-DARHS评估/描述外，还要填 **分类标签 5 列**（交互模式/业务性质/安全等级/使用频率/成熟度）和 **健康度基线列**（关联需求ID/需求数/健康等级）。

**分类标签判定**（方法论 §4.4）：
| 维度 | 标签 | 判定依据 |
|------|------|---------|
| 交互模式 | 单实体操作/多实体协作/跨角色流转/跨系统交互 | 候选条目的协作描述 |
| 业务性质 | 临床业务/管理业务/财务业务/平台支撑 | 功能归属 |
| 安全等级 | 高/中/低 | 与 C-DARHS 的 H 联动：H✅→高 |
| 使用频率 | 高频/中频/低频 | 资料区有依据则标，无依据 `⏳ 待确认` |
| 成熟度 | 稳定/频繁变更/新上线 | 资料区有依据则标，无依据 `⏳ 待确认` |

**健康度基线登记**（方法论 §5，落地为"当前可得的基线事实"）：
- 关联需求ID / 需求数：从历史需求 xlsx 中统计归属本功能点的需求编号（可统计则填）；无数据标记 `⏳ 待确认`。
- 健康等级：有完整指标数据才判 🟢🟡🟠🔴；只有部分数据时给异常模式提示（如"需求过载"）并标记 `⏳ 待确认`。
- **绝不虚构**需求数、增速、来源数或健康等级。完整健康度统计与看板属治理阶段，不在 Phase 1 展开。

**粒度校准四步收尾**（方法论 §3.4）：对定稿前的功能点逐一执行拆分测试 → 合并测试 → 一句话测试，并把"L1:L2 比例"登记到第1章基本信息。

### 1.4 第6章：基线能力声明

**目的**：防止功能清单膨胀。告诉读者"以下变更是有的，但我们不把它们当作独立功能点"。

**判断标准**：
| 问自己 | 是 → 基线能力 | 否 → 候选功能点 |
|--------|-------------|---------------|
| 这个变更只涉及单个字段的增删改？ | ✅ | ❌ |
| 这个变更只涉及界面展示调整（颜色/位置/显示/隐藏）？ | ✅ | ❌ |
| 这个变更纯粹是版本合并/数据迁移？ | ✅ | ❌ |
| 这个变更涉及完整的业务流程和多个角色？ | ❌ | ✅ |

## 2. Phase 2：三件套编写要点

### 2.1 编写顺序（强制）

```
1. -Spec.md（研发视角）→ 定"为什么做、做成什么"
2. PM-Spec.md（业务视角）→ 定"做什么+验收标准"
3. Analyst-Spec.md（产品视角）→ 定"怎么做细节"
```

**原因**：后写的文档可以引用先写的，保证口径递进一致。违反顺序会导致三份文档口径漂移。

### 2.2 -Spec 编写要点

> ⚠️ **代码事实优先**：-Spec 第4章（数据模型）、第5章（接口契约）、第6章（技术方案）**必须以代码扫描结果填充**（标注 `（来源：代码）`），而非仅凭需求文本中的零散代码线索。需求文本中提到的接口/表名/组件可标注 `（来源：需求XXXX）` 作为补充。

**第2.1章 功能背景**：按四层组织（不是每层都必须有）：
1. **法规规范**：只列资料区引用的规范名，不补充未提及的规范
2. **管理要求**：来自需求分析中的管理诉求
3. **现状痛点**：来自需求分析中的问题描述，不自行发现痛点
4. **历史需求演进脉络**：引用真实需求编号，描述各阶段需求变化

**第2.2章 功能定位**：3~5 个点，每个点一句话。从"合规性/效率/闭环/协同/灵活"等维度归纳。

**第2.3章 目标用户**：角色 + 主要使用场景。角色必须在需求原文中出现过，不细化角色粒度。

### 2.3 PM-Spec 编写要点

**目标**：一句话说清实现什么、覆盖什么、确保什么。可量化但**不编造量化指标**。

**业务约束**：每条标注来源。来源格式：`《法规名》` 或 `需求<编号>`。

**非功能性约束**：指标数值必须来自资料区。资料区无指标的写 `⏳ 待确认：性能/安全/可用性指标未在资料区中找到`。**绝不填默认值——没有就是没有。**

**验收标准 AC**：
- ✅ `系统在3秒内返回患者基本信息并填充到首页对应字段`
- ❌ `系统正常响应用户请求`
- ✅ `CA签名失败时显示具体原因，支持最多3次重试`
- ❌ `签名功能正常`

### 2.4 Analyst-Spec 编写要点

**功能编号体系**：父级子功能点（`<编号>-001`）按能力域划分，子项（`<编号>-001-01`）按用户操作节点划分。

**Mermaid 流程图**：用 `flowchart TD`，节点类型：
- `[方框]` = 操作/状态
- `{菱形}` = 判断
- `-->` = 流程线
- `-->|条件|` = 条件分支

**Given/When/Then 场景**：
- Given：前置条件（数据状态、系统配置、用户状态）
- When：操作步骤（具体、可执行）
- Then：预期结果（可观察、可验证）

**场景数量达标检查**：
| 类型 | 最少 | 说明 |
|------|------|------|
| 主流程 | 1 | 最常见的成功路径 |
| 异常流程 | 3 | 业务异常1个 + 数据异常1个 + 系统异常1个 |
| 边界流程 | 2 | 空值/多值/未配置/极端值中选2个 |

**数据字段定义**：每个字段必须在资料区中出现过。无概念ID的写 `⏳ 待确认`。

**业务规则 BR**：每条 BR 注明来源需求编号。规则描述必须能从需求原文中逐字对应。

## 3. 跨文档口径一致性检查

编写过程中，每写完一个三件套文档，检查以下交叉引用：

| 检查项 | 方法 |
|--------|------|
| 功能编号 | 三份文档的标题、REQ-ID、文件名一致 |
| 功能名称 | -Spec 1.1、PM-Spec 目标、Analyst-Spec 概述一致 |
| 排除范围 | PM-Spec 第四章与 Analyst-Spec 第四章一致 |
| 关联文档版本 | 三份文档的关联文档索引中 Phase 1 功能点Spec 版本一致 |
| AC 编号 | Analyst-Spec 中的 AC 编号与 PM-Spec 对应 |
| 术语 | -Spec 中定义的术语，PM/Analyst 复用，不另定义 |

## 4. 常见编写陷阱

| 陷阱 | 表现 | 纠正 |
|------|------|------|
| Spec 越界 | -Spec 中展开 Given/When/Then | 场景细节只在 Analyst-Spec |
| 术语漂移 | -Spec 写"审核签名"，Analyst 写"审签" | 统一为 -Spec 术语表中的正式术语 |
| 场景编造 | Given 中写"系统展示确认弹窗"，需求没提弹窗 | 需求没描述的交互细节不编造 |
| 角色细化 | 需求说"医生"，你写"主任医师/主治医师/住院医师" | 需求用什么粒度就用什么粒度 |
| 指标编造 | 需求没写响应时间，你写"≤200ms" | 写 `⏳ 待确认` |
| 上下文推测 | 需求说"支持自动同步"，你写"每5分钟同步一次" | 频率不在资料区就不写 |
