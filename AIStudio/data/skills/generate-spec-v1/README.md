# generate-spec-v1 使用手册

> 版本：v5.2 | 更新日期：2026-08-18

## 1. 这个技能是做什么的？

一句话概括：**把"历史需求Excel + 功能清单md + 代码遍历"变成一份结构化、方法论驱动的功能点Spec文档。**

分两个阶段 + 一个强制前置步骤：
- **Phase 0.5（强制前置）**：扫描代码仓库（默认 `E:\39EMR\sr-next`）提取 API 端点、数据实体（PO/DO）、Controller/Service、前端路由、模块目录映射、技术栈
- **Phase 1**：产出"模块级功能点Spec"——一份包含 L1/L2 功能点清单（含 C-DARHS 评估、分类标签、健康度基线）和 L3/L4 基础能力附录的索引文档，第8章代码架构来自代码扫描
- **Phase 2**：为每个功能点逐一产出"三件套"Spec（Spec（研发视角）+ PM-Spec（业务视角）+ Analyst-Spec（产品视角）），接口契约/数据模型/技术方案章节来自代码扫描

整个过程不写代码、不改产品，只产出规格文档。**生成任何 Spec 前必须完成代码扫描（R17/R18），代码扫描结果是接口契约、数据模型、代码架构、技术方案章节的事实来源。**

> **当前默认场景：WiNEX 病历管理（住院）**（v3.5，2026-08-18）：默认资料区 `E:\37结构性问题治理\01WiNEX 病历管理\资料区`，输出目录按模块编码前缀自动映射（根目录 `E:\37结构性问题治理\01WiNEX 病历管理`）：BLGL→`住院病历Spec`、JZBL→`急诊病历Spec`、MZBL→`门诊病历Spec`。模块编码 BLGL-01~BLGL-99。如需切换到急诊/门诊场景，明确指定产品线、资料区即可，输出目录无需指定（按编码前缀自动映射）。

> **v3.2 更新（2026-08-14）**：**代码扫描升级为强制前置步骤**——代码仓库默认地址 `E:\39EMR\sr-next`，生成 Spec 前必须先扫描代码并标注"来源：代码"，不再以需求文本中的零散代码线索替代扫描；新增强制规则 R17（代码扫描强制前置）、R18（代码来源可验证），自检新增 S16/S17。

> **v3.1 更新（2026-08-14）**：按"WiNEX功能点划分原则与方法论.md"（v1.0）更新功能点划分方法论——Phase 1 功能点清单新增**分类标签 5 维**（交互模式/业务性质/安全等级/使用频率/成熟度）与**健康度基线**（关联需求ID/需求数/健康等级）登记，粒度校准改为拆分/合并/一句话三测试，编号规则保持 module-checklist 编码。详见 `references/methodology-guide.md`。

## 2. 使用前需要准备什么？

### 2.1 需要准备的材料

| 材料 | 格式 | 说明 | 是否必须 |
|------|------|------|---------|
| **功能模块名称和编号** | 口头指定 | 如"病案首页 BLGL-13-BASY" | ✅ 必须 |
| **资料区** | 目录 | 包含模块相关文档的目录，有什么用什么 | ✅ 必须（至少一个文件） |
| **功能点划分方法论文档** | `.md` | WiNEX功能点划分原则与方法论 | ✅ 必须 |
| **输出目录** | 目录路径 | 按模块编码前缀自动映射（BLGL→住院病历Spec / JZBL→急诊病历Spec / MZBL→门诊病历Spec），无需手动指定 | 自动 |
| **代码仓库** | 目录 | 默认 `E:\39EMR\sr-next`（无需用户提供，技能自动扫描） | ✅ 必须（自动） |

> ⚠️ **代码扫描是强制前置步骤**：生成任何 Spec 前，技能会自动扫描代码仓库（默认 `E:\39EMR\sr-next`）提取 API 端点、数据实体（PO/DO）、Controller/Service、前端路由、模块目录映射、技术栈。接口契约、数据模型、代码架构、技术方案章节以代码扫描结果为事实来源并标注"来源：代码"。

资料区中的材料**不预设必须项**，常见材料包括：

| 材料 | 作用 | 说明 |
|------|------|------|
| 历史需求 xlsx | 提供需求分析原文、业务场景、字段、规则 | 最优情况 |
| 功能清单 md | 提供功能 ID、名称、描述、参数、数据表 | 最优情况 |
| 操作手册 / 产品手册 | 辅助获取功能列表和业务流程 | 有就更好 |
| 设计文档 / 接口文档 | 辅助获取系统架构和数据流向 | 有就更好 |
| 知识库文件 | 辅助获取功能类别和关联系统 | 有就更好 |

**资料区有什么就用什么，缺失材料不阻塞流程。** 由技能自动扫描并列出已有材料清单，缺材料导致的信息缺口用 `⏳ 待确认` 标记。

## 5. 核心概念速查

### 5.1 什么是功能点？

**功能点**是具有完整业务语义的最小独立功能单元，必须涉及"上下文交互"（多实体协作、状态流转、跨系统调用、业务规则推导中至少一种）。

**不是功能点的**：纯增删改查、导出、打印、单点配置、纯技术接口。

### 5.2 C-DARHS 是什么？

六个判定维度：

| 要素 | 问题 |
|------|------|
| **C**ontext | 是否在端到端业务流程中？ |
| **D**ecision | 是否有业务规则判断或人工决策？ |
| **A**ction | 是否引起状态变更或跨系统消息？ |
| **R**ole | 是否由特定角色执行？ |
| **H**ealth-Safety | 是否直接影响患者安全？ |
| **S**LA | 是否有性能/可用性要求？ |

### 5.4 分类标签（方法论 §四）

每个 L1/L2 功能点打 5 个分类标签：交互模式（单实体/多实体/跨角色/跨系统）、业务性质（临床/管理/财务/平台）、安全等级（高/中/低，与 H 联动）、使用频率（高/中/低频）、成熟度（稳定/频繁变更/新上线）。无资料依据的维度标记 `⏳ 待确认`。

### 5.5 健康度基线（方法论 §五）

Phase 1 功能点清单登记健康度基线（关联需求ID、需求数、健康等级 🟢🟡🟠🔴）。资料区无需求绑定数据时标记 `⏳ 待确认`，不虚构数值。完整健康度统计与看板属治理阶段，由治理团队基于需求绑定数据滚动维护。

### 5.3 L1-L4 等级

| 等级 | 条件 | 处理 |
|------|------|------|
| **L1 核心功能** | ≥5要素 + C+D+A+H | ✅ 纳入功能点 |
| **L2 重要功能** | ≥4要素 + C+A | ✅ 纳入功能点 |
| **L3 基础功能** | ≤3要素 | ❌ 附在附录 |
| **L4 技术细节** | ≤2要素 + 不含H | ❌ 排除 |

## 6. 常见问题

### Q1：资料区文件名字有要求吗？

没有。只要目录里有一个 `.xlsx`（历史需求）和一个 `.md`（功能清单），技能会自动识别。推荐放在 `<模块目录>/资料区/` 下。

### Q2：资料区没有功能清单 md / 没有历史需求 xlsx 怎么办？

**不会阻塞。** 技能会自动适配：

| 缺失材料 | 处理方式 |
|---------|---------|
| 无功能清单 md | 从历史需求 xlsx 标题聚类中提取候选条目；功能 ID、参数说明、数据表清单等信息标记 `⏳ 待确认` |
| 无历史需求 xlsx | 以功能清单 md 为主素材；业务背景、需求分析、用户角色等标记 `⏳ 待确认` |
| 两者都没有 | 从操作手册等其他材料中提取；大量信息标记 `⏳ 待确认` |

核心原则：**资料区有什么就用什么，缺什么就标什么。**

### Q3：Phase 1 和 Phase 2 必须连着做吗？

不必。可以先只做 Phase 1 产出功能点清单，Phase 2 留到以后做。Phase 2 也可以只选其中几个功能点生成三件套，不用一次全部做完。

### Q4：输出中有 ⏳ 待确认 怎么办？

说明资料区信息不足以支撑这个结论。找到标 ⏳ 的部分，找对应领域的人补充信息，然后让 AI 更新 Spec。

### Q5：方法论文档每次都要指定路径吗？

是的。方法论文档不在 skill 内部维护（skill 里只有一份 `methodology-guide.md` 速查表），完整方法论由用户每次指定路径。

### Q6：怎么更新已有的功能点Spec？

说"重新执行 XX 模块的 Phase 1"，技能会检测到已有 Spec 并询问你是覆盖还是仅更新。
