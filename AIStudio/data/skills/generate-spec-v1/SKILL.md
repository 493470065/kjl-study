# 功能模块 Spec 生成技能 (v5.2)

将资料区素材转换为符合治理规范的 Spec 文档。采用**两阶段流程**。**代码扫描是强制前置步骤**——生成任何 Spec 前必须完成代码仓库扫描。

- **Phase 0.5 — 代码仓库扫描（强制前置）**：生成 Spec 前必须扫描代码仓库（默认 `E:\39EMR\sr-next`），提取 API 端点、数据实体（PO/DO）、Controller/Service、前端路由、模块目录映射、技术栈等结构化信息。这是 Spec 中接口契约、数据模型、代码架构、技术方案章节的**事实来源**，优先于资料区文档中的零散代码线索。
- **Phase 1 — 产出模块级功能点 Spec**：基于"WiNEX功能点划分原则与方法论"三层漏斗 + C-DARHS 判定法，对从资料区中提取的全部候选条目执行基线过滤→六要素评估→L1-L4分级→粒度校准，产出模块级功能点索引（含 L1/L2 功能点清单和 L3/L4 基础能力附录），第8章代码架构用代码扫描结果填充。
- **Phase 2 — 逐功能点产出三件套 Spec**：基于 Phase 1 的功能点清单，对每个功能点逐一生成三件套（Spec（研发视角）、PM-Spec（业务视角）、Analyst-Spec（产品视角）），接口契约、数据模型、技术方案章节用代码扫描结果填充。

**核心原则**：资料区有什么就用什么。理想情况是历史需求 xlsx + 功能清单 md 齐全，但如果只有其中一种，或者还有其他材料（操作手册、设计文档、接口文档等），也照常处理——缺失材料导致的信息缺口用 `⏳ 待确认` 标记即可，不阻塞流程。

**方法论落地要点**：功能点划分遵循"WiNEX功能点划分原则与方法论"（用户指定路径）——三层漏斗（基线过滤 → C-DARHS 六要素 → L1-L4 分级）+ 第四层粒度校准；对 L1/L2 功能点打**分类标签**（交互模式/业务性质/安全等级/使用频率/成熟度）并登记**健康度基线**（需求密度、增速、来源集中度、健康等级，无需求绑定数据时标记 `⏳ 待确认`）。完整健康度统计与看板属治理阶段，不在 Phase 1 输出中展开。方法论要点速查见 `references/methodology-guide.md`，完整方法论以用户指定的文档为准。

分析阶段不写代码、不改产品，只产出规格文档；材料用于归纳业务背景、功能边界、规则与场景。

## 核心原则：严格基于素材，禁止随意发挥

**本技能的定位是"资料整理与结构化呈现"，不是"创意写作"。** 输出的每一句话都必须能在资料区中找到直接或间接依据。具体而言：

- ✅ **允许**：从资料区原文中提取、归纳、归类、重组、用模板格式呈现
- ✅ **允许**：对资料区中模糊、矛盾之处标记 `⏳ 待确认` 并写入待确认问题清单
- ❌ **禁止**：根据行业常识或经验补充资料区未提及的功能、场景、规则、字段
- ❌ **禁止**：推测用户意图或"应该是这样"来填补信息缺口
- ❌ **禁止**：编造概念ID、参数路径、表名、字段名、接口名、性能指标
- ❌ **禁止**：凭空设计业务规则（BR 必须能从需求原文或功能清单中归纳）
- ❌ **禁止**：虚构 Given/When/Then 场景中的具体操作步骤、系统状态、数据内容
- ❌ **禁止**：推测或假设用户角色、使用场景、痛点，除非资料区明确提及

**信息缺失时的正确做法**：标记 `⏳ 待确认`，在 Analyst-Spec 末尾汇集"待确认问题清单"，逐条注明"缺失什么信息、为什么需要、建议由谁补充"。宁可留白，不可编造。

## 代码仓库作为素材来源（强制）

**代码仓库扫描是本技能生成 Spec 的强制前置步骤，不是可选项。** 代码仓库默认地址为 `E:\39EMR\sr-next`（前端/后端微服务集合），用户未另行指定时使用该地址。代码中的 **API 端点、数据实体（PO/DO）、模块目录结构、前端路由、技术栈** 是客观存在的事实，优先于资料区文档中的零散代码线索作为 Spec 的事实来源，可以安全使用，不违反"禁止随意发挥"原则。

**流程要求**：执行 `guides/01-input-extraction.md` 第 5 节代码扫描，提取信息后先填入 Spec 对应章节并标注 `（来源：代码）`；资料区需求文本中提到的代码线索（接口路径、表名、组件名等）作为补充，标注 `（来源：需求XXXX）`。**Spec 的接口契约、数据模型、代码架构、技术方案章节必须以代码扫描结果为事实来源，不得仅凭需求文本填写后即视为完成。**

代码扫描提取的信息可直接填入 Spec 的这些章节：
- **API端点** → -Spec 第5章（接口契约设计）和 Analyst-Spec 数据字段定义
- **数据实体（PO/DO）** → -Spec 第4章（数据模型设计），表名和字段名直接使用，标注 `（来源：代码）`
- **Controller类与API路径常量** → -Spec 第5章（API列表），路径和入参/出参类型直接使用
- **前端路由/页面目录** → -Spec 第6章（技术方案设计，页面路径）
- **模块目录映射** → Phase 1 功能点Spec 第8章（代码架构）
- **配置文件（pom.xml/application.yml）** → 辅助识别技术栈和模块依赖

**来自代码的信息必须标注来源为"代码"**，与来自文档的信息区分。代码中没有的信息（如业务规则、用户场景、验收标准）仍需从资料区获取或标记 `⏳ 待确认`。具体注入规则见 `guides/01-input-extraction.md` 第 5.7 节。

## 适用边界

- **Phase 1 输入**：资料区（历史需求 xlsx / 功能清单 md / 操作手册 / 设计文档等，有什么用什么，缺失不影响流程）、功能点Spec模板（`assets/feature-point-spec-template.md`）、输出目录、**代码仓库扫描结果（强制，默认 `E:\39EMR\sr-next`）**。
- **Phase 1 输出**：`<模块ID> <模块名称>功能点Spec.md`（模块级功能点索引，含完整功能点清单，第8章代码架构来自代码扫描）。
- **Phase 2 输入**：Phase 1 输出的功能点Spec + 资料区 + 3 个 Spec 模板（-Spec / PM-Spec / Analyst-Spec）。
- **Phase 2 输出**：每个功能点一个子目录，内含三件套 Spec。
- **可跳过 Phase 1**：若模块级功能点 Spec 已存在且用户确认直接进入 Phase 2，则跳过 Phase 1，以现有功能点Spec 作为 Phase 2 的锚点。
- **只产出规格文档**：不生成数据建模、API 契约、技术方案、测试计划（由设计层后续产出，Analyst-Spec 中登记"待产出"）。
- **Phase 2 支持单点/批量**：可指定单个功能点编号生成单份三件套，也可遍历全部功能点逐一生效。

## 强制规则

| 编号 | 规则 |
| --- | --- |
| R0 | **素材溯源（最高优先级）**：Spec 中每一个陈述（业务背景、场景、规则、数据字段、概念ID、参数路径、表名、验收标准）都必须在资料区中有直接或可归纳的来源。无来源的信息不得写入，改为标记 `⏳ 待确认` 并汇入待确认问题清单。这是 R1～R14 的总纲，与其他规则冲突时以 R0 为准。 |
| R1 | 模板优先：严格按用户给的模板（Phase 1 用功能点Spec模板，Phase 2 用三件套模板）的结构、章节号、表头生成；模板中的填写说明（`> 📌` 行）在成稿中删除，占位符 `[ ]` 和 `< >` 全部填写后删除。 |
| R2 | 口径唯一：功能编号在模块内唯一，Phase 1 功能点清单与 Phase 2 所有三件套的 REQ-ID、文件名、父需求、关联文档互相引用必须完全一致；目录名若用变体（如 `BLGL-13-BASY--001`），文件内一律用规范单短线编号。 |
| R3 | 素材从资料区来：业务背景、场景、数据字段（概念ID）、参数路径、数据表名一律取自历史需求原文与功能清单，禁止凭空编造概念ID、参数名、表名；无来源的细节写成待确认问题。 |
| R4 | 分层清晰：Phase 1 功能点Spec 只写"有哪些功能点+模块全景"，不展开功能细节；Phase 2 三件套中 -Spec.md 只写"为什么做、做成什么"；PM-Spec 只写"做什么+验收标准"；Analyst-Spec 写功能细节（场景/规则/字段/AC）。各层不得互相越界。 |

| R6 | 验收标准可验证：AC 编号独立，写"结果+时限+数据变化/界面表现"，禁止"功能正常""体验良好"等模糊表述；AC 与 Scenario 对应关系明确。**AC 必须从需求原文中的验收要求归纳，不得自创验收条件。** |
| R7 | 版本与登记：功能点Spec 初始版本 v1.0；三件套中 -Spec=V1.0、PM-Spec=V0.1、Analyst-Spec=V1.0；日期用当天；编写人默认 RACC；"关联文档索引""参考文档"登记齐三件套+模块级功能点 Spec。 |

| R14 | **方法论驱动划分**：Phase 1 的功能点识别必须严格遵循用户指定的功能点划分方法论文档（如"WiNEX功能点划分原则与方法论"），按三层漏斗 + C-DARHS + L1-L4 分级流程执行，不得凭经验主观划分。方法论文档路径由用户提供。 |

##### (a) 后端代码扫描

- **Phase 1 第8章（代码架构）**：填入完整目录树 + 职责注释 + 模块映射表

### 1.3 执行三层漏斗 + C-DARHS 判定（核心步骤）

> ⚠️ 严格遵循用户指定的方法论文档。以下流程基于"WiNEX功能点划分原则与方法论"。

**候选条目来源优先级**：功能清单 md 的功能 ID 列表 > 历史需求 xlsx 标题聚类出的功能主题 > 操作手册中提取的功能列表 > 代码仓库 Controller @ApiOperation 标签聚类出的功能主题（辅助参考）。有功能清单时以功能清单为基准，没有则从可用材料中提取。**代码仓库的功能分组仅作辅助参考**——Controller 的 @Api(tags=...) 帮助确认模块边界，但代码的粒度不等于业务功能点的粒度，最终仍需通过 C-DARHS 判定。

#### 1.3.1 第一层：基线过滤

对**全部候选条目**逐项检查，排除以下基线能力：

| 排除类型 | 判断标准 | 示例 |
|---------|---------|------|
| 纯 CRUD | 单对象的增/删/改/查，不涉及上下文交互 | 新增患者、查询医嘱列表、修改药品信息 |
| 导出/打印 | 数据的呈现形式，非业务逻辑 | 导出费用清单、打印腕带 |
| 字典/配置管理 | 单点参数配置，不含业务规则协作 | 维护药品字典、配置角色权限 |
| 纯技术接口 | 技术通道，不含承载的业务操作 | REST API、HL7 消息通道 |

**⚠️ 查询类候选的区分判定（重要）**：基线过滤中的"查询"（"查"、"列表"）仅指**单对象简单查询**（如"查询患者列表""查询医嘱列表"——单表单字段过滤，无业务逻辑）。**包含以下任一特征的"复杂检索"不得排除，进入第二层 C-DARHS 判定**（依据方法论 §8.2"多维度患者检索与权限过滤"案例）：

| 复杂检索特征 | 说明 | 示例 |
|------------|------|------|
| 跨权限/跨范围 | 不同角色看到不同数据范围（科室 vs 全院） | 科室病历查询 vs 全院病历查询 |
| 多条件组合检索 | 多维度条件组合过滤（诊断/手术/时间/医疗组等） | 按诊断+出院时间+医疗组检索病历 |
| 跨系统取数 | 检索涉及跨系统数据源 | 从数据中心查历史病历 |
| 触发审计/操作日志 | 查询行为需留痕 | 溯源水印、导出日志 |

判定口诀：**"一个输入框查一个表"是基线；"多条件+多范围+跨系统+留痕"是功能点。**

**输出**：通过第一层的候选条目清单（排除项编号和原因同时记录，作为第6章素材）。

#### 1.3.2 第二层：C-DARHS 六要素评估

对通过第一层的每个条目，逐项评估 6 个要素并标记 ✅ 或 ❌，**每个要素写一句话说明**：

| 要素 | 代码 | 判定问题 | 满足标准 |
|------|------|---------|---------|
| **Context** | C | 是否处于端到端业务流程中？上下游是什么？ | 能明确说出触发条件和后续环节 |
| **Decision** | D | 是否包含业务规则判断或人工决策分支？ | 有规则推导、人工审核、异常处理中至少一种 |
| **Action** | A | 是否引起实体状态变更或跨系统消息？ | 创建/更新/删除数据、发送通知、触发下游 |
| **Role** | R | 是否由特定角色执行？不同角色看到内容不同？ | 有明确的角色绑定和权限控制 |
| **Health-Safety** | H | 是否直接影响患者安全或诊疗质量？ | 错误可能导致患者伤害、用药错误、诊断延误 |
| **SLA** | S | 是否有明确的性能/可用性/一致性要求？ | 响应时间、并发数、可用性有量化指标 |

**输出**：每个候选条目的 C-DARHS 六要素标记、满足数和一句话说明。无量化指标时 S 标记 ❌ 并在说明中注明（不得编造指标值）。

#### 1.3.3 第三层：L1-L4 分级

按 C-DARHS 满足数分级：

| 等级 | 判定规则 | 处理方式 |
|------|---------|---------|
| **L1 核心功能** | 满足 ≥5 要素，**必须包含 C+D+A+H** | ✅ 纳入功能点清单，必须写完整 Spec，参与健康度分析 |
| **L2 重要功能** | 满足 ≥4 要素，**必须包含 C+A** | ✅ 纳入功能点清单，Spec 可简化，参与健康度分析 |
| **L3 基础功能** | 满足 ≤3 要素 | ❌ 不单独作为功能点，记录在"基础能力附录" |
| **L4 技术/字典功能** | 满足 ≤2 要素且不含 H | ❌ 不计入功能点，仅作为技术实现细节 |

**分级要点**：
- **H 是关键分级要素**：涉及患者安全的候选（如危急值通知、配伍禁忌校验、效期拦截）通常判为 L1；不涉患者安全的（如纯财务功能）即使满足 5 要素也只判 L2。
- **L1:L2 建议比例约 3:7 或 4:6**：偏离时在功能点清单备注说明原因。

#### 1.3.4 第四层：粒度校准

对判定为 L1/L2 的功能点，执行三个测试（来自方法论 §3.4）：

**拆分测试**：能否拆出 2 个以上同样满足 L1/L2 标准的子步骤？能 → 拆分（当前粒度过粗），不能 → 粒度合适。

**合并测试**：两个功能点是否服务于同一业务目标且触发条件、角色、数据完全相同？是 → 合并（当前粒度过细），否 → 粒度合适。

**一句话测试（终极检验）**：能否用一句话说清楚"谁，在什么场景下，做了什么，达成了什么业务结果"？能 → 粒度合适；需要说好几句话 → 可能过粗；说出来觉得很 trivial → 可能过细。

#### 1.3.5 分类标签与健康度基线（方法论 §四、§五）

对全部 L1/L2 功能点，登记**分类标签**与**健康度基线**：

**分类标签（5 维）**：

| 维度 | 标签示例 | 判定依据 |
|------|---------|---------|
| 交互模式 | 单实体操作 / 多实体协作 / 跨角色流转 / 跨系统交互 | 候选条目的协作描述 |
| 业务性质 | 临床业务 / 管理业务 / 财务业务 / 平台支撑 | 功能归属 |
| 安全等级 | 高 / 中 / 低 | 与 H 要素联动：H✅→高，H❌→中/低 |
| 使用频率 | 高频 / 中频 / 低频 | 资料区有依据则标注，无依据 `⏳ 待确认` |
| 成熟度 | 稳定 / 频繁变更 / 新上线 | 资料区有依据则标注，无依据 `⏳ 待确认` |

**健康度基线**（关联需求ID、需求数、健康等级）：
- 资料区可统计（如历史需求 xlsx 中归属本功能点的需求编号）时如实填写。
- 无需求绑定数据时标记 `⏳ 待确认`，**不得虚构需求数或健康等级**。
- 健康等级判定（方法论 §5.2）：🟢 全指标正常 / 🟡 1~2 项超阈值 / 🟠 3~4 项超阈值 / 🔴 全部超阈值或极端值；只有部分数据时给异常模式提示并标记 `⏳ 待确认`。
- 完整健康度统计（需求密度/增速/来源集中度）与看板属治理阶段，由治理团队滚动维护，不在 Phase 1 输出中展开。

### 1.4 生成功能点 Spec

按 `assets/feature-point-spec-template.md` 的 9 章结构生成。**每写完一个章节，自问：这一段的素材来自资料区的哪里？**

输出要求：
- 第5章功能点清单：每个功能点标注功能等级（L1/L2）、C-DARHS 评估摘要（如 C✅D✅A✅R✅H❌S✅ (5/6)）、分类标签 5 列、健康度基线（关联需求ID/需求数/健康等级）
- 第6章基线能力附录：L3/L4 项逐个编号并标注评估结果和等级
- 不在正文中展开 C-DARHS 逐项评估详情（评估过程在执行时记录但不在 Spec 中输出）

### 1.5 Phase 1 质量自检

对照功能点Spec 模板末尾"填写检查清单" C1~C10 逐项核对，外加 P1-1~P1-5 方法论专项检查：

## Phase 2：逐功能点产出三件套

Phase 2 基于 Phase 1 的功能点清单，对每个功能点逐一生成三件套 Spec。

### 2.1 确定目标功能点

```
用户是否指定了功能点编号？
    ├── 指定了单个编号 → 只处理该功能点
    ├── 指定了多个编号 → 逐个处理，一个完成后再开始下一个
    └── 未指定（或说"全部"）→ 列出功能点清单，请用户选择
```

**批量处理原则**：每个功能点独立生成；前一完成后汇报进度再开始下一个；用户可随时中断。

### 2.2 针对性资料解析

对当前功能点，从资料区中**深度过滤**相关素材：

- **历史需求 xlsx**：按功能点关键词二次过滤，逐条读取 `需求分析` 原文，按六维度摘录（业务规则/场景/字段/参数/数据表/边界），每条标注需求编号。
- **功能清单 md**：定位当前功能点章节，提取参数配置、数据表、数据流向。
- **跨线/关联**：仅在资料区明确提及时记录。

### 2.3 功能点级梳理论证

- **功能编号体系**：拆为父级子功能点（`<编号>-001` ~ `-00N`），下设子项（`-001-01` ~）。
- **子主题清单**：每个父级子功能点 = 功能概述 + 用户角色 + 场景 + 数据字段 + 验收标准。
- **业务规则清单**：BR-001~，每条从需求原文可逐字对应。
- **约束**：业务/技术/非功能约束，指标数值必须来自资料区。
- **排除范围**：对照 Phase 1 第6章，确认不越界。
- **关键决策**：仅记录资料区中明确出现的决策。

### 2.4 生成三件套

按以下顺序生成：**先 -Spec，再 PM-Spec，最后 Analyst-Spec**。

#### 2.4.1 Spec（研发视角）（-Spec.md）

按 `assets/base-spec-template.md`（10 章扩展模板）：文档索引（关联文档必须包含 Phase 1 功能点Spec）；第1章文档概述（目的/范围/术语/阅读指南/参考文档）；第2章功能背景与定位（背景/定位/目标用户/核心价值）；第3章业务流程设计（Given/When/Then 主流程/异常流程/边界流程）；第4章数据模型设计（数据结构/状态/参数）；第5章接口契约设计（API列表/详细设计/错误码）；第6章技术方案设计（页面路径/技术栈/关键点/部署）；第7章测试用例预设计；第8章非功能性要求；第9章依赖与风险；第10章附录（流程图/时序图/参考文档）。

> 📌 第3~10章为设计实现层：资料区信息充足时可完整填写，资料区信息不足的章节用 `⏳ 待确认` 标记，绝不编造路径/表名/接口/指标数值。

#### 2.4.2 PM-Spec（_PM-spec.md）

按 `assets/pm-spec-template.md`：目标一句话、约束（业务≥3条/技术/非功能）、验收标准 AC、排除范围、关键决策记录、优先级、关联文档（必须引用 Phase 1 功能点Spec）。

#### 2.4.3 Analyst-Spec（_Analyst-spec.md）

按 `assets/analyst-spec-template.md`：功能编号体系（树形+表）、核心业务流程（Mermaid ≥2个）、功能规格说明（每个子功能点：概述/角色/场景/AC，**不含数据字段定义**）、排除范围、业务规则清单、关联文档（必须引用 Phase 1 功能点Spec）、**待确认问题清单**。

### 2.5 Phase 2 质量自检

对照 S1~S12 溯源核查表、各模板检查清单逐项复核。**发现编造内容→立即删除→改为 ⏳ →登记到 Analyst-Spec 第七章。**

### 2.6 输出优化（后处理）

三件套生成完成后，执行以下清理步骤，确保输出文档干净、合规：

#### 2.6.1 删除来源标注与技术引用

将 Spec 正文中所有**来源标注**和**技术引用**删除，保持文档简洁：

| 删除内容 | 示例 | 说明 |
|---------|------|------|
| 来源标注 | `（来源：代码 EmgEmrStatusEnum）`、`（来源：需求 913183）` | 开发阶段，来源信息对读者无意义，全部删除 |
| TFS需求号 | `需求 430023`、`（1078250）`、`需求1469382` | 具体编号读者不关心，仅保留"需求"二字（在合理语境中） |
| 代码引用 | `（#1519667）`、`、代码 check_create_permission` | 代码注释和引用号删除 |
| 字段来源行 | `> 字段来源：代码扫描 pages/main/index.js...` | 整行删除 |

**清理规则**：
- 删除所有 `（来源：代码...）`、`（来源：需求...）` 格式的括号注释
- 删除所有 `（需求 XXXX、YYYY）` 格式的括号需求号
- 删除 `需求 XXXX`（数字前有空格）和 `需求XXXX`（数字直接附着）两种格式的需求号
- 删除 `（#XXXXXX）` 格式的引用号
- 删除 `、代码[^）|，,\n]*` 格式的代码引用残留
- 删除 `> 字段来源/字段名/结构来源：代码...` 整行
- 清理空括号 `（）`、多余空格、连续的空白行

**特殊保护**：保留表格结构（`|` / `|---`）、JSON 示例数据、状态码（如 `960074`、`390030405`）、错误码（如 `WB0220010042`）、概念ID（如 `138126/138127`）等非TFS编号。

#### 2.6.3 删除 PM-Spec 业务约束表的"来源"列

#### 2.6.4 表格完整性保护

- 不得删除或修改表格的 `|` 分隔符
- 不得删除或修改表格的 `|---` 分隔线

## 常见违规场景警示

| 违规行为 | 正确做法 |
|---------|---------|
| 需求只说"支持自动同步"，你写"系统每5分钟自动同步一次" | 频率不在资料区就不写，标记 `⏳ 待确认` |
| 需求列表有"患者姓名"，你补充了"患者性别""出生日期" | 需求没列的就是没有 |
| 需求提到一处业务规则，你推理出另外两条"配套规则" | 需求中没有的规则不写 |
| 功能清单没有性能指标，你写上"响应时间<2秒" | 资料区没有的指标写 `⏳ 待确认` |
| 需求提到"医生"角色，你细分为"主任医师/主治医师/住院医师" | 需求用什么粒度就用什么粒度 |
| Phase 1 功能清单没有某个功能点，Phase 2 你自行增加 | Phase 2 的功能编号必须在 Phase 1 第5章中注册 |

## 失败降级速查

| 场景 | 处理 |
|------|------|
| 无功能模块名称/编号 | 停止，请用户提供 |
| 资料区不可读或空 | 停止，请用户提供资料区 |
| Phase 1 模板缺失 | 停止，请用户提供模板 |
| 无 npm/node 环境且无法提取 xlsx | 降级：请用户另存为 CSV 或提供文本版 |
| 资料区中无功能清单 md | **不停止**。从历史需求 xlsx 标题聚类或其他材料中提取候选条目。功能清单缺失导致的功能ID、参数说明、数据表清单等信息标记 `⏳ 待确认` |
| 历史需求 xlsx 中"模块名称"列大量为空（如住院历史需求清单） | **不停止**。按标题关键词（如"病历书写""会诊""模板""诊疗信息""打印""签名"）聚类识别模块归属；无法确认归属的需求标记 `⏳ 待确认：需人工确认模块归属` |
| 资料区中无历史需求 xlsx | **不停止**。以功能清单 md 为主素材。业务背景、需求分析、用户角色等信息标记 `⏳ 待确认` |
| 资料区中无功能清单 md 也无历史需求 xlsx | **不停止**。从操作手册、设计文档等其他材料中提取候选条目。大量信息标记 `⏳ 待确认` |
| 某功能点资料区信息严重不足 | 写出已有内容，其余标记 `⏳ 待确认`，记录后继续下一个 |
| 资料区场景数量不足 R5 要求 | 写出已有场景，不足部分标记 `⏳ 待确认` |
| 资料区无性能/安全指标 | 写 `⏳ 待确认`，不填默认值 |
| 用户中途要求停止批量处理 | 汇报已完成清单，记录下一个待处理编号 |
| 用户未提供代码仓库路径 | **不停止，使用默认代码仓库 `E:\39EMR\sr-next`**。代码扫描是强制前置步骤，扫描后继续 |
| 代码仓库路径不可读或无权限 | 降级：提示用户检查路径，记录原因；API端点、数据实体、代码架构等章节标记 `⏳ 待确认`。不得以需求文本中的零散代码线索替代扫描 |
| 代码仓库过大导致扫描超时（>300个Controller 或 >500个PO） | 降级：只扫描顶层目录结构 + 各模块的 Controller 文件名列表（不深入解析方法），其余标记 `⏳ 待确认` |
| 代码仓库结构与 module-checklist.md 不匹配 | **不停止**。扫描结果按实际目录结构输出，模块映射表标记 `⏳ 待确认：需人工确认代码与业务模块的对应关系` |
| 前端代码仓库结构与常见模式不一致（无 src/router/modules 等目录） | 降级：只列出顶层页面目录，不提取路由配置，页面结构标记 `⏳ 待确认` |
