# 约定：命名 / 版本 / 引用

本文件固化 generate-spec-v1 的公共约定，Phase 1 功能点Spec 与 Phase 2 三件套统一遵循。

---

## 1. 功能编号命名

- **模块编码与名称**：以 `references/module-checklist.md` 为唯一权威来源。Phase 0 启动时必须先对照 module-checklist 确认模块是否存在。
- **模块级**：模块功能点编号，格式 `<产品线缩写>-<模块编号>-<子系统缩写>`（如 `BLGL-13-BASY`）。
- **功能点编号**：`<模块编号>-<3位序号>`（如 `BLGL-13-BASY-001`），在 Phase 1 功能点Spec 第5章中注册。
- **REQ-ID**：Phase 2 三件套使用 `<功能点编号>`（规范单短线）。
- **父子层级**：Phase 2 中展开子功能点时，父级 `<编号>-001`，子项 `<编号>-001-01`，逐级下钻。
- **目录名**：允许带变体（如 `BLGL-13-BASY--001_患者信息管理`），但文件内部编号必须用规范单短线。

## 3. 三件套展示名称规范

### 3.1 展示名称映射

三件套在文档索引（章节索引/关联文档索引）及文档正文引用处统一使用以下展示名称，不得使用其他变体：

| 文档 | 展示名称 | 说明 |
|------|---------|------|
| -Spec | Spec（研发视角） | 覆盖业务背景、数据模型、接口契约、技术方案 |
| PM-Spec | PM-Spec（业务视角） | 覆盖约束、验收标准、排除范围、决策记录 |
| Analyst-Spec | Analyst-Spec（产品视角） | 覆盖功能编号体系、业务流程、场景规则、验收标准 |

### 3.2 排序规则

在文档索引的章节索引和关联文档索引中，三件套按以下顺序排列：

**PM-Spec（业务视角）→ Analyst-Spec（产品视角）→ Spec（研发视角）→ 功能点Spec（模块级）**

此排序基于读者从"做什么"（业务视角）到"做成什么样"（产品视角）再到"怎么做"（研发视角）的认知路径。

## 6. 优先级定义

- **P0（核心必须）**：不做则需求无意义，必须本次交付
- **P1（重要但非核心）**：影响用户体验或效率，本次交付优先级高
- **P2（附加价值）**：锦上添花，可延后到后续版本

## 7. 引用规范

- 引用法规规范名时保留原名，不缩写。
- 引用历史需求时写"需求<编号>"。
- 引用概念ID、参数路径、表名时保持材料原文格式。
- **引用 Phase 1 功能点Spec 时写完整文件名 + 版本号**。

## 8. Phase 间口径一致性

### 8.1 必须一致的字段

| 字段 | Phase 1 位置 | Phase 2 位置 |
|------|-------------|-------------|
| 功能点编号 | 第5章"功能点编号"列 | 三件套标题、REQ-ID、文件名 |
| 功能点名称 | 第5章"功能点"列 | -Spec 1.1、PM-Spec 目标 |
| 模块ID | 第1章 | 三件套文档索引 |

### 8.2 允许展开但不允许偏离的字段

| 字段 | Phase 1 | Phase 2 |
|------|---------|---------|
| 功能描述 | 第5章一句话 | 三件套详细展开，核心语义不得偏离 |
| 核心用户 | 第1章角色列表 | 各功能点细化到涉及的角色子集，不得新增角色 |
| 排除范围 | 第6章基线能力 | 各功能点补充功能点级排除项，不得冲突 |

### 8.3 冲突解决

若 Phase 2 执行中发现 Phase 1 需要调整：
1. 先在 Phase 2 输出中标注 `⏳ 待确认：建议 Phase 1 同步调整（具体建议）`
2. 登记到 Analyst-Spec 待确认问题清单
3. Phase 1 正式调整由用户决策后统一执行

## 10. 分类标签与健康度（方法论落地）

### 10.1 分类标签（Phase 1 功能点清单 5.1 节必填列）

| 维度 | 标签示例 | 判定依据 |
|------|---------|---------|
| 交互模式 | 单实体操作 / 多实体协作 / 跨角色流转 / 跨系统交互 | 候选条目的协作描述 |
| 业务性质 | 临床业务 / 管理业务 / 财务业务 / 平台支撑 | 功能归属 |
| 安全等级 | 高 / 中 / 低 | 与 C-DARHS 的 H 联动：H✅→高 |
| 使用频率 | 高频（每日千次以上）/ 中频 / 低频 | 资料区有依据则标，无依据 `⏳ 待确认` |
| 成熟度 | 稳定 / 频繁变更 / 新上线 | 资料区有依据则标，无依据 `⏳ 待确认` |

标签判定必须基于资料区事实，安全等级与 H 联动，其余维度无依据标记 `⏳ 待确认`，不凭经验猜测。

### 10.2 健康度基线（Phase 1 功能点清单 5.1 节健康度列）

- **关联需求 ID / 需求数**：资料区可统计时填写（如历史需求 xlsx 归属本功能点的需求编号列表），无数据标记 `⏳ 待确认`。
- **健康等级**：有完整指标数据才判 🟢 全指标正常 / 🟡 1~2 项超阈值 / 🟠 3~4 项超阈值 / 🔴 全部超阈值或极端值（方法论 §5.2）；只有部分数据时给异常模式提示（设计不完整/需求过载/频繁变更/来源单一，§5.3）并标记 `⏳ 待确认`。
- **绝不虚构**需求数、增速、来源集中度或健康等级。完整健康度统计与看板属治理阶段（方法论 §7.3"阶段三：健康度分析与治理"），由治理团队基于需求绑定数据滚动维护，不在 Phase 1 输出中展开。

## 11. 功能点中文名称命名规则

功能点**中文名称**（Phase 1 功能点清单第5章"功能点"列、Phase 2 三件套文件名与标题）遵循以下规则。

### 11.1 核心形式：动宾短语

采用「动词 + 宾语」动宾结构，表达"这个功能点做什么"，而非"这是什么页面/对象"。例外：纯页面/实体型功能点可用名词短语（如「中医诊疗信息页」）。

| ✅ 动宾（正确） | ❌ 名词/载体（错误） |
|---|---|
| 病历签署、报告引用、药品目录同步 | 病历信息页、报告列表、药品目录 |

### 11.2 单动词原则（含「与」字用法）

一个功能点名称只允许一个核心动词；用「与」连接时，两端必须属于同一业务闭环，且只能是以下三种关系之一：

| 关系 | 含义 | 正例 |
|---|---|---|
| ① 动作 → 自动联动/结果 | 前一动作触发后一结果 | 患者入院登记与床位分配 |
| ② 流程前后环节 | 同一流程串联 | 病历解锁申请与审批 |
| ③ 决策的两个分支 | 一个判断的两种出口 | 检验标本核收与拒收处理 |

**例外（团队已确认保留）**：正向动作 + 其反向动作的强耦合对允许合并命名，如「病历签署与撤销」「病历打印与打印锁定」「急诊病历归档与召回」。这类反相对在业务上互为镜像、拆分收益低，团队决议保留为单功能点。

**判定方法**：把「与」换成「，并且」读一遍——语义通顺、是同一件事的延续 → 合法；读成两个不相干的事 → 应拆（反向对除外）。

### 11.3 一句话测试

每个名称都能补全成一句"谁，在什么场景下，做了什么，达成什么业务结果"。展开需 2 句以上 → 粒度过粗，应拆；展开后只是增删改查 → 太细或属基线能力。

### 11.4 基线能力词禁止

以下词不能作为功能点名称核心（属 L3/L4 基础能力，归入附录）：

- 纯 CRUD：新增 / 删除 / 修改 / 查询 / 列表 / 导出 / 打印
- 纯配置：维护 XX 字典 / 配置角色 / 设置科室
- 纯技术：XX 接口 / XX 消息通道

区分：`药品目录同步与价格联动` 的「同步」是跨系统联动（功能点）；`维护药品字典` 的「维护」是配置（非功能点）。判据仍是方法论 §2.2 的"是否涉及上下文交互"。

### 11.5 动词词表统一

| 概念 | 用 | 不用 |
|---|---|---|
| 生成新记录 | 创建 | 新建、生成 |
| 修改内容 | 编辑 | 书写、录入、修改（作"编辑"近义时） |
| 同意/签发 | 签署 | （CA 签名才用「签名」） |
| 看数据 | 查看（点开看）/ 浏览（翻阅列表） | 展示（结果非动作，不作核心动词） |
| 取用他处数据 | 引用 | 引入、调阅、带出 |
| 数据一致性 | 同步 | 更新、刷新 |
| 人工裁决 | 审批 | （规则校验用「审核」） |

### 11.6 名词词表统一

| 概念 | 用 | 不用 |
|---|---|---|
| 病历模板 | 模板 | 模版 |
| 既往就诊记录 | 历史病历 | 既往病历、历史病历记录 |
| 检查/检验结果 | 报告 | — |

**「缺省值」保留**：`模板缺省值配置` 中的「缺省值」是领域既定术语（需求原文、代码实体 `EmgEmrTemporaryDataPO` 均用「缺省值」），与「默认模板」是不同业务概念，不得改为「默认值」。

### 11.7 名实相符 + 唯一性

- 名称必须准确反映正文业务边界（禁止模块叫「案例管理」却挂「病历综合查询」等名实不符）。
- 同一能力全库只出现一个功能点（禁止「病历综合查询」在两个模块各挂一个、需求号重合）。

### 11.8 长度

中文名 4~12 字为宜，上限 16 字。

### 11.9 命名自检清单

每命名一条逐项打勾：

1. ☐ 是否「动词 + 宾语」？
2. ☐ 是否只含一个核心动词（或属反向对例外）？
3. ☐ 若用「与」，两端是否属于同一闭环（或反向对例外）？
4. ☐ 能否一句话展开成「谁/场景/动作/结果」？
5. ☐ 是否避开了基线词？
6. ☐ 动词、名词是否在统一词表内？
7. ☐ 是否名实相符、全库唯一？
8. ☐ 字数是否 4~16 字？

- 三件套展示名称规范变更时，更新第3节并同步 SKILL.md 输出优化流程。
