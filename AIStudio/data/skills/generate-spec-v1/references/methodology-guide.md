## 1. 核心概念

**功能点（Feature Point, FP）**：系统中一个**具有完整业务语义的最小独立功能单元**——代表用户在特定业务场景下完成的一个有意义操作，涉及上下文交互（多实体协作、多角色流转、状态变更、跨系统调用中的至少一种），是需求绑定的最小锚点。

**一句话判定测试**：能否用一句话说清"谁，在什么场景下，做了什么，达成了什么业务结果"？

- 能 → 可能是功能点
- 不能 → 需要再审视

### 1.1 什么不是功能点

| 不是功能点 | 原因 | 如何处理 |
|---|---|---|
| 对象的增、删、改、查、列表、导出 | 基线能力，不构成业务功能 | 归属于所在业务场景，作为功能点的"底层支撑" |
| 页面/表单本身 | 载体，不是功能 | 页面是功能点的容器，一个页面可承载多个功能点 |
| 字段级校验、格式转换 | 技术细节 | 归属于承载它的功能点 |
| 按钮/操作入口 | UI 元素 | 入口背后的业务逻辑才是功能点 |
| 权限配置、角色管理 | 平台基线能力 | 归入"平台支撑"类，不计入业务功能点 |
| 接口本身 | 技术通道 | 接口承载的业务操作才是功能点 |

> ⚠️ **"查询"的特殊判定**：基线过滤中的"查/列表"仅指**单对象简单查询**（单表单字段过滤、无业务逻辑）。包含**复杂检索特征**的查询（跨权限/跨范围、多条件组合、跨系统取数、触发审计留痕）**不得排除**，按方法论 §8.2 案例应升级为功能点"多维度患者检索与权限过滤"并进入 C-DARHS 判定。判定口诀：**"一个输入框查一个表"是基线；"多条件+多范围+跨系统+留痕"是功能点。**

### 1.2 关键区分：基线能力 vs 功能点

**判断核心**：是否涉及**上下文交互**——多实体协作、状态流转、跨系统调用、业务规则推导中的至少一种。

| 基线能力（❌ 不是功能点） | 功能点（✅ 是功能点） |
|---|---|
| "新增一条医嘱" | "开立长期医嘱并自动分解为执行任务" |
| "查询患者列表" | "患者入院登记并触发床位分配和押金缴纳" |
| "修改药品信息" | "药品目录同步并触发价格联动调整" |
| "删除检验报告" | "检验报告审核发布并推送给临床医生" |
| "导出费用清单" | "费用预审并触发医保规则校验和自付比例计算" |

## 2. 三层漏斗 + C-DARHS 判定流程

```
全部候选条目（来自功能清单md / 历史需求xlsx聚类 / 其他材料）
  ↓
第一层：基线过滤 → 排除纯CRUD/导出打印/字典配置/纯技术接口
   └── ⚠️ 复杂检索（跨权限/多条件/跨系统/留痕）不排除，进入第二层
  ↓
第二层：C-DARHS 六要素评估 → 逐项标记 ✅/❌ 并写一句话说明
  ↓
第三层：L1-L4 分级
  ├─ L1（≥5要素 + 必须含C+D+A+H）→ ✅ 纳入功能点清单，写完整Spec
  ├─ L2（≥4要素 + 必须含C+A）→ ✅ 纳入功能点清单，Spec可简化
  ├─ L3（≤3要素）→ ❌ 记录"基础能力附录"，不参与健康度分析
  └─ L4（≤2要素 + 不含H）→ ❌ 仅作技术实现细节，不记录
  ↓
第四层：粒度校准 → 拆分测试 / 合并测试 / 一句话测试
  ↓
输出：功能点清单（L1/L2）+ 基础能力附录（L3/L4）+ 分类标签 + 健康度基线
```

**关键规则**：**只有 L1 和 L2 才算"功能点"**，才需要绑定需求、计算健康度。L1 必须写完整 Spec；L2 Spec 可简化（仅需主流程+异常流程）。

**基线排除速查**：

| 类型 | 判断 | 复杂检索例外 |
|------|------|-------------|
| 纯 CRUD | 单对象增删改查 | 多条件组合检索不排除（诊断/手术/时间/医疗组等） |
| 导出/打印 | 数据呈现形式 | — |
| 字典/配置 | 单点参数配置 | — |
| 纯技术接口 | 技术通道 | 接口承载的业务操作不算 |

> **复杂检索升功能点的特征**（方法论 §8.2）：跨权限/跨范围（科室 vs 全院）、多条件组合、跨系统取数、触发审计留痕——满足任一即不排除，进入 C-DARHS 判定。

## 3. C-DARHS 六要素

| 要素 | 代码 | 判定问题 | 满足标准 |
|------|------|---------|---------|
| **Context** | C | 是否处于端到端业务流程中？上下游是什么？ | 能明确说出触发条件和后续环节 |
| **Decision** | D | 是否包含业务规则判断或人工决策分支？ | 有规则推导、人工审核、异常处理中至少一种 |
| **Action** | A | 是否引起实体状态变更或跨系统消息？ | 创建/更新/删除数据、发送通知、触发下游 |
| **Role** | R | 是否由特定角色执行？不同角色看到的内容不同？ | 有明确的角色绑定和权限控制 |
| **Health-Safety** | H | 是否直接影响患者安全或诊疗质量？ | 错误可能导致患者伤害、用药错误、诊断延误 |
| **SLA** | S | 是否有明确的性能/可用性/一致性要求？ | 响应时间、并发数、可用性有量化指标 |

**评估方式**：每个要素标记 ✅ 或 ❌，并写一句话说明。无量化指标时 S 标记 ❌ 并在备注说明（不得编造指标值）。

## 4. L1-L4 分级

| 等级 | 判定规则 | 处理方式 |
|------|---------|---------|
| **L1 核心功能** | 满足 ≥5 要素，**必须包含 C+D+A+H** | ✅ 纳入功能点清单，必须写完整 Spec，参与需求绑定和健康度分析 |
| **L2 重要功能** | 满足 ≥4 要素，**必须包含 C+A** | ✅ 纳入功能点清单，Spec 可简化（主流程+异常流程），参与需求绑定和健康度分析 |
| **L3 基础功能** | 满足 ≤3 要素 | ❌ 不单独作为功能点，记录在"基础能力附录"，不参与健康度分析 |
| **L4 技术/字典功能** | 满足 ≤2 要素且不含 H | ❌ 不计入功能点，仅作为技术实现细节 |

**判定要点**：
- **H 是关键分级要素**：涉及患者安全的（如危急值、配伍禁忌、效期拦截）通常为 L1；不涉患者安全的（如纯财务）即使满足 5 要素也是 L2。
- L1:L2 建议比例约 **3:7 或 4:6**（方法论经验值，偏离时在功能点清单备注说明）。

## 5. 粒度校准

| 测试 | 判定 |
|------|------|
| **拆分测试** | 能否拆出 ≥2 个同样满足 L1/L2 的子步骤？能 → 拆分（当前过粗）；不能 → 粒度合适 |
| **合并测试** | 两个功能点是否服务于同一业务目标，且触发条件、角色、数据完全相同？是 → 合并（当前过细）；否 → 粒度合适 |
| **一句话测试**（终极检验） | 能否用一句话说清"谁，在什么场景下，做了什么，达成什么结果"？能 → 粒度合适；需多句 → 过粗；觉得很 trivial → 过细 |

## 6. 层次结构与分类维度

### 6.1 四层层次结构

```
业务域（Domain）  →  10~20 个
  └─ 功能模块（Module）  →  每域 5~15 个
       └─ 功能点（Feature Point, FP）  →  每模块 5~30 个（L1/L2）
            └─ 子功能点（Sub-FP，可选）  →  每功能点 0~5 个
```

**关键规则**：
- **需求绑定层级**：需求绑定到功能点或子功能点，不能绑定到业务域或功能模块（太粗）。
- **健康度统计层级**：健康度按功能点统计，向上聚合到功能模块和业务域。
- **子功能点是否独立**：仅当满足 L2 及以上标准、且用户感知为"独立操作"时才单独列出；否则作为功能点内部步骤。
- **业务域划分原则**：业务独立性、角色聚合、数据内聚、流程完整（能独立完成端到端业务闭环）。
- **功能模块划分原则**：业务目标导向、角色聚焦、数据共享。

### 6.2 分类维度（标签体系）

除层次结构外，每个功能点打多个分类标签，用于多维度分析：

| 维度 | 标签示例 | 用途 |
|------|---------|------|
| **交互模式** | 单实体操作 / 多实体协作 / 跨角色流转 / 跨系统交互 | 识别复杂度、发现设计不完整 |
| **业务性质** | 临床业务 / 管理业务 / 财务业务 / 平台支撑 | 按业务性质统计需求分布 |
| **安全等级** | 高（直接影响患者安全）/ 中 / 低 | 识别高风险功能点 |
| **使用频率** | 高频（每日千次以上）/ 中频 / 低频 | 识别性能瓶颈 |
| **成熟度** | 稳定 / 频繁变更 / 新上线 | 识别需要重构的功能点 |

**落地**：Phase 1 功能点清单表增加上述 5 列。标签判定依据**资料区事实**：交互模式按候选条目的协作描述判定；业务性质按功能归属判定；安全等级与 C-DARHS 的 H 要素联动（H✅→高，H❌→中/低）；使用频率、成熟度资料区有依据则标注，无依据标记 `⏳ 待确认`。

## 7. 健康度分析模型

### 7.1 健康度指标

| 指标 | 定义 | 计算方式 | 健康阈值 |
|------|------|---------|---------|
| **需求密度** | 功能点关联的需求数量 | 统计绑定的需求总数 | 2~10 个/功能点为正常 |
| **需求增速** | 单位时间内新增需求数 | 近 6 个月需求数 / 6 | < 2 个/月为正常 |
| **需求类型分布** | 需求中"新增/修改/缺陷"的比例 | 统计各类型占比 | 修改类 < 50% 为正常 |
| **变更频率** | 功能点被修改的次数 | 近 12 个月的代码变更次数 | < 12 次/年为正常 |
| **需求来源集中度** | 需求来源的科室/角色数量 | 统计不同来源数 | ≥ 3 个来源为正常 |

### 7.2 健康等级

| 健康等级 | 判定规则 | 含义 | 建议动作 |
|----------|---------|------|---------|
| 🟢 **健康** | 所有指标在阈值内 | 功能设计完整、稳定 | 保持现状，持续监控 |
| 🟡 **关注** | 1~2 个指标超出阈值 | 可能存在设计不完整或轻微过载 | 分析原因，纳入下季度优化计划 |
| 🟠 **预警** | 3~4 个指标超出阈值 | 设计不完整或需求过载 | 优先纳入重构计划，安排专项优化 |
| 🔴 **危险** | 所有指标超出阈值，或出现极端值 | 严重设计缺陷或需求失控 | 立即启动重构，暂停新需求接入 |

### 7.3 异常模式识别

| 模式 | 特征 | 建议动作 |
|------|------|---------|
| **设计不完整（需求稀疏）** | 需求密度 < 2 个/功能点 + 来源集中度 = 1 + 属于 L1 | 调研是否覆盖完整流程；考虑降级 L2 或合并 |
| **需求过载（需要重构）** | 需求密度 > 10 个/功能点 + 增速 > 2 个/月 + 修改类 > 50% | 拆分职责；引入配置化/规则引擎；暂停新需求，优先重构 |
| **频繁变更（稳定性差）** | 变更频率 > 12 次/年 + 缺陷类 > 30% | 统计 Bug 类型；评估重新设计；加强评审和测试 |
| **来源单一（通用性不足）** | 来源集中度 = 1 + 需求密度 > 5 个/功能点 | 调研其他科室/角色需求；改造为通用功能或配置化 |

### 7.4 在 Phase 1 中的落地（健康度基线）

健康度统计依赖需求绑定数据，Phase 1 阶段往往无历史绑定记录。此时在功能点清单表的健康度列登记**当前可得的基线事实**（资料区有则填、无则 `⏳ 待确认`），不虚构数值、不编造健康等级：

- **关联需求 ID / 需求数**：资料区可统计时填写（如历史需求 xlsx 中归属本功能点的需求编号列表），无数据标记 `⏳ 待确认`。
- **健康等级**：有完整指标数据才判定 🟢🟡🟠🔴；只有部分数据时给出**异常模式提示**（如"需求过载（资料区需求数 N > 10）"）并标记 `⏳ 待确认：健康等级需需求绑定数据支撑`。
- **完整健康度统计与看板**（需求密度、增速、来源集中度、看板视图）属于持续治理阶段（方法论"阶段三：健康度分析与治理（每季度）"），由治理团队基于需求绑定数据滚动维护，**不在 Phase 1 输出中展开**。

## 8. 编号规则

### 8.1 方法论文档通用格式（参考）

- **功能点 ID**：`FP-{域缩写}-{模块缩写}-{序号}`，如 `FP-IN-ADM-001`（域缩写 2~5 大写字母，模块缩写 2~5 大写字母，序号 3 位从 001 起）。
- **基础能力 ID**：`BC-{域缩写}-{模块缩写}-{序号}`，如 `BC-IN-ADM-001`。
- **需求 ID**：`R-{序号}` 或 `REQ-{序号}`，由需求管理系统生成，与功能点无关。

### 8.2 本技能实际采用格式（落地）

> 本技能以 `references/module-checklist.md` 的模块编码为唯一权威来源（如 `BLGL-13-BASY`），**不另起 FP 格式**。理由：模块编码已在公司内部唯一分配，直接沿用可保持历史引用连续。

| 类型 | 格式 | 示例 |
|------|------|------|
| 模块编码 | `<产品线缩写>-<序号>-<模块缩写>` | BLGL-13-BASY |
| 功能点 ID | `<模块编码>-<3位序号>` | BLGL-13-BASY-001 |
| 基础能力 ID | `BC-<模块缩写>-<3位序号>` | BC-BASY-001 |
| 子功能点 ID | `<父功能点ID>-<序号>` | BLGL-13-BASY-001-01 |

### 8.3 编号管理规则（方法论要求，技能沿用）

1. **唯一性**：每个功能点/基础能力的 ID 必须全局唯一。
2. **不可复用**：功能点删除后其 ID 不可重新分配（避免历史数据混淆）。
3. **序号递增**：同一模块内功能点序号递增，不可跳号。
4. **缩写统一**：业务域/模块缩写由产品架构组统一分配，不可自行创建。
5. **变更记录**：功能点 ID 变更需记录在"编号变更日志"。

### 8.4 与 FP 格式的映射（如需对齐治理规范）

当需要向治理规范文档（如健康度看板、重构报告）对齐时，按以下规则把本技能编号映射为方法论通用格式：

- 域缩写 ← module-checklist 中产品线对应的业务域（如"WiNEX 病历管理"→ 病历域 BL）；产品线未定义统一缩写时标注 `⏳ 待确认`。
- 模块缩写 ← module-checklist 模块编码末段（如 `BLGL-13-BASY` → 缩写 `BASY`）。
- 序号 ← 功能点/基础能力序号。

例：`BLGL-13-BASY-001` → `FP-BL-BASY-001`。**该映射仅用于向治理文档对齐，Phase 1/Phase 2 文档内部编号一律用 module-checklist 编码。**

## 9. 执行节奏与参考案例

### 9.1 三阶段执行节奏（方法论）

| 阶段 | 内容 | 周期 |
|------|------|------|
| **阶段一：功能点划分** | 收集功能清单→基线过滤→C-DARHS→分级→粒度校准→层次归类→打标签，输出功能点清单表+基础能力附录 | 3~6 个月 |
| **阶段二：需求绑定** | 历史需求逐条绑定功能点；新增需求强制绑定；月度校验绑定率（历史>90%、新增=100%） | 持续进行 |
| **阶段三：健康度分析与治理** | 计算健康度→识别异常→治理决策→效果评估 | 每季度 |

**本技能对应关系**：Phase 1（功能点 Spec）≈ 阶段一；Phase 2（三件套）≈ 阶段一的细化产出 + 阶段二的部分输入；健康度治理属于阶段三，由治理团队基于本技能产出的功能点清单滚动维护。

### 9.2 参考案例（方法论 §八）

方法论提供了 4 个 HIT 场景完整演示（入院管理、药品管理、检验检查、费用结算）和住院医嘱录入、患者列表查询、药品目录同步三个单点案例，可作判定示例。核心结论：

1. **基线过滤率高**：典型场景约 50% 原始条目被排除为基线能力（CRUD、打印、导出）。
2. **L1 集中在安全相关**：危急值、配伍禁忌、效期拦截等涉患者安全功能为 L1。
3. **L2 占比最高**：多数跨实体/跨系统交互功能为 L2。
4. **业务域特征不同**：药品域安全要求高（L1 占比 ~43%），费用域 L1 为 0。

## 10. 总结（方法论核心要点）

1. **明确边界**：CRUD 不是功能点，有上下文交互的 function 才是功能点。
2. **三层漏斗**：基线过滤 → C-DARHS 判定 → L1-L4 分级 → 粒度校准。
3. **层次结构**：业务域 → 功能模块 → 功能点 → 子功能点。
4. **分类标签**：交互模式/业务性质/安全等级/使用频率/成熟度 5 维打标。
5. **健康度模型**：需求密度、增速、类型分布、变更频率、来源集中度 + 4 级健康等级 + 4 类异常模式。
6. **落地工具**：Excel 模板（功能点清单/需求绑定/健康度统计/基础能力附录）+ 操作指南 + 案例演示。

**验收参考标准**（方法论 §7.1）：功能点数量 500~2000；L1:L2 比例约 3:7 或 4:6；每个功能点通过"一句话测试"；业务域和功能模块划分清晰无重叠。
