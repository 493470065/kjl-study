# rationality-analysis-v1 — 设计合理性分析报告生成

## 技能概述

本技能基于**需求清单问题点分类统计报告**，对照设计文档/架构文档，对每个问题点进行设计覆盖度评估，生成结构化的设计合理性分析报告。

核心方法论源自两个参考文档：
- **01 辅助录入模块需求清单_问题点分类统计.md** — 问题点分类、关键词匹配、数据统计
- **02 辅助录入模块设计合理性分析报告.md** — 五维评分框架、法规合规性、竞品对比、执行建议

## 触发条件

以下场景**必须**使用本技能：
- 用户要求"做设计合理性分析"、"评估设计"、"做健康度分析"
- 用户要求"生成设计合理性分析报告"、"按五维评分评估"
- 用户提供需求清单问题点分类统计 + 设计文档，要求做覆盖度评估
- 用户需要将需求问题点映射到设计覆盖度评估

## 输入参数

| 参数 | 说明 | 必填 | 默认值 |
|------|------|------|--------|
| 模块名称 | 要分析的模块名称（如"辅助录入"、"病历管理"） | ✅ | — |
| 需求清单路径 | 问题点分类统计报告路径 | ✅ | 从 `E:\37结构性问题治理\04参考资料\{模块名}\` 查找 |
| 设计文档路径 | 详细设计文档/架构文档路径 | ✅ | 从 `E:\37结构性问题治理\04参考资料\{模块名}\` 查找 |
| 输出目录 | 报告输出路径 | ❌ | `E:\37结构性问题治理\04参考资料\{模块名}\` |

## 工作流程

### Phase 1：数据采集与输入验证

**步骤 1.1：读取需求清单问题点分类统计报告**

读取 `01{模块名}需求清单_问题点分类统计.md` 或类似文件，提取以下信息：

1. **数据概况** — 总需求数量、功能性/软件质量/支持单/内部虚拟需求分布
2. **问题点分类汇总表** — 所有问题点及其需求数量统计（按14个大类分组）
3. **TOP 10 问题点排名** — 按需求数量排序的问题点排名
4. **按菜单分类分布** — 菜单分类维度的需求分布
5. **问题点分类关键词说明** — 每个问题点的关键词匹配规则（用于后续分析）

如果需求清单文件不包含问题点分类统计，则先通过**关键词匹配分类法**对原始需求进行分类（使用关键词规则重新生成分类统计）。

**步骤 1.2：读取设计文档/架构文档**

查找并读取以下类型的设计文档：
1. 详细设计文档（如 `*详细设计*.md`、`*设计*.md`）
2. 架构设计文档（如 `*架构*.md`、`*架构设计*.md`）
3. 设计规则文档（如 `*规则*.md`、`*规则说明*.md`）
4. 接口文档（如 `*接口*.md`、`*API*.md`）
5. 其他相关文档（如 `*规范*.md`、`*方案*.md`）

> **注意**：如果设计文档路径不存在或不可读，在相关章节标记 ⏳待确认，并记录缺失的具体文档名称。

**步骤 1.3：输入验证**

确认已获取以下信息，缺失则标记并继续：
- ✅ 问题点清单（含需求数量）
- ✅ 设计文档内容（至少部分可读）
- ❌ 缺失项在报告中标记为 ⏳待确认

---

### Phase 2：五维评分框架评估

对每个问题点应用 **五维评分框架** 进行设计覆盖度评估：

#### 评估维度

| 维度 | 权重 | 说明 |
|------|------|------|
| 设计覆盖度 | 40% | 设计文档是否覆盖了该问题点的核心需求 |
| 设计合理性 | 25% | 设计方案是否合理、可行 |
| 法规合规性 | 15% | 是否符合相关法规规范要求 |
| 竞品对标 | 10% | 与竞品相比是否存在差距 |
| 需求密度 | 10% | 需求量大小（需求越多越应重视） |

#### 评分等级（五级）

| 等级 | 标记 | 条件 | 优先级 |
|------|------|------|--------|
| **设计合理（良好覆盖）** | ✅ | 设计文档全面覆盖，方案合理，符合法规，达竞品水平 | 无需优化 |
| **基本合理（需细节完善）** | 🟢 | 设计覆盖大部分，但存在细节缺失（如入口不统一、配置缺失） | 低优先级 |
| **部分合理（需补充设计）** | 🟡 | 设计仅覆盖部分，存在明显缺失或设计不完整 | 中优先级 |
| **设计不合理（缺失/严重不足）** | 🔴 | 设计完全未涉及或严重不足，对用户体验影响大 | 高优先级 |
| **非设计范畴** | ⚪ | 属于BUG修复、编辑器原生能力、独立功能模块等非设计范畴 | 不评估 |

#### 一票否决制

以下任一条件满足时，**直接判定为 🔴 设计不合理**，无需逐维评分：
1. 该问题点完全无设计文档覆盖
2. 设计存在重大架构缺陷（如同步加载无异步方案）
3. 违反法规规范要求且无补救措施
4. 竞品已有成熟方案而本系统完全缺失

### Phase 3：逐问题点分析

对每个问题点（包括需求量为0的问题点）进行逐项分析，输出以下内容：

#### 3.1 判定为 ✅ 设计合理的问题点

输出格式：
```
### {问题点名称}（{需求数量}条）

**判定：✅ 设计合理**

**设计覆盖依据**:
- 列出具体的设计文档/规则/组件覆盖情况（至少3条具体依据）
- 引用设计文档中的具体规则编号或章节

**法规规范符合性**:
- 列出相关法规规范及设计如何满足

**竞品对比**:
- 与竞品对比情况说明

> 注：对需求量大但设计合理的问题点，说明实现层面的细节问题仍需通过BUG修复和配置完善解决。
```

#### 3.2 判定为 🟢 基本合理的问题点

输出格式：
```
### {问题点名称}（{需求数量}条）

**判定：🟢 基本合理，需{具体待完善事项}**

**现有覆盖**:
- 列出已有设计覆盖范围

**需完善细节**:
1. 具体缺失点1
2. 具体缺失点2
3. 具体缺失点3

**优化建议**:
```
具体优化方案代码块
```
```

#### 3.3 判定为 🟡 部分合理的问题点

输出格式：
```
### {问题点名称}（{需求数量}条）

**判定：🟡 部分合理，需补充{具体缺失内容}**

**现有覆盖**:
- 列出已有设计覆盖范围

**不合理之处**:
1. 具体问题1
2. 具体问题2
3. 具体问题3

**优化建议**:
```
具体优化方案代码块
```
```

#### 3.4 判定为 🔴 设计不合理的问题点

输出格式：
```
### {问题点名称}（{需求数量}条）

**判定：🔴 设计不合理（{具体问题类型：缺失/严重不足/覆盖不全}）**

**问题现状**:
- 现有设计缺失或不足的具体描述

**需求依据**（典型需求）:
- [需求号] 典型需求描述

**不合理之处**:
1. **架构缺陷**: 具体架构问题描述
2. **用户体验**: 对用户的具体影响
3. **数据/设计缺失**: 缺失的具体内容

**法规规范符合性**:
- 违反的法规及说明

**竞品对比**:
- 竞品已有方案及差距

**优化方案**:
```
具体优化方案代码块（含策略、参数、接口设计等）
```
```

#### 3.5 判定为 ⚪ 非设计范畴的问题点

输出格式：
```
### {问题点名称}（{需求数量}条）

**判定：⚪ 不评估（{具体原因}）**

**说明**: 不属于设计范畴的具体原因说明。

**建议**: 处理建议。
```

### Phase 4：生成综合报告

生成完整的分析报告，包含以下章节：

#### 4.1 覆盖状态汇总表

| 覆盖状态 | 问题点数量 | 需求总量 | 占比 | 优先级 |
|---------|-----------|---------|------|--------|
| ✅ 设计合理（良好覆盖） | N个 | N条 | N% | 无需优化 |
| 🟢 基本合理（需细节完善） | N个 | N条 | N% | 低优先级 |
| 🟡 部分合理（需补充设计） | N个 | N条 | N% | 中优先级 |
| 🔴 设计不合理（缺失/严重不足） | N个 | N条 | N% | 高优先级 |
| ⚪ 非设计范畴 | N个 | N条 | — | 不评估 |

> 说明：需求量为0的问题点标记为「无需求，无需评估」；未分类的问题点标记为「无法评估」。

#### 4.2 各问题点详细分析

按顺序排列：
1. 先 ✅ 设计合理（含0需求无需评估）
2. 再 🟢 基本合理
3. 再 🟡 部分合理
4. 再 🔴 设计不合理
5. 最后 ⚪ 非设计范畴

#### 4.3 按优先级排序的完整汇总表

| 排名 | 问题点 | 需求量 | 判定 | 优先级 |
|------|--------|--------|------|--------|
| 1 | 问题点名称 | N条 | 判定标记 | P0-最高 |
| ... | ... | ... | ... | ... |

优先级规则：
- **P0-最高**：🔴 设计不合理 + 需求量大（>50条）
- **P1-高**：🔴 设计不合理 + 需求量小（<50条）
- **P2-中**：🟡 部分合理 + 需求量大（>30条）
- **P3-低**：🟡 部分合理 + 需求量小 / 🟢 基本合理
- **P4-最低**：🟢 基本合理 + 需求量极小

#### 4.4 法规合规性评估

| 法规要求 | 对应问题点 | 合规状态 | 说明 |
|---------|-----------|---------|------|
| 《法规名称》- 具体要求 | 相关的问题点 | ✅/🟡/🔴 | 说明 |

参考法规清单（按模块类型选择）：
- 《电子病历应用管理规范》- 数据可追溯、操作可审计
- 《电子病历系统功能规范》- 系统响应及时
- 《病历书写基本规范》- 格式标准
- 《医院信息系统功能规范》- 界面清晰
- 其他模块相关法规

#### 4.5 竞品对比分析

| 维度 | 本系统现状 | 竞品优势 | 差距 | 影响的问题点 |
|------|-----------|---------|------|------------|
| 维度1 | 现状描述 | 竞品优势 | 🔴/🟡/🟢 | 关联问题点 |
| ... | ... | ... | ... | ... |

#### 4.6 执行建议

**P0（立即执行）**
1. 具体行动项1 — 简要说明

**P1（迭代完善）**
1. 具体行动项1 — 简要说明

**P2（持续优化）**
1. 具体行动项1 — 简要说明

**P3（低优先级）**
1. 具体行动项1 — 简要说明

### Phase 5：输出优化

报告生成后，执行以下清理：
1. 确认所有章节标题格式一致
2. 确认标记符号使用正确（✅/🟢/🟡/🔴/⚪）
3. 确认表格格式对齐
4. 删除冗余的中间分析过程，保留最终结论
5. 确认文件输出路径有效

## 注意事项

1. **需求量为0的问题点**：标记为「无需求，无需评估」，设计合理
2. **未分类的问题点**（如"其他-未分类"）：标记为「无法评估，需人工复核」
3. **BUG类问题点**：标记为「不评估，BUG修复范畴」
4. **编辑器原生能力**（如复制粘贴）：标记为「不评估，编辑器原生能力范畴」
5. **独立功能模块**（如数据导出）：标记为「不评估，非引用功能范畴」
6. 如果设计文档缺失或不可读，在相关章节标记 ⏳待确认，并记录缺失的具体文档名称
7. 对于需求量大的问题点（>50条），即使设计合理，也应说明实现层面仍需关注
8. 报告应覆盖所有问题点，没有遗漏
