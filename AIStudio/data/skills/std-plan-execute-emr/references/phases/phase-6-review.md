# 阶段6: 代码审查（完整细节）

本文件包含阶段6的所有步骤。**不随 skill 加载**，进入阶段6时由 agent 按需读取。

> **在用户确认代码功能正确后执行。** 审查在最终代码上进行，结果不会被后续修改作废。

### 阶段6.1: 后端原生 SQL 规范检查（强制，纯前端跳过）

扫描变更文件，检查：
- **禁止循环内数据库查询（🔴 最高风险）** — for/while/forEach/for-each 循环体内不得包含数据库查询调用（包括 Mapper 调用、MyBatis selectList/selectOne、jdbcTemplate.query 等），必须改为批量查询后在内存中关联
- **禁止无 WHERE 的 SQL（🔴 最高风险）** — 所有原生 SQL 必须 WHERE 条件
- **List 入参不超过 1000（🔴 最高风险）** — IN 查询的 List 必须有大小约束

违规时强制终止，输出具体文件行号，修复后才能继续（参见 E-23）。

### 阶段6.2: 执行代码审查

调用 `code-review` 技能，提供需求号、修改范围、基于 fromBranch 的 diff。

### 阶段6.3: 审查结果处理

- **高风险**：必须修复，修复后重新审查
- **中风险**：建议修复，用户决定
- **低风险**：记录，用户决定

高风险问题存在时强制终止后续操作（参见 E-22）。

### 阶段6.4: 审查完成

生成审查报告保存到 `{codeBasePath}/{planBasePath}/{workItemId}/code-review-{workItemId}.md`，上传到 TFS **需求**附件（注意：必须上传到需求工作项，而非任务工作项）。

**上传保障（三级重试 + 验证）：**

对审查报告附件上传执行以下保障流程：

1. **第一级：主路径** — 使用 `mcp__mcp-tfs-query__upload_attachments` 上传，完成后调用 `list_attachments` 验证文件名存在
2. **第二级：重试 3 次** — 间隔 2s/4s/8s，每次验证
3. **第三级：降级 curl** — 使用 `curl` 直接调 TFS REST API 上传附件并关联工作项，降级后验证
4. **降级仍失败** → 输出失败报告（含本地文件路径），阻塞等待用户介入（参见 E-25~E-27）

向用户汇报开发完成（修改文件数、审查结果），代码尚未提交。

### 输出

- SQL 规范检查通过（后端）
- `code-review-{workItemId}.md` 审查报告已生成
- 审查报告已上传到 TFS 需求附件（非任务附件）
