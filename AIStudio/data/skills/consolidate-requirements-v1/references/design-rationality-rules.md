# 功能点设计合理性判定规则

**版本**: v2.0（2026-09-07 修订）  
**适用范围**: 病历片区产品线所有功能点的设计合理性评估  
**判定依据**: 历史需求数据信号（量化）+ 五维评分框架（评审）+ 一票否决制  
**v2.0 核心变更**: 数据基础从「新增需求快照」升级为「2025-01-01 起全量历史需求生命周期分析」，新增复发率与长尾指标，明确五维中哪些维度由数据驱动、哪些必须独立评审

---

## 〇、数据基础（v2.0）

### 0.1 数据窗口

| 项 | v1.0 | v2.0 |
|---|---|---|
| 需求范围 | 新增需求存储查询（近期窗口切片） | **CreatedDate >= 2025-01-01 的全量需求 + 软质**（历史生命周期模式 `--since=2025-01-01`） |
| 覆盖项目 | — | WiNEX-Inpatient-2 / WiNEX-Outpatient / WiNEX-Emergency（按产品名过滤） |
| 时间序列 | 无 | 按季度分桶（quarterly），可看趋势与长尾 |

**为什么升级**：只用新增需求判健康度存在两个系统性偏差——①存量盲区（历史上靠定制/打补丁消化的需求不再出现，健康度虚高）；②"零需求 ≠ 健康"（没人提需求可能是僵尸功能点或用户已放弃反馈，沉默的功能点会被误判为合理）。历史窗口 + 需求分析字段 + Spec 知识库三角验证可同时修复这两点。

### 0.2 量化指标定义（由 consolidate.js `--json` 输出）

| 指标 | 字段 | 定义 | 健康含义 |
|---|---|---|---|
| 需求密度 | `avgMonthly` | 该功能点工单总量 / 需求时间跨度（月） | 越高 → 诉求压力越大 |
| 软质比 | `softRatio` | 软质（软件质量）数 / 需求数 | 越高 → 实现质量越差（非设计问题，单独展示不混算） |
| 近期趋势 | `trend` | 近 90 天 vs 前 90 天工单量环比 | 升温 → 新痛点爆发 |
| **复发对数** | `recurrence` | 同功能点内，标题相似（Jaccard ≥ 0.45）且时间差 > 90 天的需求对数 | **> 0 → 设计未收敛的最硬信号：同类诉求反复出现说明改了但没改对** |
| 时间跨度 | `spanMonths` | 首末工单间隔月数 | ≥ 18 个月仍有新工单 → 长尾不收敛 |
| 季度分布 | `quarterly` | 按季度分桶的工单数 | 看需求是收敛还是持续 |

### 0.3 量化健康分 HPI（脚本自动计算，0-100）

```
HPI = 100
    − 软质比惩罚（softRatio × 40，上限 50）
    − 升温惩罚（90 天环比每 +20% 扣 4，上限 20）
    − 复发惩罚（每对复发扣 3，上限 15）        ← v2.0 新增
    − 长尾惩罚（跨度 ≥ 18 个月且历史模式启用，扣 5）← v2.0 新增
小样本降权：工单总数 < 3 时，全部惩罚按样本量比例缩放，避免单条工单直接判危险
```

> HPI 只反映「需求侧压力信号」，不等于最终健康等级。最终判定 = HPI（数据）× 五维评审（设计文档/代码/竞品），见第三章融合规则。

## 一、五维判定框架（v2.0：明确数据来源）

每个功能点从 5 个维度评估，每维 0-3 分。**v2.0 关键原则：量化数据与人工评审的来源边界——数据能支撑的维度用数据佐证，数据支撑不了的维度必须独立评审，禁止用需求数据硬算合规与竞品。**

| 维度 | 权重 | 满分 | 数据来源类型 | 数据信号（历史需求佐证） | 评审要点 |
|------|------|------|------------|------------------------|---------|
| ① 设计覆盖度 | 30% | 3分 | **数据 + 评审** | 该功能点历史需求中"设计未覆盖场景"类占比；零需求功能点必须回归评审防沉默偏差 | Spec/详细设计是否描述该功能点（规则、流程、交互、边界） |
| ② 实现一致性 | 20% | 3分 | **数据 + 评审** | 复发对数（>0 直接 ≤2 分）；跨模块同类需求模式重复度 | 各模块/菜单项实现是否统一，有无配置化架构支撑 |
| ③ 法规合规性 | 25% | 3分 | **仅独立评审** | （禁止从需求数据推断） | 《电子病历应用管理规范》《病历书写规范》等符合性 |
| ④ 竞品差距 | 15% | 3分 | **仅独立评审** | （禁止从需求数据推断） | 与主流竞品功能对比 |
| ⑤ 用户效率 | 10% | 3分 | **数据 + 评审** | 操作繁琐/效率类需求占比（标题含"操作繁琐/步骤多/每次都要"等） | 现有设计是否导致效率低下 |

### 各维度评分标准

#### 维度①：设计覆盖度

| 分数 | 标准 |
|------|------|
| 3分 | 设计文档有完整描述，含规则定义、流程、交互、边界场景 |
| 2分 | 设计文档有提及，但描述不够完整，缺少边界场景或异常处理 |
| 1分 | 设计文档仅部分提及，或仅覆盖部分模块/场景 |
| 0分 | 设计文档完全未提及 |

> v2.0 数据佐证：若该功能点历史需求中出现"应支持 X 场景但未覆盖"类诉求且 Spec 无对应描述，①不得高于 1 分。

#### 维度②：实现一致性

| 分数 | 标准 |
|------|------|
| 3分 | 统一架构方案支撑，配置化实现，各模块表现一致 |
| 2分 | 有架构方案，但配置化能力不完整，部分模块需定制 |
| 1分 | 各模块各自实现，无统一规范，表现不一致 |
| 0分 | 无统一架构，各模块实现方式完全不同 |

> v2.0 数据佐证：`recurrence > 0` 时本维度不得高于 2 分；`recurrence ≥ 3` 时不得高于 1 分。

#### 维度③：法规合规性

| 分数 | 标准 |
|------|------|
| 3分 | 完全满足法规要求，有合规设计文档 |
| 2分 | 基本满足法规要求，但缺少部分合规细节 |
| 1分 | 部分满足，存在合规风险点 |
| 0分 | 违反法规要求或完全未考虑合规性 |

> v2.0 约束：本维度**只依据法规文本比对**，需求数据不作为评分依据（用户没提需求不代表合规）。

#### 维度④：竞品差距

| 分数 | 标准 |
|------|------|
| 3分 | 与主流竞品持平或领先 |
| 2分 | 略有差距但可接受，不影响核心体验 |
| 1分 | 存在明显差距，竞品有更好的解决方案 |
| 0分 | 竞品有完整方案而本系统完全缺失 |

> v2.0 约束：本维度**只依据竞品调研**，需求数据不作为评分依据（国内没医院提需求不代表领先）。

#### 维度⑤：用户效率

| 分数 | 标准 |
|------|------|
| 3分 | 设计高效，操作路径短，用户无需额外操作 |
| 2分 | 操作合理，但偶有不便，可通过培训弥补 |
| 1分 | 操作繁琐，频繁出错，用户反馈较多 |
| 0分 | 设计缺陷导致用户无法高效完成任务 |

> v2.0 数据佐证：历史需求中操作效率类占比 > 30% 时本维度不得高于 1 分。

## 二、一票否决规则（v1-V6）

满足以下**任一条件**，直接判定为 **🔴 设计不合理**（无需算分）：

| 编号 | 否决条件 | 说明 |
|------|---------|------|
| V1 | **法规红牌** | 违反《电子病历应用管理规范》强制性条款 |
| V2 | **数据安全** | 存在数据泄露或不可追溯的设计漏洞 |
| V3 | **架构缺陷** | 导致无法扩展的架构设计错误 |
| V4 | **零覆盖** | 设计文档完全未提及，且该功能点有明确需求 |
| V5 | **严重不一致** | 同一功能在不同菜单项实现逻辑完全相反 |
| V6 | **复发性设计缺陷** | 同一功能点同类诉求跨季度反复出现 ≥ 2 次且均已在版本中"解决"后复发（`recurrence ≥ 2` 且有落地记录）← v2.0 新增 |

> V6 判定须人工复核：确认复发对的需求确实是同类设计问题（脚本按标题相似度初筛，存在误报可能），且历史版本中曾"解决"过同类诉求。

## 三、综合判定规则（v2.0：双轨融合）

### 3.1 判定流程

```
收到一个功能点
  │
  ├─ 判断：是 BUG/运维/第三方集成问题？
  │     ├─ 是 → ⚪ 非设计范畴，不评估（软质/BUG 单独统计，不混入设计健康度）
  │     └─ 否 → 继续
  │
  ├─ 判断：满足任一票否决条件（V1-V6）？
  │     ├─ 是 → 🔴 设计不合理，直接出方案
  │     └─ 否 → 继续
  │
  ├─ 数据轨：计算 HPI（0-100，脚本自动）
  │     ├─ HPI < 40（压力极高）→ 直接进入 🔴/🟡 候选，须人工评审确认
  │     ├─ 40 ≤ HPI < 70 → 进入正常五维评审
  │     └─ HPI ≥ 70 且零需求 → 仍须评审 ①④ 维度（防沉默偏差：僵尸功能点/用户放弃反馈）
  │
  └─ 评审轨：五维评分（每维 0-3 分，按第一章标准，①②⑤ 用数据信号约束下限）
        │
        ├─ 计算总分：___分（满分 15 分）
        │
        └─ 对照总分区间定级，并用 HPI 校准（见 3.2 融合矩阵）
```

### 3.2 HPI × 五维总分融合矩阵

| 五维总分 \ HPI | HPI < 40（压力极高） | 40-69（压力中等） | ≥ 70（压力低） |
|---|---|---|---|
| **13-15 分** | 🟡 部分合理（数据与评审矛盾，优先信数据，需解释原因） | ✅ 设计合理 | ✅ 设计合理 |
| **10-12 分** | 🟡 部分合理 | 🟢 基本合理 | 🟢 基本合理 |
| **6-9 分** | 🔴 不合理 | 🟡 部分合理 | 🟡 部分合理 |
| **0-5 分** | 🔴 不合理 | 🔴 不合理 | 🟡 部分合理（评审确认） |

### 3.3 处理策略

| 判定 | 处理策略 | 标记 |
|------|---------|------|
| 设计合理 | 暂不处理，保持监控 | ✅ |
| 设计基本合理 | 暂不处理，记录待完善细节 | 🟢 |
| 设计部分合理 | 暂不处理，纳入迭代计划 | 🟡 |
| 设计不合理 | **必须给出优化方案** | 🔴 |
| 非设计范畴 | BUG/运维/第三方集成问题，不评估（软质单列统计） | ⚪ |

## 四、判定示例

### 示例1：引用操作-插入功能（低压力高评审）

| 维度 | 评分 | 理由 |
|------|------|------|
| ① 设计覆盖度 | 3分 | 17项引用功能详细设计中有O系列规则（8条），覆盖完整 |
| ② 实现一致性 | 2分 | 有统一架构，但部分菜单项不支持批量引用 |
| ③ 法规合规性 | 3分 | 符合数据来源可追溯要求 |
| ④ 竞品差距 | 2分 | 竞品支持一键批量引用，本系统需分步操作 |
| ⑤ 用户效率 | 2分 | 操作尚可，但分步操作较多 |
| **总分** | **12分** | HPI 85 → **🟢 设计基本合理，暂不处理**（融合矩阵：10-12 分 × HPI≥70） |

### 示例2：性能-加载优化（高压力高缺陷）

| 维度 | 评分 | 理由 |
|------|------|------|
| ① 设计覆盖度 | 0分 | 设计文档未提及分层加载、预加载机制 |
| ② 实现一致性 | 1分 | 各菜单项各自实现，无统一加载策略 |
| ③ 法规合规性 | 3分 | 无直接法规冲突 |
| ④ 竞品差距 | 1分 | 竞品有分层加载+缓存方案，本系统差距明显 |
| ⑤ 用户效率 | 1分 | 加载慢导致用户频繁等待，历史窗口内效率类需求占比 > 40% |
| **总分** | **6分** | HPI 35 → **🔴 设计不合理**（融合矩阵：6-9 分 × HPI<40） |

### 示例3：会诊状态同步（v2.0 典型：复发触发）

- 历史数据：2024-Q1、2024-Q3、2025-Q2 三轮"会诊状态显示不一致"类需求，前两轮均已标记解决
- `recurrence = 3` → ② 实现一致性封顶 1 分；若确认两轮均落地后复发 → **V6 一票否决 → 🔴**
- v1.0 规则下该功能点若当前窗口无新增需求会被误判 ✅，v2.0 通过历史窗口 + 复发检测捕获

### 示例4：BUG-异常报错

| 判定 | 理由 |
|------|------|
| **⚪ 非设计范畴** | 程序错误/异常报错属于 BUG 修复（软质），单列实现质量统计，不评估设计健康度 |

## 五、补充说明

### 5.1 多维度交叉验证

当某个功能点同时涉及多个维度时，取各维度评分加权后综合判定，避免单一维度决定结果。

### 5.2 评分争议处理

- 评分两级（如 0 分 vs 3 分）争议时，以「设计文档是否存在」为第一证据
- 评分一级差距（如 2 分 vs 3 分）争议时，以「历史需求信号（HPI/复发）」为辅助判断
- 数据与评审矛盾时（HPI 低但五维总分高）：优先信数据，复盘评审是否遗漏了历史上下文

### 5.3 判定结果有效期

- 设计合理性判定**随设计文档更新而失效**
- 当设计文档新增/修订后，需重新评估受影响的功能点
- v2.0 增补：HPI 随历史窗口滚动（每月重跑 `--since`），复发对数只增不减，判定复核周期建议每季度一次

### 5.4 规则适用范围

本规则适用于：
- ✅ 功能类需求点的设计合理性评估
- ✅ 交互类需求点的设计合理性评估
- ✅ 数据类需求点的设计合理性评估
- ✅ 配置类需求点的设计合理性评估
- ❌ BUG 类问题（软质单列实现质量统计，不评估）
- ❌ 运维类问题（不评估）
- ❌ 第三方集成问题（不评估）

### 5.5 v2.0 已知局限与后续路线

- **语义映射覆盖**：历史全量需求（万级）中未在语义映射表（semantic-fp-map.json）内的条目走关键词/模块级匹配，功能点级归属准确率低于模块级——功能点级健康度建议先抽检映射准确率（≥80% 再采信），否则先看模块级粒度
- **使用规模归一化未完成**：HPI 未按功能点使用规模归一（缺每功能点活跃使用数据），高频功能点天然压力分高；横向比较时优先同模块内比较
- **LLM 批量打标（规划中）**：结合 `Winning.Demand.Analysis` 字段做缺陷类型标注（设计缺失/边界缺失/多模块不一致/超范围定制），可进一步提升 ①②⑤ 维度的数据化程度
