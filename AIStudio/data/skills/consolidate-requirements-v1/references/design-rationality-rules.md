# 功能点设计合理性判定规则

**版本**: v1.1
**适用范围**: 病历片区产品线所有功能点的设计合理性评估
**判定依据**: 五维评分框架 + 一票否决制
**来源**: 微信文件 2026-08；v1.1（2026-09-10）引入 Spec 正文证据作为第一证据源

> **v1.1 变更**：维度①（设计覆盖度）与维度③（法规合规性）的评分**必须引用 Spec 三件套正文的具体章节/规则编号**（纳入范围 1.2.1、排除范围 1.2.2、约束 BC-*、验收标准 AC-*、业务规则 BR-*），正文索引见 `references/spec-evidence.json`（`build-spec-index.js` 产出）。引用不到正文证据时该维度最高 2 分。

---

## 一、五维判定框架

每个功能点从以下5个维度交叉评估，每个维度分四个等级（0-3分）：

| 维度 | 权重 | 满分 | 判定要点 |
|------|------|------|----------|
| ① 设计覆盖度 | 30% | 3分 | 设计文档是否明确描述了该功能点 |
| ② 实现一致性 | 20% | 3分 | 各模块/菜单项实现是否统一，有无配置化支撑 |
| ③ 法规合规性 | 25% | 3分 | 是否符合《电子病历应用管理规范》《病历书写规范》等 |
| ④ 竞品差距 | 15% | 3分 | 与主流竞品相比是否有明显功能缺失 |
| ⑤ 用户效率 | 10% | 3分 | 现有设计是否导致操作效率低下或频繁出错 |

---

## 二、各维度评分标准

### 维度①：设计覆盖度

| 分数 | 标准 | Spec 正文证据要求 |
|------|------|------|
| 3分 | 设计文档有完整描述，含规则定义、流程、交互、边界场景 | 须引用正文章节（如 1.2.1 纳入范围、BR 规则、AC 验收）与命中条数 |
| 2分 | 设计文档有提及，但描述不够完整，缺少边界场景或异常处理 | 引用正文章节，指出缺失点；或引用不到正文（封顶 2 分） |
| 1分 | 设计文档仅部分提及，或仅覆盖部分模块/场景 | 引用正文中仅有的相关条目 |
| 0分 | 设计文档完全未提及 | 索引 `hasSpec=false` 或正文无相关条目 → 同时核查 V4 零覆盖 |

### 维度②：实现一致性

| 分数 | 标准 |
|------|------|
| 3分 | 统一架构方案支撑，配置化实现，各模块表现一致 |
| 2分 | 有架构方案，但配置化能力不完整，部分模块需定制 |
| 1分 | 各模块各自实现，无统一规范，表现不一致 |
| 0分 | 无统一架构，各模块实现方式完全不同 |

### 维度③：法规合规性

| 分数 | 标准 | Spec 正文证据要求 |
|------|------|------|
| 3分 | 完全满足法规要求，有合规设计文档 | 须引用正文合规条目（如 PM-Spec 约束 BC-*、医疗行业特殊要求） |
| 2分 | 基本满足法规要求，但缺少部分合规细节 | 引用正文中已有的合规条目并指出缺口；或引用不到正文（封顶 2 分） |
| 1分 | 部分满足，存在合规风险点 | 引用正文 + 指出风险条款 |
| 0分 | 违反法规要求或完全未考虑合规性 | 正文无合规条目且法规有明确要求 |

### 维度④：竞品差距

| 分数 | 标准 |
|------|------|
| 3分 | 与主流竞品持平或领先 |
| 2分 | 略有差距但可接受，不影响核心体验 |
| 1分 | 存在明显差距，竞品有更好的解决方案 |
| 0分 | 竞品有完整方案而本系统完全缺失 |

### 维度⑤：用户效率

| 分数 | 标准 |
|------|------|
| 3分 | 设计高效，操作路径短，用户无需额外操作 |
| 2分 | 操作合理，但偶有不便，可通过培训弥补 |
| 1分 | 操作繁琐，频繁出错，用户反馈较多 |
| 0分 | 设计缺陷导致用户无法高效完成任务 |

## 三、综合判定规则

| 总分 | 对应判定 | 处理策略 | 标记 |
|------|---------|----------|------|
| 13-15分 | **设计合理** | 暂不处理，保持监控 | ✅ |
| 10-12分 | **设计基本合理** | 暂不处理，记录待完善细节 | 🟢 |
| 6-9分 | **设计部分合理** | 暂不处理，纳入迭代计划 | 🟡 |
| 0-5分 | **设计不合理** | **必须给出优化方案** | 🔴 |
| 不适用 | **非设计范畴** | BUG/运维/第三方集成问题，不评估 | ⚪ |

## 四、一票否决规则

满足以下**任一条件**，直接判定为 **🔴 设计不合理**（无需算分）：

| 编号 | 否决条件 | 说明 |
|------|---------|------|
| V1 | **法规红牌** | 违反《电子病历应用管理规范》强制性条款 |
| V2 | **数据安全** | 存在数据泄露或不可追溯的设计漏洞 |
| V3 | **架构缺陷** | 导致无法扩展的架构设计错误 |
| V4 | **零覆盖** | 设计文档完全未提及，且该功能点有明确需求。**核查程序（v1.1）**：① 正文索引 `hasSpec=false` → 查 Spec 目录确认三件套确实缺失；② `hasSpec=true` → 逐查纳入范围/业务规则/验收标准，确认无一覆盖该需求主题。两步确认后才判 V4 |
| V5 | **严重不一致** | 同一功能在不同菜单项实现逻辑完全相反 |

## 五、判定流程图

```
收到一个功能点
  │
  ├─ 判断：是BUG/运维/第三方集成问题？
  │     ├─ 是 → ⚪ 非设计范畴，不评估
  │     └─ 否 → 继续
  │
  ├─ 判断：满足任一票否决条件（V1-V5）？
  │     ├─ 是 → 🔴 设计不合理，直接出方案
  │     └─ 否 → 继续
  │
  └─ 正常评估流程：
       │
       ├─ 五维评分（每维0-3分）
       │   ① 设计覆盖度：___分
       │   ② 实现一致性：___分
       │   ③ 法规合规性：___分
       │   ④ 竞品差距：___分
       │   ⑤ 用户效率：___分
       │
       ├─ 计算总分：___分（满分15分）
       │
       └─ 对照总分区间定级：
             13-15分 → ✅ 设计合理（暂不处理）
             10-12分 → 🟢 基本合理（暂不处理）
              6-9分  → 🟡 部分合理（暂不处理）
              0-5分  → 🔴 不合理（给出优化方案）
```

## 六、判定示例

### 示例1：引用操作-插入功能

| 维度 | 评分 | 理由 |
|------|------|------|
| ① 设计覆盖度 | 3分 | 17项引用功能详细设计中有O系列规则（8条），覆盖完整 |
| ② 实现一致性 | 2分 | 有统一架构，但部分菜单项不支持批量引用 |

## 七、补充说明

### 7.1 多维度交叉验证

当某个功能点同时涉及多个维度时，取各维度评分加权后综合判定，避免单一维度决定结果。

### 7.2 评分争议处理

- 评分两级（如0分 vs 3分）争议时，以「设计文档是否存在」为第一证据
- 评分一级差距（如2分 vs 3分）争议时，以「用户反馈量级」为辅助判断

### 7.3 判定结果有效期

- 设计合理性判定**随设计文档更新而失效**
- 当设计文档新增/修订后，需重新评估受影响的功能点

### 7.4 规则适用范围

本规则适用于：
- ✅ 功能类需求点的设计合理性评估
- ✅ 交互类需求点的设计合理性评估
- ✅ 数据类需求点的设计合理性评估
- ✅ 配置类需求点的设计合理性评估
- ❌ BUG类问题（不评估）
- ❌ 运维类问题（不评估）
- ❌ 第三方集成问题（不评估）
