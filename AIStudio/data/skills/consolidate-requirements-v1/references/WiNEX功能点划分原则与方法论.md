## 一、背景与目标

### 1.1 现状问题

WiNEX 系统每年接受医院现场大量需求，这些需求呈现以下特征：

- **点状涌入**：需求来自不同科室、不同角色，缺乏系统性规划
- **被动响应**：开发和产品按需求逐点修复，缺少顶层设计
- **难以评估**：无法识别哪些功能设计不完整、哪些功能需求过载需要重构
- **缺乏度量**：没有统一的"功能锚点"来统计需求分布和趋势

### 1.2 目标

通过功能点划分，实现：

1. **需求锚定**：每个需求必须绑定到一个功能点，建立需求-功能点的映射关系
2. **健康度可视化**：统计每个功能点的需求数量、变更频率、需求类型分布，识别异常
3. **设计完整性评估**：通过功能点的需求密度，发现设计不完整的功能点（需求稀疏）或过度设计的功能点（需求过载）
4. **重构优先级排序**：基于健康度数据，量化确定重构优先级
5. **顶层设计落地**：从"功能点清单"出发，规划系统的能力演进路线

### 1.3 适用范围

- **适用对象**：产品经理、架构师、需求分析师
- **适用系统**：WiNEX 全业务线
- **适用阶段**：需求规划、架构评审、重构决策

## 二、核心概念定义

### 2.1 什么是功能点

**功能点（Feature Point, FP）** 是系统中一个**具有完整业务语义的最小独立功能单元**，它：

- 代表用户在特定业务场景下完成的**一个有意义的操作**
- 涉及**上下文的交互**（多实体协作、多角色流转、状态变更、跨系统调用中的至少一种）
- 是需求绑定的**最小锚点**——每个需求至少归属于一个功能点

**一句话判定测试**：

> 能否用一句话说清楚"谁，在什么场景下，做了什么，达成了什么业务结果"？
> - 能 → 可能是功能点
> - 不能 → 需要再审视

### 2.2 什么不是功能点

| 不是功能点 | 原因 | 如何处理 |
|---|---|---|
| 对象的增、删、改、查、列表、导出 | 基线能力，不构成业务功能 | 归属于其所在的业务场景，作为功能点的"底层支撑" |
| 页面/表单本身 | 载体，不是功能 | 页面是功能点的容器，一个页面可承载多个功能点 |
| 字段级校验、格式转换 | 技术细节 | 归属于承载它的功能点 |
| 按钮/操作入口 | UI 元素 | 入口背后的业务逻辑才是功能点 |
| 权限配置、角色管理 | 平台基线能力 | 归入"平台支撑"类，不计入业务功能点 |
| 接口本身 | 技术通道 | 接口承载的业务操作才是功能点 |

### 2.3 关键区分：基线能力 vs 功能点

| 基线能力（❌ 不是功能点） | 功能点（✅ 是功能点） |
|---|---|
| "新增一条医嘱" | "开立长期医嘱并自动分解为执行任务" |
| "查询患者列表" | "患者入院登记并触发床位分配和押金缴纳" |
| "修改药品信息" | "药品目录同步并触发价格联动调整" |
| "删除检验报告" | "检验报告审核发布并推送给临床医生" |
| "导出费用清单" | "费用预审并触发医保规则校验和自付比例计算" |

**判断核心**：是否涉及**上下文交互**——多实体协作、状态流转、跨系统调用、业务规则推导中的至少一种。

## 三、三层漏斗 + C-DARHS 判定法

### 3.1 第一层：基线过滤

**目标**：排除不构成业务功能的基线能力。

**排除清单（一票否决）**：

| 基线能力 | 示例 | 说明 |
|---|---|---|
| 单对象增删改查 | 新增患者、删除医嘱、修改药品信息、查询检验报告列表 | 对象管理的基础操作 |
| 列表/导出/打印 | 导出费用清单、打印腕带、打印检验报告 | 数据的呈现形式，非业务逻辑 |
| 字典/配置管理 | 维护药品字典、配置角色权限、设置科室信息 | 系统基础配置 |
| 纯技术接口 | REST API、HL7 消息通道、数据库同步 | 技术通道，需看承载的业务 |

**通过第一层后的状态**：剩下的条目进入第二层判定。

---

### 3.2 第二层：C-DARHS 六要素判定

对通过第一层的每个条目，逐项评估以下 6 个要素：

| 要素 | 代码 | 判定问题 | 满足标准 |
|---|---|---|---|
| **Context** | C | 是否处于端到端业务流程中？上下游是什么？ | 能明确说出触发条件和后续环节 |
| **Decision** | D | 是否包含业务规则判断或人工决策分支？ | 有规则推导、人工审核、异常处理中至少一种 |
| **Action** | A | 是否引起实体状态变更或跨系统消息？ | 创建/更新/删除数据、发送通知、触发下游 |
| **Role** | R | 是否由特定角色执行？不同角色看到的内容不同？ | 有明确的角色绑定和权限控制 |
| **Health-Safety** | H | 是否直接影响患者安全或诊疗质量？ | 错误可能导致患者伤害、用药错误、诊断延误 |
| **SLA** | S | 是否有明确的性能/可用性/一致性要求？ | 响应时间、并发数、可用性有量化指标 |

**评估方式**：每个要素标记 ✅ 或 ❌，并写一句话说明。

---

### 3.3 第三层：L1-L4 分级

根据 C-DARHS 要素满足度，划分为 4 个等级：

| 等级 | 判定规则 | 处理方式 |
|---|---|---|
| **L1 核心功能** | 满足 ≥5 要素，**必须包含 C+D+A+H** | ✅ 纳入功能点清单<br>✅ 必须写完整 Spec<br>✅ 参与需求绑定和健康度分析 |
| **L2 重要功能** | 满足 ≥4 要素，**必须包含 C+A** | ✅ 纳入功能点清单<br>✅ Spec 可简化（仅需主流程+异常流程）<br>✅ 参与需求绑定和健康度分析 |
| **L3 基础功能** | 满足 ≤3 要素 | ❌ 不单独作为功能点<br>✅ 记录在"基础能力附录"<br>❌ 不参与健康度分析 |
| **L4 技术/字典功能** | 满足 ≤2 要素且不含 H | ❌ 不计入功能点<br>❌ 仅作为技术实现细节 |

**关键规则**：**只有 L1 和 L2 才算"功能点"**，才需要绑定需求、计算健康度。

---

### 3.4 第四层：粒度校准

对判定为 L1/L2 的功能点，用两个测试调整粒度：

**测试 1：拆分测试**
- 问：能否拆出 2 个以上同样满足 L1/L2 的子步骤？
- 能拆 → 应该拆分（当前粒度过粗）
- 不能拆 → 粒度合适

**测试 2：合并测试**
- 问：两个功能点是否服务于同一个业务目标，且触发条件、角色、数据完全相同？
- 是 → 应该合并（当前粒度过细）
- 否 → 粒度合适

**一句话测试（终极检验）**：

> 能否用一句话说清楚"谁，在什么场景下，做了什么，达成了什么业务结果"？
> - 能 → 粒度合适
> - 需要说好几句话才能说清楚 → 可能粒度过粗
> - 说出来觉得很 trivial → 可能粒度过细

---

### 3.5 判定流程图

```
开始
  ↓
[条目：来自系统功能清单]
  ↓
[第一层：基线过滤]
  ├─ 是纯 CRUD/导出/配置？→ ❌ 排除
  └─ 否 ↓
       ↓
[第二层：C-DARHS 六要素评估]
  ├─ 逐项标记 ✅/❌
  └─ 统计满足数 ↓
       ↓
[第三层：L1-L4 分级]
  ├─ L1（≥5要素，含C+D+A+H）→ ✅ 纳入功能点
  ├─ L2（≥4要素，含C+A）→ ✅ 纳入功能点
  ├─ L3（≤3要素）→ ❌ 归入基础能力附录
  └─ L4（≤2要素，不含H）→ ❌ 排除
       ↓
[第四层：粒度校准]
  ├─ 拆分测试 → 过粗则拆分
  ├─ 合并测试 → 过细则合并
  └─ 一句话测试 → 最终确认
       ↓
输出：功能点清单（含ID、名称、等级、描述）
```

## 四、层次结构与分类维度

### 4.1 四层层次结构

```
业务域（Domain）
  └─ 功能模块（Module）
       └─ 功能点（Feature Point, FP）
            └─ 子功能点（Sub-FP，可选）
```

**各层定义**：

| 层次 | 定义 | 示例 | 数量级 |
|---|---|---|---|
| **业务域** | 系统的顶层业务板块，通常对应一个独立的业务部门或业务线 | 住院管理、门急诊管理、药品管理、检验检查 | 10~20 个 |
| **功能模块** | 业务域内按业务目标或角色划分的逻辑集合 | 住院域下的：入院管理、医嘱管理、床位管理、出院管理 | 每域 5~15 个 |
| **功能点** | 具有完整业务语义的最小独立功能单元（L1/L2） | 医嘱管理下的：长期医嘱开立、临时医嘱执行、医嘱审核 | 每模块 5~30 个 |
| **子功能点** | 功能点内可独立识别的、有独立触发条件的子操作（可选） | 长期医嘱开立下的：医嘱模板调用、医嘱复制、医嘱组套 | 每功能点 0~5 个 |

**关键规则**：

- **需求绑定层级**：需求可以绑定到功能点或子功能点，但**不能**绑定到业务域或功能模块（太粗）
- **健康度统计层级**：健康度按功能点统计，向上聚合到功能模块和业务域
- **子功能点是否独立**：只有当子功能点满足 L2 及以上标准，且用户感知为"独立操作"时，才单独列出；否则作为功能点的内部步骤

---

### 4.2 业务域划分指南

**划分原则**：

1. **业务独立性**：每个业务域应有明确的业务目标和边界，域间耦合尽量低
2. **角色聚合**：同一业务域通常服务于同一类角色群体（如住院域服务住院医生/护士，门急诊域服务门诊医生/护士）
3. **数据内聚**：同一业务域的核心数据实体应尽量内聚（如住院域的核心实体是"住院记录"，药品域的核心实体是"药品"）
4. **流程完整**：一个业务域应能独立完成一个端到端的业务闭环（如入院→在院→出院）

**划分检查清单**：

- [ ] 能否用一句话说清楚这个域"做什么"？
- [ ] 这个域的数据实体是否与其他域有大量交叉？（如果有，可能需要重新划分）
- [ ] 这个域是否有独立的业务负责人或业务部门？
- [ ] 这个域的功能是否能独立演进，不影响其他域？

---

### 4.3 功能模块划分指南

**划分原则**：

1. **业务目标导向**：每个功能模块应服务于一个明确的业务目标（如"入院管理"的目标是"完成患者的入院登记和床位分配"）
2. **角色聚焦**：同一功能模块通常由同一角色（或角色组）使用
3. **数据共享**：同一功能模块内的功能点通常操作相同或强关联的数据实体

**划分检查清单**：

- [ ] 能否用一句话说清楚这个模块"达成什么业务目标"？
- [ ] 这个模块内的功能点是否服务于同一个业务场景？
- [ ] 这个模块是否由同一类角色使用？（如果有多个角色，是否可以通过权限控制区分？）

---

### 4.4 分类维度（标签体系）

除了层次结构，每个功能点还可以打上多个分类标签，用于多维度分析：

| 维度 | 标签示例 | 用途 |
|---|---|---|
| **交互模式** | 单实体操作 / 多实体协作 / 跨角色流转 / 跨系统交互 | 识别复杂度、发现设计不完整 |
| **业务性质** | 临床业务 / 管理业务 / 财务业务 / 平台支撑 | 按业务性质统计需求分布 |
| **安全等级** | 高（直接影响患者安全）/ 中 / 低 | 识别高风险功能点 |
| **使用频率** | 高频（每日千次以上）/ 中频 / 低频 | 识别性能瓶颈 |
| **成熟度** | 稳定 / 频繁变更 / 新上线 | 识别需要重构的功能点 |

## 五、健康度分析模型

### 5.1 健康度指标定义

每个功能点通过以下指标评估其"健康度"：

| 指标 | 定义 | 计算方式 | 健康阈值 |
|---|---|---|---|
| **需求密度** | 功能点关联的需求数量 | 统计绑定的需求总数 | 2~10 个/功能点为正常 |
| **需求增速** | 单位时间内新增需求数 | 近 6 个月需求数 / 6 | < 2 个/月为正常 |
| **需求类型分布** | 需求中"新增/修改/缺陷"的比例 | 统计各类型占比 | 修改类 < 50% 为正常 |
| **变更频率** | 功能点被修改的次数 | 近 12 个月的代码变更次数 | < 12 次/年为正常 |
| **需求来源集中度** | 需求来源的科室/角色数量 | 统计不同来源数 | ≥ 3 个来源为正常 |

### 5.2 健康度等级

根据指标综合评估，将功能点分为 4 个健康等级：

| 健康等级 | 判定规则 | 含义 | 建议动作 |
|---|---|---|---|
| 🟢 **健康** | 所有指标在阈值内 | 功能设计完整、稳定 | 保持现状，持续监控 |
| 🟡 **关注** | 1~2 个指标超出阈值 | 可能存在设计不完整或轻微过载 | 分析原因，纳入下季度优化计划 |
| 🟠 **预警** | 3~4 个指标超出阈值 | 设计不完整或需求过载 | 优先纳入重构计划，安排专项优化 |
| 🔴 **危险** | 所有指标超出阈值，或出现极端值 | 严重设计缺陷或需求失控 | 立即启动重构，暂停新需求接入 |

### 5.3 异常模式识别

通过健康度指标，识别以下异常模式：

#### 模式 1：设计不完整（需求稀疏）

**特征**：
- 需求密度 < 2 个/功能点
- 需求来源集中度 = 1（仅来自单一科室/角色）
- 功能点属于 L1 核心功能

**可能原因**：
- 功能设计过于简化，未覆盖完整的业务场景
- 功能仅服务于特定科室的个性化需求，缺乏通用性
- 功能处于业务边缘，尚未被充分使用

**建议动作**：
- 调研该功能是否覆盖完整的业务流程
- 评估是否需要扩展功能以覆盖更多场景
- 如果确实是边缘功能，考虑降级为 L2 或合并到其他功能点

#### 模式 2：需求过载（需要重构）

**特征**：
- 需求密度 > 10 个/功能点
- 需求增速 > 2 个/月
- 需求类型分布中"修改类" > 50%

**可能原因**：
- 功能承担了过多的业务职责（违反单一职责原则）
- 功能设计不灵活，无法通过配置满足新需求
- 功能代码质量差，每次修改都引入新问题

**建议动作**：
- 分析功能点的职责是否过多，考虑拆分为多个子功能点
- 评估是否可以通过引入配置化、规则引擎等方式提高灵活性
- 启动代码质量评审，识别技术债务
- 暂停新需求接入，优先进行重构

#### 模式 3：频繁变更（稳定性差）

**特征**：
- 变更频率 > 12 次/年
- 需求类型分布中"缺陷类" > 30%

**可能原因**：
- 功能代码质量差，Bug 频发
- 功能设计不合理，业务逻辑经常变化
- 功能依赖的外部系统不稳定

**建议动作**：
- 统计 Bug 类型，识别是否集中在特定模块
- 评估是否需要重新设计或重构
- 加强代码评审和测试覆盖

#### 模式 4：来源单一（通用性不足）

**特征**：
- 需求来源集中度 = 1
- 需求密度 > 5 个/功能点

**可能原因**：
- 功能仅服务于特定科室的个性化需求
- 功能设计未考虑多科室/多角色的通用性

**建议动作**：
- 调研其他科室/角色是否有类似需求
- 评估是否需要改造为通用功能
- 如果确实是个性化需求，考虑通过配置化满足

## 七、产品经理操作指南

### 7.1 阶段一：功能点划分（3-6 个月）

**目标**：完成全系统功能点清单的梳理，输出 Excel 功能点清单表。

**步骤**：

1. **收集现有功能清单**
   - 从需求管理系统、产品文档、开发文档中收集现有功能列表
   - 不要求格式统一，先穷举所有功能

2. **第一层：基线过滤**
   - 逐项检查，排除纯 CRUD、导出、配置类条目
   - 输出：初筛后的功能条目清单

3. **第二层：C-DARHS 评估**
   - 对每个条目，逐项评估 6 个要素，标记 ✅/❌
   - 输出：C-DARHS 评估表

4. **第三层：L1-L4 分级**
   - 根据评估结果，划分 L1-L4 等级
   - 输出：分级后的功能清单

5. **第四层：粒度校准**
   - 对 L1/L2 条目，进行拆分/合并/一句话测试
   - 输出：最终功能点清单

6. **层次结构归类**
   - 将功能点归入业务域和功能模块
   - 输出：层次化的功能点树

7. **打标签**
   - 为每个功能点打上分类标签（交互模式、业务性质、安全等级等）
   - 输出：完整的功能点清单表

**产出物**：
- 功能点清单表（Excel）
- 基础能力附录表（Excel）

**验收标准**：
- 功能点数量在 500~2000 之间
- L1:L2 比例约为 3:7 或 4:6
- 每个功能点都能通过"一句话测试"
- 业务域和功能模块划分清晰，无重叠

---

### 7.2 阶段二：需求绑定（持续进行）

**目标**：将历史需求和新增需求绑定到功能点，建立需求-功能点映射关系。

**步骤**：

1. **历史需求绑定**
   - 从需求管理系统中导出历史需求
   - 逐条绑定到功能点（可借助需求标题、描述、来源等信息）
   - 如果需求无法绑定到现有功能点，可能需要新增功能点或调整划分

2. **新增需求绑定流程**
   - 需求提出时，产品经理必须选择绑定的功能点
   - 如果需求涉及新的功能点，先完成功能点划分再绑定
   - 需求管理系统中增加"绑定功能点"字段

3. **定期校验**
   - 每月检查需求绑定率（已绑定需求数 / 总需求数）
   - 识别未绑定的需求，分析原因

**产出物**：
- 需求绑定表（Excel）

**验收标准**：
- 历史需求绑定率 > 90%
- 新增需求绑定率 = 100%

---

### 7.3 阶段三：健康度分析与治理（每季度）

**目标**：基于需求绑定数据，分析功能点健康度，识别需要干预的功能点。

**步骤**：

1. **健康度计算**
   - 按公式计算每个功能点的健康度指标
   - 自动判定健康等级

2. **异常识别**
   - 识别"预警"和"危险"级别的功能点
   - 分析异常模式（设计不完整/需求过载/频繁变更/来源单一）

3. **治理决策**
   - 对"危险"级别功能点，立即启动重构
   - 对"预警"级别功能点，纳入下季度优化计划
   - 对"关注"级别功能点，持续监控

4. **效果评估**
   - 重构后重新计算健康度，评估治理效果
   - 对比重构前后的需求密度、变更频率等指标

**产出物**：
- 健康度统计表（Excel）
- 健康度看板（可选，建议用 BI 工具）
- 治理决策报告

**验收标准**：
- "危险"级别功能点数量逐季减少
- 全系统平均健康等级提升

---

### 7.4 团队培训建议

**培训对象**：产品经理、需求分析师、架构师

**培训内容**：

1. **概念培训（2 小时）**
   - 什么是功能点、什么不是功能点
   - 三层漏斗 + C-DARHS 判定法
   - L1-L4 分级标准
   - 粒度校准方法

2. **实战演练（4 小时）**
   - 选取一个常见功能（如"门诊挂号"或"检验报告查询"）
   - 全员共同完成 C-DARHS 评估和分级
   - 讨论争议点，统一理解

3. **工具培训（2 小时）**
   - Excel 模板使用说明
   - 需求绑定流程
   - 健康度计算方法

4. **评审会（每季度 1 次，2 小时）**
   - 回顾上季度健康度数据
   - 讨论治理决策
   - 分享最佳实践

#### 综合案例总结

**4 个场景统计**：

| 场景 | 原始条目数 | 通过基线过滤 | L1 功能点数 | L2 功能点数 | L1 占比 |
|---|---|---|---|---|---|
| 入院管理 | 10 | 3 | 0 | 3 | 0% |
| 药品管理 | 10 | 7 | 3 | 4 | 43% |
| 检验检查 | 10 | 5 | 1 | 4 | 20% |
| 费用结算 | 10 | 5 | 0 | 5 | 0% |
| **合计** | **40** | **20** | **4** | **16** | **20%** |

**关键发现**：

1. **基线过滤率高**：40 个原始条目中 50% 被排除为基线能力（CRUD、打印、导出）
2. **L1 功能点集中在安全相关**：药品效期预警、配伍禁忌校验、危急值 alert 等涉及患者安全的功能为 L1
3. **L2 功能点占比最高**：大多数涉及跨实体/跨系统交互的功能为 L2
4. **不同业务域特征不同**：
   - 药品管理：安全要求高，L1 占比最高（43%）
   - 费用结算：安全要求低，L1 为 0
   - 检验检查：危急值为 L1，其他为 L2

**产品经理可以从中学习到**：

1. **如何区分基线能力和功能点**：CRUD、打印、导出是基线，有上下文交互的才是功能点
2. **如何判断 L1 vs L2**：H 要素是关键，涉及患者安全的是 L1
3. **如何校准粒度**：一句话能说清楚，且能拆分出同样满足 L1/L2 的子步骤
4. **如何识别业务域特征**：不同域的安全要求不同，L1 比例不同

#### 二、BPMN 上下文（触发→流程→结束）

**触发事件**：
- 医生选择患者后点击【新建医嘱】
- 定时触发：每日凌晨自动生成常规医嘱（如长期护理医嘱）

**流程步骤**：
```
[开始] 医生选择患者
  ↓
[活动] 录入医嘱内容（药品/检验/检查/护理）
  ↓
[网关] 系统校验
  ├─ 剂量校验（按年龄/体重/诊断）
  ├─ 配伍禁忌校验（与当前未停止医嘱交叉检查）
  ├─ 药品库存校验
  └─ 医保规则校验
  ↓
[网关] 校验结果
  ├─ 全部通过 → 医生确认提交
  ├─ 警告（非阻断）→ 医生二次确认后提交
  └─ 拒绝（阻断）→ 返回修改
  ↓
[活动] 医嘱提交写入
  ↓
[活动] 库存预占（药品医嘱）
  ↓
[活动] 推送下游系统
  ├─ → 药房系统（配药任务）
  ├─ → 护理系统（执行计划）
  └─ → 医保系统（费用预审）
  ↓
[结束] 医嘱状态变更为"已提交，待执行"
```

**结束事件**：
- 成功：医嘱状态="已提交"，等待护士核对执行
- 失败：校验不通过，医嘱未创建，提示错误原因
- 超时：下游系统响应超时，提示"系统繁忙，请稍后重试"

## 九、附录：国际标准参考

### 9.1 ISO/IEC 25010（软件质量模型）

**核心观点**：功能适合性（functional suitability）包括功能完整性、功能正确性、功能适当性。

**映射**：
- 功能完整性：功能是否覆盖了用户预期业务
- 功能正确性：逻辑是否符合临床指南
- 功能适当性：角色使用是否自然

### 9.2 BPMN 2.0（业务流程建模）

**核心观点**：流程由活动、事件、网关、数据对象组成。

**映射**：功能不应是孤立活动，而应包含触发条件、数据流、决策分支、后续事件。

### 9.3 IFPUG FPA（功能点分析）

**核心观点**：功能分为外部输入、外部输出、外部查询、内部逻辑文件、外部接口文件。

**映射**：每个功能必须指明它属于哪类（CRUD 的"查"属于外部查询，不算核心；跨系统接口属于外部接口文件，应算）。

### 9.4 HL7 FHIR（医疗互操作性标准）

**核心观点**：资源是核心，操作附属于资源，更关注工作流。

**映射**：HIT 功能应围绕"一个业务角色对一组 FHIR 资源进行有上下文的工作流操作"来定义。

### 9.5 IHE（医疗集成规范）

**核心观点**：通过集成配置文件描述跨系统的交互流程。

**映射**：跨系统功能应定义 actor（系统角色）、transaction（事务）、content（内容）。

### 9.6 HIT 行业 6 维度

| 维度 | 含义 | 对功能定义的影响 |
|---|---|---|
| 患者安全 | 功能错误可能导致医疗事故 | 功能必须有强制校验点 |
| 临床决策支持 | 功能应为医生提供辅助判断 | 若无规则引擎调用，可能只是基础 CRUD |
| 身份与授权 | 不同角色操作敏感度不同 | 功能必须标注授权粒度 |
| 数据隐私与合规 | HIPAA/等保/电子病历分级要求 | 功能涉及的数据类型必须标记 |
| 互操作性 | 不同系统间数据交换 | 跨系统功能应标注交互协议 |
| 可追溯性 | 所有临床操作需审计留痕 | 关键功能必须记录操作详情 |

## 十、总结

本方案提供了一套完整的功能点划分方法论，核心要点：

1. **明确边界**：CRUD 不是功能点，有上下文交互的 function 才是功能点

5. **落地工具**：Excel 模板 + 操作指南 + 案例演示
