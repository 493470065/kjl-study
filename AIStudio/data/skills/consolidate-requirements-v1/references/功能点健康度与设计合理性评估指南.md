# 功能点健康度与设计合理性评估指南

**版本**: v2.0
**适用范围**: 病历条线（住院 BLGL / 急诊 JZBL / 门诊 MZBL）全部功能点
**定位**: 本文档是 `consolidate-requirements-v1` 技能的指导文档。聚拢脚本只产出**定量健康基线**（独立需求数 + 软质数），**设计合理性评估不在脚本内执行**，由 AI 主会话或分析人员按本文档执行，并将结果回写报告，最终产出结构性治理优先级清单。

> **v2.0 变更 — 引入 Spec 正文证据**：健康度判定依据从"功能结构树骨架"升级为"结构树骨架 + Spec 三件套正文"。归集匹配阶段（脚本）用正文排除范围做互斥校验、纳入范围/业务规则做加分；评估阶段（本指南）将 Spec 正文作为五维评分的**第一证据源**，并新增 V4 零覆盖的核查程序。正文证据索引由 `scripts/build-spec-index.js` 生成（`references/spec-evidence.json`），Spec 文档更新后需重跑刷新。

---

## 一、健康度判定模型

功能点健康度由三个因素共同决定：

| 因素 | 来源 | 说明 |
|------|------|------|
| ① 独立需求数 | 脚本自动统计 | 功能性需求中**非合并类**的需求数 |
| ② 软件质量数 | 脚本自动统计 | 该功能点归集的软质（非功能性）问题数 |
| ③ 设计合理性 | 按本文档评估 | 五维评分框架 + 一票否决制（依据 `design-rationality-rules.md`）；**第一证据源 = Spec 三件套正文** |

**定量问题数 = ① + ②**（合并需求、接口需求不计入健康度）。

> 为什么合并需求不计入：合并类需求是版本集成动作，不反映功能点本身的新增压力。
> 为什么接口不计入：接口需求按三分类单列，属于对接范畴，不反映功能设计健康度。

### 1.1 Spec 正文证据（v2.0 新增）

归集与健康度判定使用两层知识库：

| 层 | 内容 | 用途 |
|:--|:-----|:-----|
| 骨架层 | 3 份功能结构树（33 模块 / 214 功能点：编码+名称+一句话描述） | 归集的坐标系，决定"有哪些功能点" |
| 正文层 | Spec 三件套（研发 Spec / PM-Spec / Analyst-Spec），索引见 `references/spec-evidence.json` | 归集匹配的**证据**与合理性评估的**第一证据源** |

正文层参与点：

1. **归集匹配加分**：需求标题/描述命中功能点正文提取的业务短语（纳入范围/业务规则/验收标准）→ 加分（最多 +4）；
2. **排除范围互斥校验**：功能点正文"排除范围"引用了兄弟功能点编码时，需求在候选功能点间改判（报告 `evidenceRedirect` 标注）；
3. **V4 零覆盖核查**：正文索引中 `hasSpec=false` 的功能点（如会诊管理 007~011、急诊案例管理），若同时有明确需求归入 → 满足一票否决 V4 的核查前提，评估时必须确认；
4. **评估证据引用**：五维评分中维度①（设计覆盖度）、维度③（法规合规性）须引用 Spec 正文具体章节/规则编号（BC-*/AC-*/BR-*），不得凭印象打分。

正文索引是**快照**：Spec 文档新增/修订后重跑 `node scripts/build-spec-index.js` 刷新；第七章"Spec正文"列显示各功能点归集工单的正文证据覆盖率，0% 表示该功能点归集仅靠骨架匹配（结果可能漂移，评估时优先复核）。

## 二、定量健康基线（脚本输出）

聚拢报告第七章《功能点健康度基线》按问题数给出基线等级：

| 问题数 | 基线等级 | 含义 |
|:------:|:--------:|:-----|
| 0~2 | 🟢 健康 | 新增问题少，功能点稳定 |
| 3~5 | 🟡 关注 | 新增问题较多，需评估设计合理性 |
| 6~10 | 🟠 预警 | 新增问题密集，可能存在设计缺陷 |
| >10 | 🔴 危险 | 新增问题过载，建议优先纳入结构性治理 |

**该基线只是健康度评估的输入之一，不能直接作为治理结论。**

## 三、设计合理性评估流程

### 3.1 评估对象

从聚拢报告第七章中选取待评估功能点，优先级：

1. 🔴 危险、🟠 预警功能点 —— **必须评估**
2. 🟡 关注功能点 —— 应当评估
3. 🟢 健康功能点 —— 一般不评估，除非有明显设计质疑

### 3.2 评估依据

按 `references/design-rationality-rules.md` 执行：

- **五维评分框架**（满分15分）：① 设计覆盖度(30%) ② 实现一致性(20%) ③ 法规合规性(25%) ④ 竞品差距(15%) ⑤ 用户效率(10%)
- **一票否决**（V1~V5）：法规红牌 / 数据安全 / 架构缺陷 / 零覆盖 / 严重不一致 —— 满足任一直接判 🔴 设计不合理

### 3.3 评估输入

| 输入 | 路径/来源 | 证据权重 |
|:-----|:---------|:---------|
| **Spec 三件套正文** | `E:\37结构性问题治理\01WiNEX 病历管理\{线}病历Spec\{模块}\{功能点}\`；索引 `spec-evidence.json` | **第一证据源**（v2.0）：维度①③必须引用正文章节/规则编号 |
| Spec 正文证据索引 | `references/spec-evidence.json`（`build-spec-index.js` 产出） | 纳入/排除范围、业务规则（BR）、验收标准（AC）、约束（BC）的结构化快照 |
| 设计/架构文档 | `E:\37结构性问题治理\04参考资料\{模块名}\` | 第二证据源 |
| 需求问题点清单 | 聚拢报告第三章（独立需求）+ 第五章（软质） | 问题事实 |
| 代码事实（可选） | `E:\39EMR\sr-next`（辅助验证实现一致性，维度②） | 实现核对 |

### 3.4 执行方式

- **AI 主会话**：按 `design-rationality-rules.md` 第五节判定流程图逐功能点评估
- **技能衔接**：可调用 `rationality-analysis-v1` 技能批量生成设计合理性分析报告

### 3.5 评估输出

每个功能点产出：**合理性等级**（✅ 设计合理 / 🟢 基本合理 / 🟡 部分合理 / 🔴 设计不合理 / ⚪ 非设计范畴）+ 总分 + 一票否决标记（如有）。

## 四、综合健康度调整矩阵

将定量基线与合理性等级交叉，得到**综合健康等级**：

| 定量基线 \ 合理性 | ✅/🟢 合理 | 🟡 部分合理 | 🔴 不合理（含一票否决） | ⚪ 待评估/非设计范畴 |
|:-----------------:|:---------:|:----------:|:--------------------:|:------------------:|
| 🟢 健康 | 🟢 健康 | 🟡 关注 | 🟠 预警 | 维持基线（标注待评估） |
| 🟡 关注 | 🟡 关注 | 🟡 关注 | 🟠 预警 | 维持基线（标注待评估） |
| 🟠 预警 | 🟡 关注（下调） | 🟠 预警 | 🔴 危险（上调） | 维持基线（标注待评估） |
| 🔴 危险 | 🟠 预警（下调） | 🔴 危险 | 🔴 危险 | 维持基线（标注待评估） |

**规则说明**：
- 合理性 🔴 或触发一票否决 → 综合等级**至少上调到预警**，基线为预警/危险的**上调到危险**
- 合理性 ✅/🟢 且定量基线偏高 → 说明问题多为合理业务演进，可下调一级
- ⚪ 未评估时不得上调或下调，报告中须显式标注"待评估"

## 五、结构性治理优先级

按综合健康等级确定治理优先级，**健康度低的功能点优先纳入结构性治理**：

| 优先级 | 纳入条件 | 治理动作 |
|:------:|:---------|:---------|
| **P0（立即治理）** | 综合 🔴 危险；或触发一票否决（V1~V5） | 立即立项：功能点拆分/重构方案 + 给出优化方案（🔴 不合理必须出方案） |
| **P1（本期治理）** | 综合 🟠 预警；或合理性 🔴 | 纳入本期结构性治理计划，先补设计后改代码 |
| **P2（规划治理）** | 综合 🟡 关注 | 纳入治理规划，跟踪后续期次问题趋势，连续两期仍关注则升级 P1 |
| 不治理 | 综合 🟢 健康 | 保持监控 |

**治理清单字段**（回写报告时使用）：功能点编码/名称、综合健康等级、优先级、独立需求数、软质数、合理性等级与总分、一票否决标记、建议治理动作。

## 六、操作流程（端到端）

```
0. 构建/刷新 Spec 正文证据索引（Spec 文档有更新时）
   node scripts/build-spec-index.js
   → 产出 references/spec-evidence.json（纳入/排除范围、BR 规则、AC 验收、正文关键词）

1. 运行聚拢脚本（定量阶段，自动加载正文索引）
   node consolidate.js
   → 产出：三分类归集 + 独立需求按功能点归类（含正文加分/排除范围改判）
     + 健康度基线（含"Spec正文"证据覆盖列）+ 治理优先级候选

2. 提取待评估清单
   → 第七章中 🟡/🟠/🔴 功能点（🟠🔴 必须评估）
   → "Spec正文"列为 0%/无正文索引 的功能点优先复核归集准确性

3. 设计合理性评估（定性阶段，按本文档第三节）
   → 以 Spec 三件套正文为第一证据源执行五维评分 + 一票否决判定
   → 维度①③须引用正文章节/规则编号（BC-*/AC-*/BR-*）
   → 可由 AI 主会话执行，或调用 rationality-analysis-v1 技能

4. 综合判定（按本文档第四节矩阵）
   → 定量基线 × 合理性等级 → 综合健康等级

5. 产出治理清单（按本文档第五节）
   → P0/P1/P2 优先级清单，回写聚拢报告（八）章节或独立治理报告
```

---

## 七、注意事项

- **Spec 正文是第一证据源**：评分引用不到正文证据的维度（①③）最高只给 2 分，防止凭印象打分；正文索引 `hasSpec=false` 的功能点评估时先确认是否属于 V4 零覆盖
- 设计合理性判定**随设计文档更新而失效**：设计文档新增/修订后需重新评估受影响功能点，并重跑 `build-spec-index.js` 刷新正文索引
- BUG/运维/第三方集成问题属于 ⚪ 非设计范畴，不参与合理性评分，但其数量仍计入软质问题数
- 本期未评估的功能点，综合等级保持定量基线并标注"待评估"，不得凭印象上调/下调
- 合并需求与接口需求不计入健康度，但须在归集报告中完整单列，保证数据可追溯
