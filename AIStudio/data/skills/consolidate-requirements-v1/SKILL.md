# consolidate-requirements-v1

将 TFS 查询中的工作项（包括**需求**和**软质**），按照 Spec 知识库的功能模块结构树进行聚拢分类，输出结构化的需求清单（Markdown 文件）。

- **需求** = 功能性 + 接口
- **软质** = 软件质量（非功能性）

## 🚀 快速使用

### 方式1：聚拢需求清单
```bash
node ~/.claude/skills/consolidate-requirements-v1/scripts/consolidate.js
```

### 方式2：将 MD 报告转为 HTML（含导航树）
```bash
node ~/.claude/skills/consolidate-requirements-v1/scripts/generate-html-report-v3.js
```

输出文件自动生成到：`E:\37结构性问题治理\07病历条线需求聚拢\`

### 方式3：JSON 模式（供 AIStudio 需求归集「技能数据源」消费）
```bash
node scripts/consolidate.js --json          # 或调用参数 {"json": true}
```
stdout 仅输出功能点 FPI JSON 数组：`[{code,name,module,total,req,soft,avgMonthly,softRatio,trend,fpi}]`，进度信息走 stderr。

支持参数（写在调用参数 JSON 里）：`line`（inpatient/住院、outpatient/门诊、emergency/急诊，只在该条线功能点池中匹配并输出）、`queryUrl`（覆盖默认 TFS 查询）。

### 方式4：MD 报告模式（供 AIStudio 需求归集「导出 MD」下载）
```bash
node scripts/consolidate.js --md            # 或调用参数 {"md": true, "line": "..."}
```
执行完整聚拢流程，stdout 仅输出 MD 报告全文（进度走 stderr，不写文件）。与 JSON 模式共用 `line`/`queryUrl` 参数；两者同时传时 JSON 优先。

### 步骤5：匹配流程（四阶段漏斗）

```
获取需求 → 先基线判断 → 基线能力 → 标记基线排除 ✔
                      → 应纳入功能点 → 语义匹配 → 归入现有功能点 ✔
                                        → 无匹配
                                            ├─ 软质项 → 归入模块级软质统计 ✔
                                            └─ 非软质 → 建议新增功能点 ⭐
```

#### 阶段1：方法论基线过滤（优先）

先应用 [WiNEX 功能点划分原则与方法论](references/WiNEX功能点划分原则与方法论.md) 判断每个需求是否属于基线能力：

| 基线类型 | 示例 | 处理方式 |
|:---------|:-----|:---------|
| 单对象增删改查 | 新增患者、删除医嘱、修改药品信息 | ❌ 排除 |
| 列表/导出/打印 | 导出费用清单、打印腕带、查询检验报告列表 | ❌ 排除 |
| 字典/配置管理 | 维护药品字典、配置角色权限 | ❌ 排除 |
| 纯技术接口 | REST API、HL7 消息通道、数据库同步 | ❌ 排除 |
| ✅ 有业务交互特征 | 涉及校验/审核/审批/触发/联动/自动生成/预警等 | ⭐ 继续匹配 |

#### 阶段2：语义匹配（LLM 映射表）

通过基线的需求，使用 AI 语义映射表匹配到最合适的 Spec 功能点。映射表由 AI 根据需求标题+描述语义判断，比关键词匹配更准确。

#### 阶段3：软质项兜底

语义匹配不到的软质项（`requirementType = '软件质量'`），按模块级归类，归入软质统计。连模块都匹配不到的软质项，归入基线排除。

#### 阶段4：模块级匹配（兜底）

语义匹配不到的非软质需求，先按 TFS 模块名称映射，再按关键词匹配到模块级。如果仍匹配不到，标记为"建议新增功能点"。

### 步骤6：输出结果

脚本输出为 Markdown 文件，每个子系统包含以下章节（主章节六章 + 文末独立章节）：

#### （一）归集汇总
```
| 模块名称 | 匹配功能点数 | 问题数 | 合并需求 | 独立需求 | 软质数 | 占比 |
|:---------|:-----------:|:-----:|:--------:|:--------:|:-----:|:----:|
| BLGL-01-BLSX 01 病历书写 | 10 | 31 | 0 | 28 | 3 | 25% |
| **合计** | **48** | **126** | **0** | **83** | **43** | **100%** |
```

> 问题数 = 合并需求 + 独立需求 + 软质数

#### （二）合并需求详情
列出所有合并需求项的 ID、标题、所属模块、类型。

#### （三）软质详情
列出所有软质问题的 ID、标题、所属模块。

> 注：原「基线需求详情」章节已移除（未匹配到具体功能点的模块级需求归入基线排除清单）。基线排除清单移至文末独立章节并带合计统计。

## 聚拢规则

聚拢采用**四阶段漏斗策略**：

### 阶段1：方法论基线过滤（优先）

先判断每个需求是否应纳入功能点。基线能力（单对象增删改查/列表导出打印/字典配置/纯技术接口）直接排除，不纳入功能点统计。

### 阶段2：语义匹配（LLM 映射表）

通过基线的需求，查询 AI 语义映射表 `references/semantic-fp-map.json`，匹配到具体的 Spec 功能点。该映射表由 AI 根据需求标题+描述语义判断，无需维护关键词库。

### 阶段3：软质项兜底

语义匹配不到的软质项（`requirementType = '软件质量'`），按模块级归类，归入软质统计。连模块都匹配不到的归入基线排除。

### 阶段4：模块级匹配（兜底）

语义匹配不到的非软质需求，先按 TFS 模块名称映射，再按关键词匹配到模块级。如果仍匹配不到，标记为"建议新增功能点"。

## 数据口径说明

> 用于审计和追溯数据筛选逻辑。

### 聚拢范围
- **产品名** ∈ {WiNEX 病历管理, 03 WiNEX 急诊病历, WiNEX 门诊病历管理}
- **AreaPath 排除**：`WiNEX-Inpatient-2\病历质控` 与 `WiNEX-Outpatient\病历质控`
- **工作项类型**：同时纳入**需求**（功能性 + 接口）和**软质**（软件质量），不做类型过滤

### R27 过滤
- `ResolvedDate = ''` OR `ResolvedDate ≠ ClosedDate`

### 需求分类
| 类别 | 定义 |
|:-----|:------|
| **需求** | 功能性 + 接口 |
| **软质** | 软件质量（非功能性） |

### 来源分类
| 类别 | 判定规则 |
|:-----|:---------|
| **医院需求** | `CreatedBy` 含 `TfsInterface` |
| **内部优化** | 其他创建者 |

### 合并需求识别
正则：`/合并\d{3,}|@1?\d{6,}|（合并|合并多|合并代码|合代码|合并需求\d|合并需求至|合并需求：|合并【\d+】|克隆主数据|历史需求合并|合并升级|合并单|合并到版本|合并至版本|至\d{6}迭代|到\d{6}迭代|至\d{6}版本|至泰康\d/`（覆盖「合并+单号/版本号」自由格式，含医院创建的合并升级）

### 主题分类
- **标题正则（细粒度）优先**：按标题正则表达式匹配进行主题分类
- **标题归 G 时 TFS Module 标准模块兜底**：当标题无法匹配时，使用 TFS 模块名称字段

### 本次未使用主题关键词筛选
- 仅按产品过滤
- 主题分类由 AI 在主 session 内动态归纳

## 注意事项

- **默认令牌**已内置在脚本中，直接运行即可
- **默认查询**为病历条线新增需求查询（WiNEX 病历管理/急诊病历/门诊病历管理）
- 如需切换其他查询，传入参数覆盖默认值即可
