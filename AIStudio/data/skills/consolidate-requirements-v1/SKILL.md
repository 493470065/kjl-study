# consolidate-requirements-v1

将 TFS 查询中的工作项，按照 Spec 知识库的功能模块结构树进行聚拢分类，输出结构化的需求归集报告（Markdown 文件）+ 功能点健康度定量基线 + 结构性治理优先级建议。

## 🎯 需求归集四目标

1. **三分类**：把 TFS 获取到的需求按 **功能性的 / 接口 / 软件质量** 分类
2. **合并/独立区分**：功能性需求区分 **合并类** 与 **独立类**（合并识别仅针对功能性需求）
3. **按功能点归类排序**：独立性功能需求按 Spec 功能点归类，并按功能点编码排序
4. **健康度与治理优先级**：功能点健康度 = **独立需求数 + 软件质量数**（定量基线）+ **设计合理性**（按指导文档评估）；健康度低的功能点优先纳入结构性治理

> ⚠️ **设计合理性已从脚本中拆出**：脚本只产出定量健康基线，设计合理性评估按指导文档《功能点健康度与设计合理性评估指南》执行（五维评分 + 一票否决），评估结果回写报告后确定综合健康度与治理优先级。

## 工作流程

### 步骤0：获取 Spec 知识库（动态加载）

脚本启动时自动从 Git 仓库获取最新 Spec 知识库（住院/急诊/门诊 3 份功能结构树，解析出 33 个模块、214 个功能点）。Git 仓库不可用时自动回退到本地缓存。

**Spec 正文证据（v2.0）**：除结构树骨架外，归集匹配还使用 Spec 三件套正文（纳入范围/排除范围/业务规则/验收标准）做证据——正文关键词命中加分、排除范围引用兄弟功能点编码时做互斥改判。正文索引由 `scripts/build-spec-index.js` 预先构建（`references/spec-evidence.json`，覆盖 Spec 目录下全部功能点三件套）；**Spec 文档更新后需重跑该脚本刷新**，索引缺失时脚本降级为纯骨架匹配并打印警告。

### 步骤1：获取输入（使用默认值）

- **TFS 查询 URL** → 病历条线新增需求查询（已内置）
- **PAT 令牌** → 已配置
- **输出路径** → 默认 `E:\37结构性问题治理\07病历条线需求聚拢\`，自动按当天日期命名

如需切换到其他查询，可传入参数覆盖默认值。

### 步骤2：检查依赖

```bash
node --version
```
（脚本使用 Node.js 内置 http 模块，无需 npm 安装）

### 步骤3：执行聚拢脚本

```bash
node <skill-path>/scripts/consolidate.js [tfs-query-url] [pat-token] [output-path]
```

### 步骤4：三分类 + 聚拢匹配

```
获取需求 → 目标(1) 三分类：功能性的 / 接口 / 软件质量
  │
  ├─ 功能性的 → 合并识别（目标2）→ 合并类 → （二）合并需求详情
  │         └─ 独立类 → 基线过滤 → 基线能力 → 基线排除清单
  │                             └─ 非基线 → 功能点语义匹配（目标3）→ （三）按功能点归类排序
  │                                                     └─ 无匹配 → （六）建议新增功能点
  ├─ 接口 → （四）接口需求详情（单列，不计入健康度）
  └─ 软件质量 → 功能点/模块级归类 → （五）软质详情（计入健康度）
```

**基线过滤仅作用于功能性需求**（单对象增删改查/列表导出打印/字典配置/纯技术接口），依据 [WiNEX 功能点划分原则与方法论](references/WiNEX功能点划分原则与方法论.md)。接口与软质按分类单列，不做基线排除。

### 步骤5：输出报告（每子系统八章）

| 章节 | 内容 |
|:-----|:-----|
| （一）三分类归集汇总 | 各模块 功能性-合并/功能性-独立/接口/软质/问题数/占比 |
| （二）合并需求详情 | 功能性-合并类完整列表 |
| （三）独立需求功能点归类详情 | 功能性-独立类，按功能点编码排序 |
| （四）接口需求详情 | 接口需求单列 |
| （五）软质详情 | 软质问题 + 关联功能点 |
| （六）建议新增功能点 | 未匹配到现有功能点的独立需求 |
| （七）功能点健康度基线 | 独立需求数 + 软质数 → 定量基线；设计合理性列标 ⚪待评估 |
| （八）结构性治理优先级建议 | P0/P1/P2 候选清单 |

### 步骤6：设计合理性评估与治理清单（定性阶段，脚本外执行）

按 [功能点健康度与设计合理性评估指南](references/功能点健康度与设计合理性评估指南.md) 执行：

1. 从第七章提取 🟡/🟠/🔴 功能点作为待评估清单（🟠🔴 必须评估）
2. 对照设计文档执行五维评分 + 一票否决判定（依据 [design-rationality-rules.md](references/design-rationality-rules.md)，可衔接 `rationality-analysis-v1` 技能）
3. 按指南第四节"综合健康度调整矩阵"得出综合健康等级
4. 按指南第五节产出 P0/P1/P2 结构性治理清单，回写报告

## 数据口径说明

> 用于审计和追溯数据筛选逻辑。

### 聚拢范围
- **产品名** ∈ {WiNEX 病历管理, 03 WiNEX 急诊病历, WiNEX 门诊病历管理}
- **AreaPath 排除**：`WiNEX-Inpatient-2\病历质控` 与 `WiNEX-Outpatient\病历质控`

### R27 过滤
- `ResolvedDate = ''` OR `ResolvedDate ≠ ClosedDate`

### 需求三分类
| 类别 | 判定规则（Microsoft.VSTS.CMMI.RequirementType） |
|:-----|:------|
| **功能性的** | 功能性的 / 空值 / 未知（默认） |
| **接口** | 接口 / Interface |
| **软件质量** | 软件质量 / 软质 |

### 合并/独立
- 合并识别**仅针对功能性需求**；接口与软质不做合并区分
- 正则覆盖「合并+单号/版本号」自由格式，含 `合并到{版本号}`/`合并至{版本号}`（如"合并到260715"）
- 合并需求、接口需求**不计入**功能点健康度

### 健康度口径
- **问题数 = 独立需求数 + 软质数**
- 0~2 🟢健康 / 3~5 🟡关注 / 6~10 🟠预警 / >10 🔴危险（定量基线）
- 综合健康度 = 定量基线 × 设计合理性（调整矩阵见指导文档）
- **归集匹配证据 = 结构树骨架 + Spec 三件套正文**（v2.0）：正文命中加分（≤+4）、排除范围互斥改判；第七章输出各功能点"Spec正文"证据覆盖率，0% 的功能点归集仅靠骨架匹配，评估时优先复核

### 来源分类
| 类别 | 判定规则 |
|:-----|:---------|
| **医院需求** | `CreatedBy` 含 `TfsInterface` |
| **内部优化** | 其他创建者 |

## 注意事项

- **Spec 正文索引刷新**：Spec 三件套文档新增/修订后，先运行 `node scripts/build-spec-index.js` 重建 `spec-evidence.json`，再跑聚拢脚本；索引缺失时归集降级为纯骨架匹配（脚本会打印警告）
- **默认令牌**已内置在脚本中，直接运行即可
- **默认查询**为病历条线新增需求查询（WiNEX 病历管理/急诊病历/门诊病历管理）
- 如需切换其他查询，传入参数覆盖默认值即可
- PAT 令牌需要 **Work Items 读取** 权限；Basic Auth 认证（格式: `PAT:{token}`）
- TFS 2018 兼容，使用 `api-version=2.0`；单次查询最多 20000 个工作项，超过需分批处理
- **语义映射表** `semantic-fp-map.json` 由 AI 维护，当新增需求或功能点变化时需同步更新；设计合理性评估发现的归集偏差（跨模块误归）也应回补登记，形成"归集→评估→口径修正"闭环
- **设计合理性不在脚本内评估**：健康度基线表中"设计合理性"列恒为 ⚪待评估，须按指导文档完成评估后回写
