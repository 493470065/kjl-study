# Std Code Merge - TFS 代码合并

本技能用于分析 TFS 需求工作项，查找该需求下的拉取请求，并对拉取请求修改的代码合并到目标分支上。

## 依赖

本技能依赖 `tfs2018-integration` 技能进行 TFS 操作。

## 工作流程：TFS 任务合并到新分支

**用户指令格式：**

```
合并需求 [需求号],新任务[新任务号]
```

**执行步骤：**

0. **解析用户输入：**
    - 从用户指令中提取需求号和新任务号
    - **第一个参数**：需求号 - 查询需求详情
    - **第二个参数**：新任务号 - 用于：
        1. 创建分支名 `feature/[新任务号]`
        2. Commit 前缀 `#[新任务号]`
        3. 查询其父级工作项ID（用于添加 AI-MERGE 标记）
    - 如果用户没有提供需求号和新任务号，提示用户提供

1. **查询合并信息（需求详情 + 任务父级ID）：**
    - 使用本技能提供的 `query-merge-info.mjs` 工具
    - **用法**：
        ```bash
        node tools/query-merge-info.mjs <需求号> <新任务号> [项目名称]
        ```
    - **示例**：
        ```bash
        node tools/query-merge-info.mjs 1144995 1485439 WiNEX-Inpatient-2
        ```
    - **输出内容**：
        - 需求详情（ID、标题、类型、状态、项目）- 用于显示确认
        - 新任务号的父级工作项ID - 用于后续添加 AI-MERGE 标记
        - JSON 格式结果，包含 `tagTargetId` 字段供步骤 9 使用
    - **注意**：
        - 需求号：仅查询详情显示给用户，**不查询其父级工作项**
        - 新任务号：查询其父级工作项ID，用于步骤 9 添加 AI-MERGE 标记
    - 显示需求的基本信息，确认用户要合并的需求
    - 存储标记目标ID供步骤 9 使用（从工具输出的 JSON 中获取 `tagTargetId` 字段）

2. **获取分支信息（分两步进行）：**

    **步骤 2.1 - 选择源分支：**
    - **⚠️ 重要提醒**：先确认要合并的需求信息，然后再选择分支
    - **⚠️⚠️⚠️ 极重要：description 必须严格按照下方示例中的值使用，不可随意修改！**
        - `sr-rc` 的 description 必须是 `2502.25`
        - `sr-next` 的 description 必须是 `2508.215`
        - 这些数值是分支版本标识，具有特定含义，修改会导致分支选择错误
    - 使用 `AskUserQuestion` 询问源分支：
        ```javascript
        AskUserQuestion({
            questions: [
                {
                    question: "请选择源分支（包含需要合并代码的分支）",
                    header: "源分支",
                    multiSelect: false,
                    options: [
                        { label: "sr-rc",description:2502.25},
                        { label: "sr-next",description:2508.215}
                    ]
                }
            ]
        })
        ```
    - 获取用户选择的源分支名称
    - 如果用户选择"其他"，通过其他方式获取自定义分支名称

    **步骤 2.2 - 提醒并选择目标分支：**
    - **⚠️ 重要提醒**：向用户明确提示下一步将选择目标分支，避免研发人员误操作
    - **⚠️⚠️⚠️ 极重要：description 必须严格按照下方示例中的值使用，不可随意修改！**
        - `sr-rc` 的 description 必须是 `2502.25`
        - `sr-next` 的 description 必须是 `2508.215`
    - 提示信息示例：
        ```
        ✅ 已选择源分支：[分支名称]

        📌 下一步：请选择目标分支（将要合并到的目标基础分支）

        ⚠️ 注意：源分支和目标分支不能相同！
        ```
    - 然后使用 `AskUserQuestion` 询问目标分支：
        ```javascript
        AskUserQuestion({
            questions: [
                {
                    question: "请选择目标分支（将要合并到的目标基础分支）",
                    header: "目标分支",
                    multiSelect: false,
                    options: [
                      { label: "sr-rc",description:2502.25},
                        { label: "sr-next",description:2508.215}
                    ]
                }
            ]
        })
        ```
    - 获取用户选择的目标分支名称
    - **验证**：源分支和目标分支不能相同，如果相同，提醒用户重新选择
    - 如果用户选择"其他"，通过其他方式获取自定义分支名称

    **存储结果：**
    - 将源分支和目标分支名称存储供后续步骤使用

3. **在源分支中查找有效代码：**
    - 使用 <需求号> 在TFS上查找所有相关任务
    - 在 [源分支] 上找到这些任务的有效拉取请求
    - 同时查找相关缺陷：需求 -> 任务 -> 缺陷，然后在 [源分支] 上找到这些缺陷的有效拉取请求

    **说明**：
    - **<需求号>** 使用步骤 1 中输入的需求号

    **推荐使用工具**：
    - `find-demand-code.mjs` - 查询需求下的代码提交
    - `query-demand-parent-id.mjs` - 已在步骤 1 中使用，获取了父级工作项ID

    本技能提供了 `find-demand-code.mjs` 工具，可一站式完成 **需求 -> 任务 -> 代码提交** 的查询流程（主要功能）。

    同时也支持 **需求 -> 任务 -> Bug -> 代码提交** 的查询流程。

    **用法：**
    ```bash
    # 在项目目录中执行（需要在 Git 仓库内）
    node tools/find-demand-code.mjs <需求号> [分支]

    # 示例
    node tools/find-demand-code.mjs 1205924 origin/sr-rc
    node tools/find-demand-code.mjs 1205924 HEAD
    ```

    **输出内容：**
    - 需求信息（需求号、标题、状态、项目、产品）
    - 关联任务列表（任务号、标题、状态）
    - 关联 Bug 列表（Bug号、标题、状态，如有）
    - 代码提交列表（提交哈希、提交信息、作者、日期、修改文件）
    - JSON 格式结果，便于后续处理

    **工具特点：**
    - ✅ 自动获取需求下的所有任务
    - ✅ 自动获取任务下的所有 Bug（如有）
    - ✅ 直接通过任务号查找 git 提交（主要查询方式）
    - ✅ 在指定 Git 分支上查找相关提交
    - ✅ 显示每个提交修改的文件列表
    - ✅ 输出 JSON 格式，便于集成其他流程

4. **分析和合并代码：**
    - 分析步骤3中的所有有效代码（包括任务和缺陷）
    - 与 [目标分支] 对比，了解当前状态
    - 从 [目标分支] 创建新分支 `feature/[新任务号]`

5. **重要提示：始终在功能分支上工作**，不要在 [目标分支] 上合并：
    - 使用 `git status` 确认你在功能分支上
    - 使用 `git merge <commit-hash>` 合并分析的代码（如果合并因冲突失败，进入步骤6）
    - 如果因冲突导致合并失败，使用 `git merge --abort` 中止，并在步骤6中手动处理变更

6. **处理模块移动和代码重构：**
    - 合并后（或合并失败后），识别引用了已移动或重构模块中类的文件
    - 在 [目标分支] 中搜索已移动的类，根据文件名称找到它们的新模块位置
    - 更新导入和包声明以匹配新的模块结构
    - 确保所有依赖项（DTO、DO、Service、Repository）在其新位置中被正确引用
    - 验证重定位后功能保持完整
    - 如果整个模块被重命名，相应更新 `pom.xml` 文件中的 Maven 依赖
    - 通过更新引用使用新的模块路径，修复任何未解析的导入或缺失的依赖
    - **仅在功能分支上提交所有变更**

7. **必须按照规范提交代码（强制步骤）：**
    - 使用 `git commit` 提交所有变更，提交信息**必须**以 `#[新任务号]` 为前缀
    - 提交信息示例：`#[新任务号] 合并需求1205924和1484704到sr-next`
    - 不符合规范的提交将无法通过审查

8. **推送分支到远程服务器：**
    - 使用 `git push origin feature/[新任务号]` 将功能分支推送到远程服务器

9. **添加AI合并标记：**

    更新TFS工作项，添加"AI-MERGE"标记，标识该工作项已通过AI合并：

    ```bash
    # 从 tfs2018-integration 目录返回本技能目录
    cd ../std-code-merge
    node tools/add-work-item-tag.mjs <父级工作项ID> "AI-MERGE"
    ```

    **说明**：
    - 标记名称：`AI-MERGE`
    - 用途：标识该工作项已通过AI合并
    - 执行时机：代码推送成功后
    - **<父级工作项ID>** 使用步骤 1 中查询到的父级工作项ID
    - 如果标记已存在，不会重复添加

    **示例**：
    ```bash
    # ✅ 使用步骤 1 中获取的父级工作项ID
    node tools/add-work-item-tag.mjs 1485197 "AI-MERGE"
    ```

10. **生成合并完成报告：**
    - 合并完成后，生成以下详细报告内容：
        - **需求信息**：需求号、需求标题、需求描述
        - **分支信息**：源分支、目标分支、功能分支名称
        - **合并任务列表**：包含的任务编号及描述
        - **合并Bug列表**：包含的Bug编号及描述
        - **PR合并记录**：所有被合并的PR编号、提交哈希、提交信息
        - **修改文件统计**：修改的文件数量、新增文件、删除文件、修改文件列表
        - **冲突处理情况**：是否发生冲突、冲突文件列表、解决方案摘要
        - **提交信息**：功能分支的提交哈希、提交时间
        - **下一步建议**：代码审查建议、测试验证建议、合并到主分支的建议

## 成功经验

### 合并任务的正确方法

**问题背景（示例：从 sr-rc 合并到 sr-next）：**

- 初次尝试合并任务 1466732 时，试图直接合并 `sr-rc` 上的所有相关提交，遇到大量冲突
- `sr-rc` 和 `sr-next` 分支之间存在大量代码差异和重构

**正确做法：**

1. **只查询需求下的任务和bug关联的PR**
    - 使用 `git log origin/sr-rc --grep="任务号|bug号" --grep="已合并 PR" --oneline`
    - 找到具体的PR合并提交，例如：
        - `已合并 PR 735560: #1009242 计算业务单元类型`
        - `已合并 PR 783374: #1113006 接口返回的业务单元，临床根据算法重算业务单元`
        - `已合并 PR 783541: 将 bugfix/1113006/sr-rc 合并到 sr-rc`

2. **提取PR中的核心代码变更**
    - 使用 `git show <commit-hash> --name-only` 查看PR修改了哪些文件
    - 只关注与任务直接相关的文件，而不是PR中的所有文件
    - 例如任务 1466732 相关的只有：
        - `ClinicalConstant.java` - 添加常量
        - `BusinessUtil.java` - 更新业务逻辑

3. **在feature分支上手动应用变更**
    - 使用 `git show <commit-hash>` 查看具体的代码diff
    - 逐个文件应用这些变更
    - 避免合并大量无关代码导致的冲突

4. **遇到冲突时的处理**
    - 如果cherry-pick遇到冲突，先abort
    - 手动查看并应用具体的代码变更
    - 不要试图解决所有冲突，只应用任务需要的部分

**关键要点：**

- ✅ 只查询和合并任务|Bug相关的PR，而不是所有提交
- ✅ 提取PR中与任务|Bug 直接相关的文件变更
- ✅ 避免合并大范围的重构代码
- ✅ 手动应用具体的代码变更，而不是整体merge
- ✅ 保持代码简洁，只包含功能性变更

**对比示例：**

- ❌ 错误：`git merge <large-merge-commit>` - 会导致大量冲突
- ✅ 正确：提取PR中的具体文件变更，手动应用
- ✅ 正确：`git show <commit-hash>` 查看diff，然后手动编辑文件

> **说明：** 上述示例使用 `sr-rc` 作为源分支、`sr-next` 作为目标分支。实际执行时应替换为用户通过步骤 0 输入的分支名称。

**重要说明：**

- **只需要合并代码逻辑，不要调整格式**
- 不要修改空行、缩进、换行符等格式相关的改动
- 格式调整会影响代码对比，导致无法正确验证合并是否正确
- 只保留功能性的代码变更
