# 医疗信息系统知识库需求分析（不扫码版）

把 TFS 医疗信息系统需求转成可确认、可追溯、可回写 `Winning.Demand.Analysis` 的正式产品业务分析正文。分析阶段不修改代码、不创建开发分支、不拆研发计划；**不扫描代码仓库**，基于 **知识库（功能清单/Spec文档/参数资料/业务知识）** 验证现状、判断边界、形成产品设计、原型字段明细和测试用例。

## 适用边界

- **必须有 TFS 需求号**：无 TFS 需求号即停止，不生成 `产品业务分析.md`，不搜索代码，不读取旧文件，不回写 TFS。
- **输入来源独立**：只以当前 TFS 工作项、附件/图片、前置/相关工作项、知识库功能清单、参数资料和 Spec 文档为输入；**不依赖代码仓库扫描**。
- **只做产品业务分析**：不生成研发实现方案、接口设计、数据库设计、开发任务拆分或研发计划。
- **不处理时限讨论**：不追加"时限要求/AI时限建议"类讨论。
- **正式交付固定三件事**：写入 `Winning.Demand.Analysis`，追加 `AI-ANALYSIS` 和 `std-req-analysis-kb-only-v5` **标签**（不写入正文），上传最终版 `产品业务分析.md`。
- **自动创建分析任务**：正式分析完成后默认检查并创建 `需求分析_<需求号>` 子任务，已存在则跳过。

## 强制规则

> 详细规则说明见 [references/rules.md](references/rules.md)（注意：本技能为不扫码版，Rule 3 代码搜索规则不适用，替代为知识库核查规则）

| R13 | 正文不得含待确认：需求分析正文中不得出现"待确认"、"待讨论"、"需确认"、"TBD"等不确定表述。所有待确认问题必须在正文生成前向用户逐项澄清。 |
| R14 | 历史痕迹隔离：严禁复用本地 `.ai-work/` 或工程目录下的旧源稿、旧正文或旧过程记录作为分析依据。每次分析新建带时间戳的运行目录。 |
| R15 | 简单需求快速通道：当 `System.Tags` 包含"简单需求"时，跳过 Brainstorming（步骤 4）和 `autoplan` 深度评审（步骤 6），直接使用增强自检。 |
| R16 | 相似需求来源识别：除工作项关联外，还要从注释/讨论区 `【相似需求清单】`、`【同机构相关需求清单】` 识别相似需求；准入条件 `State ∈ {已解决/已关闭/已验证}` 且 `ResolvedDate ≠ ClosedDate`；通过准入的相似需求必须读取描述/分析字段/附件作为推荐方案依据；禁止凭标题臆造历史需求号。 |
| R17 | 变通方案书写规则：客户诉求 ≠ 最终方案。知识库已有功能/参数/相似需求能覆盖时鼓励给出推荐方案；变通方案非强制但**必须具体**（明确复用对象+差异点+取舍理由），禁止"可以考虑复用"等空泛表述；无变通空间时直接展开推荐方案。 |
| R18 | 重点文字加粗节制：句中加粗关键改造对象/业务效果/业务规则/代码值；禁止加粗章节标题、变更点引导词、整句整段、情感强调；一次加粗 4-15 字，一句话最多 2-3 处；没有关键信息就不加粗。 |

## 执行流程

按以下步骤顺序执行。遇到阻塞项立即停止。`notes.md` 只用于记录**异常、降级、待确认线索**（如下载失败、降级原因），不记录每步状态或已知判断结论。

### 0. 前置检查

1. **TFS 需求号**：用户必须提供，无则终止
2. **产品线识别**：按 `Winning.Product.Name` 判断（R3）。无法判断时使用 `defaultProduct` 配置值
3. **简单需求标记**：检查 `System.Tags`，若包含"简单需求"，后续跳过步骤 4（Brainstorming）和步骤 6 的 `autoplan` 深度评审（R15）

运行目录使用 `.ai-work/requirements/<需求号>/<yyyyMMdd-HHmmss>/`，直接创建，不检查历史目录。严禁复用历史目录下的分析文件（R14）。

### 1. 获取需求

使用当前会话的 TFS MCP 工具直接调用，不要在调用前检查工具是否存在。MCP 调用失败时，降级到本地 `tfs-client.mjs`（从 SKILL 同级目录或 `mcp-tfs-query` 目录查找）。两者都不可用时才终止。需要的 TFS 能力：获取工作项、列出附件、下载附件、上传附件、更新字段、更新需求分析、创建工作项。

**第一波并行**（互不依赖，同时发起）：
1. 获取工作项 — 同时完成 TFS 可用性验证和产品线识别（R3）
2. 列出附件
3. 对每个前置/参见需求、父子项、关联 Bug 同时获取

**第二波并行**（收到附件列表后）：
1. 对所有附件同时发起 `download_attachments`，批量下载到 `attachments/`。**跳过 AI 生成的附件**（附件名包含：评审单、需求分拣结果、需求预分析、产品业务分析、自测报告）
2. 对 `System.Description` 中提取的内嵌图片（`<img src="...">`、`FileNameGuid`、`_apis/wit/attachments`），并行下载

附件和内嵌图片处理要点：
- `list_attachments()` 返回 0 时仍需检查 `System.Description` 中的内嵌图片
- 图片要通过已认证的 TFS MCP 下载，优先复用 `serverUrl + PAT`
- 图片 URL 返回 401/403 时先判断是权限问题还是链接失效，再决定是否写入 `notes.md`
- 图片、截图、原型图和流程图都要解读；无法识别或下载失败时记录到 `notes.md`
- 图片**不应出现在最终正文**中
- 解读界面图时至少提取入口位置、区域名称、字段/按钮、权限差异、默认值/空态；看不清的写成待确认问题
- **图片分析方式**：下载到本地后，使用当前 AI 工具的图片读取能力（如文件读取、视觉模型等）查看图片内容。若当前工具无法直接分析本地图片，尝试先通过文件读取功能获取可访问的图片 URL，再调用图片分析工具

**内嵌图片下载**：必须优先使用 `scripts/download_tfs_embedded_images.py` 脚本下载，该脚本已内置 gzip 自动解压和 PAT 认证。**禁止使用 curl 直接下载**（TFS 服务器返回 gzip 压缩响应，curl 未加 `--compressed` 时会保存损坏的二进制文件）。仅在 Python 不可用时才允许 curl 降级，且必须加 `--compressed` 参数。认证细节见 `references/tfs-integration.md`。

**读取相关工作项**：只读取当前需求明确提到且与本次诉求相关的关联项；不遍历全部历史需求。关联项中的图片/附件仅在影响本需求理解时处理。

**分析者描述偏重**：TFS `System.Description` 中【分析者描述】段是分析人员对现场描述的**补充与初步分析**，比现场描述更明确。判断该段是否含实质内容（去掉 HTML 标签、空白和占位符提示文字"要求的详细分析…"等之后，剩余有效文字 ≥ 20 汉字或含具体业务信息）：
- **有实质内容**：分析时偏重参考分析者描述——业务意图、方案方向、字段口径、测试用例以它为优先依据；与现场"原始描述"冲突时优先分析者描述
- **无实质内容**（仅占位符或空白，这是大多数需求的情况）：按现场描述正常分析

不强制抽取子项，分析时偏重即可。

### 2. 识别业务背景

- 根据标题、产品、页面名称和关键词判断候选业务域
- **知识库加载策略**：按产品线加载对应的 `Knowledge/` 目录：
  - 病案产品线 → 优先加载 `Knowledge/病案/` 下相关功能清单
  - 病历产品线 → 优先加载 `Knowledge/病历/` 下相关功能清单
  - 默认只加载最相关的 1-3 个知识库文件，避免加载无关大文件
- 涉及菜单名称时，结合知识库 Spec 文档中的功能描述和页面结构判断
- 同一组件被多个菜单复用时，把所有受影响菜单都写入功能变更表格
- **相似需求来源识别**：除工作项关联（`related`/`predecessor`/`successor`）外，还要从注释/讨论区识别相似需求。注释常见结构：
  - `【相似需求清单】` 标题 + 紧随其后的 `相似需求ID：<逗号分隔的7位ID列表>` 行，下方每个 ID 对应业务场景、核心诉求、方案成熟度等结构化描述，为主体相似需求来源。
  - `【同机构相关需求清单】` 为同机构补充参考来源，每个 ID 对应一行简要关联说明，不强制满足准入条件，仅作背景参考。
- **相似需求准入条件**：从注释/讨论识别的相似需求必须同时满足：`System.State` ∈ {`已解决`，`已关闭`，`已验证`}，且 `Microsoft.VSTS.Common.ResolvedDate` ≠ `Microsoft.VSTS.Common.ClosedDate`（含时分秒完整比较，任一字段为空视为不满足）。不满足的相似需求只作为背景参考，不作为推荐方案依据。
- **相似需求内容读取**：通过准入的相似需求**必须读取**其 `System.Description`、`Winning.Demand.Analysis` 和附件，将业务场景、核心诉求和方案要点反映到当前需求的产品设计章节，作为推荐方案/变通方案的参考依据。不得凭相似标题自行编造历史需求号——只有当前需求描述、工作项关系、相似需求来源或 TFS 查询结果明确返回某个历史需求号时，才能引用。

### 3. 知识库核查（替代原代码搜索步骤）

> **R5-KB 强制**：分析前必须基于知识库验证现状，知识库是主要参考依据。

**知识库加载策略**：不要加载全部知识库文件。按以下优先级选择性加载：

1. **功能清单优先**：根据产品线和需求关键词，从 `Knowledge/` 中找到对应的功能结构树（如 `Knowledge/病历/住院病历系统功能结构树.md`）或功能清单文档
2. **Spec 文档次之**：涉及具体功能点时，读取对应模块的 Spec 文档（如 `BLGL-02-FZLR/` 下的 Spec 文档），了解字段定义、交互逻辑和业务规则
3. **参数资料**：涉及参数配置时，加载 `references/Param/` 下的参数资料

**关键词提取**：从需求标题和描述中提取 2-4 个业务关键词，用于在知识库中定位相关功能模块。优先客户原文中的菜单名、页面名、字段名、按钮名、唯一业务术语。

**知识库核查要点**：
- 需求中的功能点是否在知识库 Spec 中已有定义？
- 知识库中是否有类似功能可参考？
- 涉及字段时，知识库中对字段的显示条件、默认值、空值处理、数据来源？
- 涉及参数时，参数路径、默认值、取值范围？
- 知识库与需求描述是否一致？不一致时以知识库为准并说明差异

**实现状态判断（基于知识库）**：

| 状态 | 判断依据 | 后续动作 |
|------|---------|---------|
| 知识库已有完整功能 | Spec 文档中已有需求描述的全部功能 | 停止分析，报告知识库位置 |
| 参数配置可解决 | 知识库或参数资料中已有对应参数可控制该行为 | 标注参数方案，停止分析 |
| 部分实现 | 知识库中实现了部分功能 | 标注已完成部分，分析增量 |
| 未实现 | 知识库中未找到相关功能 | 继续后续分析 |
| 知识库有参考 | 知识库中有相似功能可参考 | 标注参考位置，继续分析增量 |

#### 参数查询

**触发条件**：需求涉及参数、配置开关、默认值、院区差异化、兼容旧行为兜底时。查询前读取 `references/parameter-reading.md`。

**参数查询路径**：
1. 优先查询 `references/Param/` 下的 CSV 参数资料
2. 其次查询 `Knowledge/` 中涉及参数配置的 Spec 文档
3. 仍无法确认 → 记录到 `notes.md`：`【待确认】参数路径`

**结论写法**：只写业务信息。参数路径基于知识库和参数资料中的既有路径层级，不得按业务模块归属或菜单名称编造。

### 4. Brainstorming 业务分析

> **简单需求跳过**：当 `System.Tags` 包含"简单需求"时，跳过本步骤（R15），直接进入步骤 5。

优先调用 `superpowers:brainstorming`，传入需求原文、知识库核查结果、附件摘要，明确告知"这是需求分析任务，目标是确保业务规则无遗漏、识别边界条件和兼容性风险，不涉及代码架构设计"。调用示例：
```
需求分析任务。
需求原文：[粘贴 System.Title + System.Description]
知识库核查结果：[粘贴关键知识库文件路径和实现状态]
附件摘要：[粘贴附件内容摘要]
目标：确保业务规则无遗漏、识别隐含边界条件和兼容性风险。不涉及代码架构设计。
```
不可用时回退结构化提问。

**结构化提问三个维度**：
- **业务意图**：解决什么问题？用户场景？现状 vs 期望？
- **边界条件**：特殊处理？角色差异？数据权限？批量操作？
- **基于知识库的追问**：知识库已有类似功能 → 差异？参数可控制 → 配置方案？

**提问策略**：每次只问一个问题，等用户回答后再问下一个。不问纯技术问题，聚焦业务规则和用户场景。

**产出**：业务规则清单、边界场景列表、待澄清问题。

**澄清不确定项**：遇到以下情况必须向用户确认：
- 需求描述模糊、存在歧义，无法确定业务意图
- 需求中提到的功能/参数/字段在知识库中都找不到对应
- 需求描述与知识库功能清单或前置需求冲突
- 业务规则缺少关键条件、分支、口径或角色范围
- 前置需求、附件、图片无法获取或不清晰

**用户确认前**：不生成正式 `产品业务分析.md`，不回写 `Winning.Demand.Analysis`，不上传临时澄清稿。

### 5. 兼容性和方案边界

涉及会诊计费或病历审签流程时，必须特别关注兼容性风险和边界条件。

**快速判断**：纯新增字段/按钮/列、不影响现有逻辑和数据的变更，可直接得出"无兼容性影响"结论，不需要逐项分析。

**需要深入分析时**，必须回答并转成可执行、可验收的结论（不要把"是否影响…"这类问题原样堆进正文）：
- 现有行为 vs 目标行为
- 是否影响其他医院/院区/角色/旧版本/历史数据
- 是否有参数/配置可复用
- 是否需新增参数、权限、字段、入口；默认值如何保持旧行为
- 冲突时：新增内容/参数/入口 vs 调整原逻辑
- 风险点和规避方案

**界面类需求补充**：页面入口/区域、字段清单（中文名、数据来源、显示条件、空值处理、排序/格式化口径）、按钮/操作清单（触发条件、动作、权限、禁用规则）、新旧入口对比、验收可测对应。

**多产品线**：病案变更不得影响病历，反之亦然。共享组件修改必须确认两个产品线不受影响。**新增参数默认值必须保持所有产品线的旧行为**。

### 6. 质量检查（不可跳过）

> ⚠️ **本步骤为强制步骤，不得跳过。**
>
> **简单需求快速通道**：当 `System.Tags` 包含"简单需求"时，跳过 `autoplan` 深度评审（R15），直接使用增强自检。

**前置**：进入深度评审前，brainstorming 和澄清阶段的所有待确认问题必须已获得用户明确答复。不得携带待确认进入评审。

**深度评审**（简单需求时跳过）：调用 `gstack-autoplan` skill，传入以下内容：
```
仅评审以下产品业务分析草案的业务完整性和一致性，不涉及代码仓库操作，不检查 git 状态。

需求原文：[粘贴 System.Title + System.Description]
知识库核查摘要：[关键知识库文件路径和实现状态]
brainstorming 输出：[业务规则清单和边界场景]
产品业务分析草案：[粘贴完整 Markdown 正文]
```
评审结果处理：机械性问题直接修复，品味性问题记录后通过，需用户确认的问题禁止出现（应在评审前已全部确认）。最多迭代 3 次。

增强自检必检项：业务流程完整、每个规则有触发条件和处理逻辑、异常场景有方案、角色和权限明确、是否有遗漏的用户场景、兼容性风险已记录、参数默认值是否保持旧行为、是否误把附件下载路径/工具日志/过程记录写入正文。

**加分项**：是否考虑了批量操作场景？数据生命周期是否明确？是否与其他功能有交互影响？

**发现待确认项时**：形成编号问题清单逐项向用户澄清，**优先一次只问 1-3 个最阻塞的问题**。确认后更新 Markdown 并**以 Markdown 为源稿重新回写**，不得只上传附件。用户无法确认且影响方案/边界/测试用例判断时停止，不回写。深度评审**默认最多一轮**，除非发现明确业务结论错误。

### 7. 生成正文

使用 `assets/product-business-analysis-template.md` 模板生成。正文不得含待确认表述（R13）。

**写作风格**：先总后分，前半部分让产品、研发、测试快速核对方向，后半部分承载设计细节、现状依据和影响范围。

**回写顺序**：记录 `CollectionHint` → Markdown 转 HTML 写入 → 回写后重新读取确认无乱码 → 附件上传后置且只上传一次 → 严禁因长度限制生成"精简版"。

**源稿结构**：

**第 1 章"背景"**：`1.1 业务诉求`（一句话，格式：客户希望[做什么]，以解决[什么问题]）、`1.2 业务现状`（一句话，格式：当前系统[状态]）。

**第 2 章"产品设计"**：标题下先写 `核心功能：` 一句话概括。`🔴 2.1 功能新增或修改`（**层级结构**：`**主题N：XXX**` 粗体引导 + 列表展开，禁止用平铺表格；变更说明不体现代码逻辑）、`🔴 2.2 原型设计`（有原型时输出，列出字段变更明细）、`🔴 2.3 参数配置`（涉及参数时输出，**必须用列表形式，禁止用表格**）、`2.4 操作流程`（概要文本箭头 + 详细编号列表。当业务流程简单的则只需要概要文本箭头部分，不需要显示详细编号列表）。

**2.1 层级化书写规则**：
- **必须层级化**：每个改造主题用 `**主题N：XXX**` 粗体引导（仅主题这一行加粗），下方用列表展开变更点；禁止用 4 列表格（`| 类型 | 功能描述 | 涉及模块 | 变更说明 |`）平铺。
- **切分依据**：按功能模块、业务流程、改造目标划分主题（如"病历辅助区数据展示"、"质控流程调整"、"权限校验加强"），不要按"新增/修改/优化"动词切分。
- **内容边界**：变更点只写"要做什么改动"——具体的程序改造动作（新增什么逻辑/修改什么校验/接入什么能力/调整什么代码默认值）。禁止夹带现状（归 1.2）、夹带效果（归 3 测试用例）、夹带操作步骤（归 2.4）。
- **加粗节制**：仅主题引导行加粗；变更点不要把引导词加粗成小标题（如 `- **关闭XX参数**：`、`- **效果**：` 都是错误的），改为在描述句中加粗真正的关键对象/动作对象。
- **颗粒度上限**：2.1 合计 ≤ 8 条变更点；简单需求（≤2 个程序改动点）直接用列表展开，不强行分主题。

**变通方案书写规则（非强制但必须具体）**：
- **核心原则——变通思考**：客户诉求基于客户视角，不等于最终方案。当知识库已有功能、参数配置或相似需求方案能部分或完全覆盖客户诉求时，鼓励给出推荐方案或变通方案，作为产品思考的方向参考。变通方案非强制、非必须采用，但一旦写出**必须具体**。
- **必须具体**：明确复用哪个现有功能/参数/相似需求方案，并说明差异点和取舍理由；禁止"可以考虑复用""可探索变通"等空泛表述。
- **优先级参考**：复用知识库已有功能 > 参数配置 > 相似需求方案 > 新增开发（用于判断是否值得写变通方案，不是硬性规则）。
- **无变通空间**：客户诉求即为最优方案时，正文按推荐方案直接展开，不写"已评估无更优方案"等空话。

**重点文字加粗规则（全篇适用，节制使用）**：
- **加粗节制使用**：只在真正关键的信息上加粗。**不强制每段都有加粗**——没有真正关键信息时就不加粗。
- **加粗位置**：在描述句中加粗，覆盖 1.1/1.2、2 核心功能、2.1 主题描述、测试用例等所有正文：
  - 关键改造对象（字段/按钮/入口/菜单/页面/状态/参数/校验规则）
  - 关键业务效果（如"**标签页自动隐藏**""**阻断提交**""**默认置灰**"）
  - 关键业务规则（如"**未签署不返回**""**超过3次锁定**"）
  - 关键代码值（如文档类型代码、参数编码、状态码）
- **禁止加粗**：
  - **章节标题或引导词**：如"推荐方案："、"核心功能："、"2 功能新增或修改"、"产品分析概述"等标签词
  - **变更点小标题式引导词**：如 `- **关闭XX参数**：`、`- **效果**：`、`- **新增XX**：`、`- **优化XX**：`
  - 整句、整段、连接性描述、情感性强调（如"非常重要"、"务必"）
- **颗粒度**：一次加粗控制在 4-15 字之间；一句话最多 2-3 处加粗。

**2.3 参数配置规则**：每个参数前必须标注**序号**和**类型**（新增/已有/修改），让多个参数能并列呈现。**参数编码字段规则**——新增参数去掉参数编码字段（系统内置规则会自动生成，无需手动定义；也避免凭空给"建议编码"造成误导）；**已有/修改参数保留参数编码**（写业务可见的编码，如 `settingType`，不写代码常量名）。每个参数包含：序号+类型+参数名称（粗体引导，如 `**1. 新增 参数名称：XXX**`）、参数编码（仅已有/修改参数）、参数路径、当前默认值（已有/修改参数）、建议值/建议默认值（新增/修改参数）、说明。详见 `assets/product-business-analysis-template.md` 的 2.3 章节。

**第 3 章"测试用例"**：表格（用例编号、角色、场景、操作步骤、预期结果、优先级）。

**第 4 章"关联说明"**：`4.1 前置需求`（表格）。

**第 5 章"兼容性与风险"**（条件章节）：仅当存在**实际的**兼容性影响或风险时输出。"不影响"、"无影响"等结论不算实质内容，不得输出。只有确认存在影响（如"影响XX角色"、"需新增参数"）或存在风险点时，才保留该章节及对应条目。

**禁止事项**：不得随意增删章节或改变顺序；不得新增"验收标准"等模板中不存在的章节；不得输出"参数分析过程"等分析过程记录；测试用例不得写"正常显示、符合要求"等泛化句；条件章节无实质内容时删除；没有实质内容的章节、空表格、仅写"无/无需新增/无明确"的条件章节必须删除。

**明确不输出的内容**：不单独输出"新旧口径对比"（并入 2.1 变更说明）；不单独输出"关联说明"独立章节（模板 §4 仅为前置需求列表）；不输出分析过程（附件下载日志只写入 `notes.md`）；不输出工具日志和报错信息（乱码排查、下载失败只写入 `notes.md`）；不输出图片（图片解读结论写入正文，图片本身不嵌入）。

**界面类需求**：逐页面列出字段/按钮变更明细、操作清单、权限变化与测试用例对应。
