# 阶段5: 生成设计文档

## 设计思路：API-First

文档生成遵循 **API-First** 原则：先确认需求分析，再定义 API 契约作为前后端的"桥梁"，最后前端和后端设计文档都基于这份契约来生成。这确保前后端对接口的理解从一开始就一致，减少后续对不上的问题。

### 元信息

- **前置条件**: 阶段1-4已完成（简单需求时阶段4可能被跳过）
- **触发条件**: 自动执行（上一阶段完成后进入）
- **预计耗时**: 3-10 分钟（简单需求偏短，复杂需求含确认环节偏长）

### 输入

- 阶段2的需求数据
- 阶段3的代码扫描摘要
- 阶段4的 `brainstorm-notes.md`（简单模式下由代码扫描结果推断）
- `state.json` 中的 `changeScope` 决定生成哪些文档，`complexity` 决定是否需要用户确认
- `state.json` 中的 `hasProductAnalysis` 决定需求分析来源，`productAnalysisFile` 指定替代文件

### 执行步骤

---

## 输入源切换（根据 hasProductAnalysis）

进入阶段 5 前，检查 `state.json` 的 `hasProductAnalysis` 字段：

**`hasProductAnalysis === true`（有产品分析）：**
- 需求分析的来源 = `产品业务分析.md`（读取 `state.json.productAnalysisFile` 指定的文件）
- **不生成** `需求分析.md` 文件
- 直接从 `产品业务分析.md` 中提取：功能范围、字段变更、影响模块、业务规则
- 将提取的信息作为 API 契约、前后端设计的输入依据
- 后续流程不变：API 契约 → 前端设计 ↔ 后端设计 → 测试文档 → 一致性校验

**`hasProductAnalysis === false`（无产品分析）：**
- 执行现有完整流程不变
- 正常生成 `需求分析.md` → API 契约 → 前后端设计 → 测试文档

---

## 简单需求流程（`complexity === "simple"`）

所有文档连续生成，无需用户确认：

生成顺序：
1. **需求分析**（单独生成）
2. **API 契约**（如需生成，基于需求分析）
3. **前端设计 ↔ 后端设计**（强制并行：当两者都需要生成时，使用 Agent 工具并行生成，在一条消息中发出两个 Agent 调用；**必须基于 API 契约中的接口定义来设计**）
4. **测试功能文档**（基于前面所有文档生成）
5. **一致性校验** → 直接进入阶段6

---

## 复杂需求流程（`complexity === "complex"`）

分三批生成，中间有两次用户确认环节：

### 第一批：需求分析

1. **需求分析**（单独生成）
2. 进入 5.5a 用户确认环节，确认需求理解无误后再生成后续文档。

### 第二批：API 契约

用户确认需求分析后：
1. **API 契约**（如需生成，基于已确认的需求分析）
2. 进入 5.5b 用户确认环节，确认接口设计无误后再生成前后端设计。

### 第三批：前后端设计

用户确认 API 契约后：
1. **前端设计 ↔ 后端设计**（强制并行：当两者都需要生成时，使用 Agent 工具并行生成，在一条消息中发出两个 Agent 调用；**必须基于已确认的 API 契约中的接口定义来设计**）
2. **测试功能文档**（基于前面所有文档生成）
3. 执行 **一致性校验**
4. 完成后进入阶段6。

#### 5.1 需求分析文档（条件生成）

> **条件：** 如果 `hasProductAnalysis === true`，跳过此文档的生成，用 `产品业务分析.md` 替代。后续 5.2-5.4 中引用"需求分析"的地方，改为引用 `产品业务分析.md` 的内容。

**文件名：** `需求分析.md`
**模板：** 读取 `references/requirement-analysis-template.md`

包含：
- 需求概述和背景
- 功能点拆解（每个功能点有明确的输入、输出和验收标准）
- 非功能性需求（性能、安全、兼容性）
- 需求依赖关系图
- 风险识别和应对策略

#### 5.2 API 契约文档（条件生成）

> **条件：** 如果判定不涉及 API 变更，跳过此文档。

**文件名：** `API契约.md`
**模板：** 读取 `references/api-contract-template.md`

在需求分析确认后、前后端设计之前生成，作为前后端协作的"唯一真相源"：
- 接口地址和 HTTP 方法
- 请求参数的 TypeScript interface 定义
- 响应数据的 TypeScript interface 定义
- 错误码定义
- 分页、排序等通用参数约定

> 为什么 API 契约要先于前后端设计？因为接口是前后端的"桥梁"——先定义好接口契约，前端知道该调什么接口、传什么参数，后端知道该实现什么接口、返回什么格式。这样生成的两份设计文档天然对齐，不需要后期再补齐或修正。

#### 5.3 前端设计文档（条件生成）

> **条件：** 如果判定无需前端改动，跳过此文档。

**文件名：** `前端设计.md`
**模板：** 读取 `references/frontend-design-template.md`

**必须基于已生成的 API 契约** 中的接口定义来设计前端调用层，确保：
- API 调用的 URL、方法、参数、返回值与 `API契约.md` 完全一致
- TypeScript interface 直接引用 API 契约中的定义

**WinDesign 组件文档加载策略（按需加载，避免上下文膨胀）：**
> 1. **默认使用精简版**：读取 `references/win-design-next-summary.md`（~12KB），包含设计规范、CSS 变量、高频组件用法和典型布局模式
> 2. **按需加载组件详细 API**：仅当设计特定组件时需要完整 props/events/slots，读取 `references/wd-components/` 目录下对应的组件文件（如 `table.md`、`form-input.md`）。索引表在精简版末尾「组件详细 API 文件索引」章节
> 3. `references/win-design-next-docs.md` 已删除（原 1.3MB / 36879 行），不要尝试读取

基于 WinDesign 3.0 (win-design-next) 组件库和 Vue 3 Composition API 风格进行设计：
- 页面/组件结构图（使用 `w-` 前缀组件）
- 新增和修改的组件清单
- 路由配置变更（Vue Router 4）
- 状态管理设计（Pinia）
- 组件间数据流
- TypeScript 类型定义

> 前端设计必须基于 WinDesign 3.0 设计规范：
> - 主题色 `#2d5afa`，CSS 变量 `--w3-color-primary`
> - 组件使用 `w-` 前缀
> - 设计稿标准 1920x1080px，最小适配 1366x768px
> - 使用 `<script setup lang="ts">` Composition API 风格

#### 5.4 后端设计文档（条件生成）

> **条件：** 如果判定无需后端改动，跳过此文档。

**文件名：** `后端设计.md`
**模板：** 读取 `references/backend-design-template.md`

**必须基于已生成的 API 契约** 中的接口定义来设计后端接口层，确保：
- Controller 端点的路径、方法、参数、返回值与 `API契约.md` 完全一致
- DTO/VO 的字段定义与 API 契约中的 TypeScript interface 对齐

基于项目现有的 Spring Boot 模式，设计：
- Controller 层 API 端点定义
- Service 层业务逻辑设计
- 数据模型（Entity/DTO/VO）设计
- 数据库表结构变更
- 中间件使用

#### 5.5 用户确认环节（仅复杂需求）

> **简单需求跳过此环节。** 仅当 `state.json` 中 `complexity === "complex"` 时执行。

##### 5.5a 需求分析确认（第一批文档后）

在需求分析文档生成后，向用户展示摘要并等待确认。

1. **展示需求摘要**：向用户展示需求分析的核心功能点、验收标准和风险识别
2. **使用 `AskUserQuestion` 确认**：
   - 问题："以上是需求分析的摘要，请确认需求理解是否正确："
   - 选项：
     - `确认无误，继续生成 API 契约` — 进入第二批文档生成
     - `需求理解需要调整` — 用户说明修改意见，修改需求分析后重新确认

##### 5.5b API 契约确认（第二批文档后）

在 API 契约文档生成后，向用户展示接口设计摘要并等待确认。

1. **展示接口摘要**：向用户展示 API 契约中的关键接口列表、数据结构定义
2. **使用 `AskUserQuestion` 确认**：
   - 问题："以上是 API 契约的摘要，确认后将为前后端设计提供接口基准："
   - 选项：
     - `确认无误，继续生成前后端设计` — 进入第三批文档生成
     - `接口设计需要调整` — 用户说明修改意见，修改 API 契约后重新确认

### 修改规则

- 每次修改后重新展示变更部分的摘要
- 修改只影响用户指定的文档，不影响其他已生成的文档
- 反复迭代直到用户确认无误

---

#### 5.6 测试功能文档（强制生成）

**文件名：** `测试功能文档.md`
**模板：** 读取 `references/test-function-template.md`

在所有设计文档（需求分析 + API 契约 + 前端设计 + 后端设计）完成后生成：

1. 读取 `需求分析.md` 中的功能点列表和验收标准
2. 如有 `API契约.md`，提取所有接口定义用于生成 API 测试用例
3. 如有 `前端设计.md`，提取页面组件和交互逻辑用于生成 UI 测试用例
4. 如有 `后端设计.md`，提取业务规则和数据模型用于生成接口和集成测试用例
5. 读取模板 `references/test-function-template.md`
6. 生成 `测试功能文档.md`

**测试文档必须覆盖：**
- 每个功能点至少 1 个正向用例 + 1 个异常/边界用例
- 每个 API 接口至少 1 个正向 + 1 个参数校验 + 1 个权限测试用例
- 端到端业务流程的集成测试场景
- 修改影响范围内的回归测试要点
- 测试数据准备清单

#### 5.7 前后端设计一致性校验

> **条件：** 当同时生成了前端设计 + 后端设计 + API 契约时执行。否则跳过。

在所有文档生成完毕后，进行交叉一致性校验。由于前后端设计已经基于同一份 API 契约生成，理论上已经对齐，此处校验作为最终兜底。

### 校验项

| 校验维度 | 检查内容 |
|---------|---------|
| **API 路径一致性** | 前端 API 调用层的 URL 与 API 契约、后端 Controller 的路径是否一一对应 |
| **请求类型匹配** | 前端调用方法（GET/POST/PUT/DELETE）与 API 契约、后端端点是否一致 |
| **字段名对齐** | 前端 TypeScript interface 的字段名与后端 DTO/VO 的字段名（camelCase）是否对齐 |
| **数据类型匹配** | 前端类型（string/number/boolean）与后端类型（String/Integer/Boolean）是否兼容 |
| **枚举值一致** | 前端和后端使用的枚举值是否完全匹配 |

### 不一致处理

- **自动修正**：字段命名风格差异（snake_case vs camelCase）→ 自动统一为 camelCase
- **自动修正**：接口路径不匹配、缺少接口定义 → 基于已确认的 API 契约自动补齐

### 校验报告

将校验结果追加到 `brainstorm-notes.md`：
```markdown
## 设计一致性校验
- 校验通过: N 个接口
- 自动修正: N 处（列举）
```

### 输出

- `需求分析.md`（`hasProductAnalysis === false` 时始终生成；`hasProductAnalysis === true` 时不生成，用 `产品业务分析.md` 替代）
- `API契约.md`（`changeScope.api === true` 时生成）
- `前端设计.md`（`changeScope.frontend === true` 时生成）
- `后端设计.md`（`changeScope.backend === true` 时生成）
- `测试功能文档.md`（始终生成）

**输出数据契约（阶段6/7 依赖的字段）：**

各文档必须包含的章节（阶段6读取这些章节转化为 Task）：

| 文件 | 阶段6依赖的章节 | 阶段7依赖的章节 |
|------|----------------|----------------|
| `需求分析.md` | 二、功能点拆解（验收标准） | 全文上传到 TFS |
| `API契约.md` | 二、接口定义（每个接口的路径、方法、参数、响应） | 作为附件上传 |
| `前端设计.md` | 二、页面/组件结构 + 六、组件详细设计（文件路径、代码片段） | 作为附件上传 |
| `后端设计.md` | 二、API端点设计 + 四、数据模型设计（Entity/DTO/VO） | 作为附件上传 |
| `测试功能文档.md` | 二、功能测试用例 + 五、集成测试场景 | 作为附件上传 |

**前端设计.md 关键字段契约（阶段6精准定位文件）：**
- 每个组件必须标注 `文件路径: src/...` 格式的确切路径
- 每个路由变更必须标注 `path` 和 `name`
- Store 变更必须标注 `stores/xxx.ts` 路径

**后端设计.md 关键字段契约（阶段6精准定位文件）：**
- 每个接口必须标注 Controller 类名和请求路径
- 每个 Entity/DTO/VO 必须标注完整包路径和类名
- 数据库变更必须标注表名和 SQL 语句

### 异常处理

| 场景 | 处理方式 |
|------|---------|
| 设计模板文件读取失败 | 使用内置的章节结构直接生成，不依赖模板文件 |
| 前后端设计一致性校验发现矛盾 | 基于已确认的 API 契约自动修正，记录修正日志到 brainstorm-notes.md |
| WinDesign 组件文档不完整 | 使用精简版 summary + 通用组件映射表，不阻塞设计 |
| 用户确认环节反复修改超过 3 轮 | 提示用户考虑回到 brainstorm 阶段重新分析 |
