# 需求分析核心规则

本文档定义了医疗信息系统（病案、病历）需求分析过程中必须遵循的核心规则，融合了 v1.x 系列的 R1-R12 规则和优先级体系。

---

## Rule 1: 需求规划流程（最高优先级）

> ⚠️ **重要**：所有需求统一执行完整分析流程，不做复杂度分流。

### 规划流程

1. 使用 `superpowers:brainstorming` 做深度分析，形成已确认范围、待确认问题、原型目标和交互边界
2. 使用 `superpowers:writing-plans` 生成实施/原型调整计划
3. 按照规划好的步骤逐步执行

---

## Rule 2: TFS MCP 不可用即停止（最高优先级）

TFS MCP 不可用或 PAT 无效时，必须立即终止分析流程。明确提示当前会话 TFS MCP 未配置或不可用，不改用 TFS Web、未认证脚本、旧文件或用户临时材料继续分析。

---

## Rule 3: 代码搜索优先（最高优先级）

**核心要求**：分析前必须先验证代码是否已实现。

- 如果发现代码中已实现（无论是代码实现还是通过参数配置），立刻停止分析，并告诉用户需求在哪些代码中已实现
- 代码是最终权威，文档仅供参考

**处理流程**：
1. 执行代码搜索
2. 发现已实现 → 停止分析，报告代码位置
3. 未发现实现 → 继续分析流程

---

## Rule 4: TFS 集合一致（高优先级）

同一需求全程使用同一 TFS 集合/`collectionHint`：读取、附件下载、图片处理、正文回写、标签追加、附件上传和任务创建必须一致。

---

## Rule 5: 产品线判断规则（高优先级）

产品线只根据 `Winning.Product.Name` 判断：病案用 `medicalArchive`，病历用 `medicalRecord`；不得用标题、描述或区域路径推断。无法判断时使用 `defaultProduct` 配置值。若 `System.Tags` 包含"新会诊"则使用 `newConsultationV2` 配置节点。

---

## Rule 6: 兼容性原则（高优先级）

**核心要求**：针对原逻辑的变更，要注意兼容。

- 不能直接改写原来设计的逻辑（除非明确告知改写）
- 不能为了单个医院直接改变其他医院、院区、角色、旧版本、历史数据或既有流程
- 优先扫描是否已存在对应的参数或配置来保持兼容
- 新增参数默认值要保持旧行为
- 新增字段前检查 PO/Entity/DTO、表字段和业务实体资料，能复用就复用
- 冲突场景优先参数、配置、字典、权限或新增独立入口

---

## Rule 7: 以代码为准（高优先级）

代码与文档冲突时，以当前代码和配置实现为事实基础，再说明差异。要直接询问确认后，再进行工作。

---

## Rule 8: 有图必处理（中优先级）

- 描述或相关工作项中出现 `<img>`、图片、附件、`FileNameGuid`、`_apis/wit/attachments` 时，必须下载或保留线索，并在正文生成前读取图片内容；未读图不得写"已处理图片"
- 附件清单为 0 时仍要检查正文中的 `<img>` 和图片链接
- 解读界面图时至少提取入口位置、区域名称、字段/按钮、权限差异、默认值/空态
- 看不清的内容写成待确认问题，不要凭猜测补成确定方案
- 图片不应出现在最终的需求分析报告正文中

---

## Rule 9: 前置/参见需求处理（中优先级）

如果需要分析的需求中有写明前置需求或者参见需求，要从 TFS 上重新获取。前置/参见需求、父子项或相关 Bug 里的图片也要按同样方式处理。

---

## Rule 10: 正文纯净（中优先级）

`Winning.Demand.Analysis` 和最终汇报只写业务结论、功能设计、原型字段变更明细、必要影响范围、待确认问题和测试用例；工具日志、代码路径清单、下载过程、乱码排查、接口报错只写入 `notes.md`。

---

## Rule 11: 正文不得含待确认（中优先级）

- 需求分析正文中不得出现"待确认"、"待讨论"、"需确认"、"待明确"、"TBD"等不确定表述
- 所有待确认问题必须在正文生成前向用户逐项澄清
- 用户无法确认且该问题影响方案、边界或测试用例判断时，停止在草案阶段
- 经用户同意后可以"待确认"标记在正文中留档的例外场景，需记录到 `notes.md`

---

## Rule 12: 源稿回写（中优先级）

默认以 UTF-8 `产品业务分析.md` 作为唯一源稿，通过 TFS MCP 文件路径回写能力或专用脚本转换 HTML 并写入；每次修改 Markdown 后，必须重新从该 Markdown 回写 `Winning.Demand.Analysis`，不得只更新附件或使用旧的硬编码 HTML。

---

## Rule 13: 附件版本治理（低优先级）

同一轮最终版 `产品业务分析.md` 只保留一份；评审后只做回写同步、排版修正、表头/格式微调或未证实的修订时，不得再次上传附件。确有业务内容变更需要更新附件时，优先覆盖同名附件，并在附件注释中写清真实业务变更原因。

---

## Rule 14: 深度评审限范围（低优先级）

深度评审只评审产品业务分析草案、需求原文摘要、关键附件结论和代码定位摘要，不重新做全仓库代码探索、不重新下载附件、不生成研发计划，默认最多一轮。

---

## Rule 15: Brainstorming 提问策略（低优先级）

- 每次只问一个问题，等用户回答后再问下一个
- 不问代码架构、服务层设计、数据库设计等纯技术问题
- 追问聚焦在业务规则和用户场景

---

## Rule 16: 历史痕迹隔离（低优先级）

严禁复用本地 `.ai-work/` 或工程目录下的旧源稿、旧正文或旧过程记录作为分析依据。每次分析新建带时间戳的运行目录。

---

## Rule 17: 相似需求来源识别（中优先级）

除工作项关联（`related`/`predecessor`/`successor`）外，还要从注释/讨论区识别相似需求：

- `【相似需求清单】` 标题 + 紧随其后的 `相似需求ID：<逗号分隔的7位ID列表>` 行（为主体相似需求来源）
- `【同机构相关需求清单】`（为同机构补充参考来源）

**准入条件**：相似需求必须同时满足 `System.State` ∈ {`已解决`，`已关闭`，`已验证`}，且 `ResolvedDate` ≠ `ClosedDate`（含时分秒完整比较）。不满足的只作背景参考。

**内容读取**：通过准入的相似需求必须读取其 `System.Description`、`Winning.Demand.Analysis` 和附件，作为推荐方案/变通方案的参考依据。

**禁止臆造**：不得凭相似标题自行编造历史需求号；只有当前需求描述、工作项关系、相似需求来源或 TFS 查询结果明确返回某个历史需求号时，才能引用。

---

## Rule 18: 变通方案书写规则（中优先级）

**核心原则——变通思考**：客户诉求基于客户视角，不等于最终方案。当代码已有功能、参数配置或相似需求方案能部分或完全覆盖客户诉求时，鼓励给出推荐方案或变通方案。

- **非强制非必须**：变通方案是供产品思考的方向参考，不强制给出，也不强制采用。
- **必须具体**：一旦写出，必须明确复用哪个现有功能/参数/相似需求方案，并说明差异点和取舍理由。
- **禁止空泛**：不得出现"可以考虑复用""可探索变通""建议产品评估"等无具体指向的措辞。
- **无变通空间**：客户诉求即为最优方案时，正文按推荐方案直接展开，不写"已评估无更优方案"等空话。

---

## Rule 19: 重点文字加粗节制（低优先级）

正文加粗节制使用，不强制每段都有加粗。

- **加粗位置**：在描述句中加粗关键改造对象（字段/按钮/入口/菜单/页面/状态/参数/校验规则/接口名）、关键业务效果（如"标签页自动隐藏"、"阻断提交"）、关键业务规则（如"未签署不返回"）、关键代码值（如文档类型代码、参数编码）。
- **禁止加粗**：章节标题或引导词（如"推荐方案："、"核心功能："）、变更点小标题式引导词（如 `- **关闭XX参数**：`、`- **效果**：`）、整句整段、情感性强调。
- **颗粒度**：一次加粗控制在 4-15 字之间；一句话最多 2-3 处加粗；没有真正关键信息时就不加粗。

---

## 规则优先级

| 规则 | 优先级 | 说明 |
|------|--------|------|
| Rule 1 | 最高 | 所有需求统一执行完整规划流程 |
| Rule 2 | 最高 | TFS MCP 不可用即停止 |
| Rule 3 | 最高 | 代码搜索优先，发现已实现立即停止 |
| Rule 4 | 高 | TFS 集合一致 |
| Rule 5 | 高 | 产品线判断规则 |
| Rule 6 | 高 | 兼容性原则，影响设计决策 |
| Rule 7 | 高 | 以代码为准，解决冲突 |
| Rule 8 | 中 | 有图必处理 |
| Rule 9 | 中 | 前置/参见需求处理 |
| Rule 10 | 中 | 正文纯净 |
| Rule 11 | 中 | 正文不得含待确认 |
| Rule 12 | 中 | 源稿回写 |
| Rule 13 | 低 | 附件版本治理 |
| Rule 14 | 低 | 深度评审限范围 |
| Rule 15 | 低 | Brainstorming 提问策略 |
| Rule 16 | 低 | 历史痕迹隔离 |
| Rule 17 | 中 | 相似需求来源识别 |
| Rule 18 | 中 | 变通方案书写规则 |
| Rule 19 | 低 | 重点文字加粗节制 |

---

## 规则应用检查清单

在需求分析过程中，按以下顺序检查规则应用：

- [ ] **Rule 1**: 已执行完整规划流程
- [ ] **Rule 2**: 已确认 TFS MCP 可用或 PAT 有效
- [ ] **Rule 3**: 已执行代码搜索，确认是否已实现
- [ ] **Rule 4**: 已使用同一 TFS 集合
- [ ] **Rule 5**: 已正确识别产品线
- [ ] **Rule 6**: 已考虑兼容性，优先使用现有配置
- [ ] **Rule 7**: 已以代码为准处理冲突（如有）
- [ ] **Rule 8**: 已处理所有图片和附件
- [ ] **Rule 9**: 已处理前置/参见需求（如有）
- [ ] **Rule 10**: 正文无工具日志和代码路径清单
- [ ] **Rule 11**: 正文无待确认表述
- [ ] **Rule 12**: 已从 Markdown 源稿回写
- [ ] **Rule 13**: 附件只上传一次
- [ ] **Rule 14**: 深度评审未越界
- [ ] **Rule 15**: 提问策略正确
- [ ] **Rule 16**: 未复用历史文件
- [ ] **Rule 17**: 已识别并读取准入的相似需求
- [ ] **Rule 18**: 变通方案具体（明确复用对象+差异点），或无变通空间已直接展开
- [ ] **Rule 19**: 加粗节制使用，未加粗引导词或整句
