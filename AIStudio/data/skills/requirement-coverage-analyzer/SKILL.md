# Requirement Coverage Analyzer

需求覆盖率分析技能，自动评估需求与代码的匹配情况。

## 🎯 使用时机

当用户需要：
- 检查需求是否已正确实现
- 分析需求与代码的业务逻辑匹配度
- 评估需求相关代码的质量风险
- 生成需求覆盖率报告

## 📋 分析流程

### 输入参数
\`\`\`
分析需求 <需求ID>
仓库根目录: <本地路径>  // 首次使用需要配置
\`\`\`

### 自动执行步骤
1. 从 TFS 获取需求详情和子工作项
2. 获取需求分析内容（预存文件/TFS字段/LLM生成）
3. 获取所有关联的代码提交记录
4. 自动发现匹配的本地仓库
5. 用 git 命令提取代码变更内容
6. 从代码中提取业务逻辑实现
7. **LLM 语义匹配分析**（见下方详细说明）
8. 计算多维度匹配度评分
9. 扫描代码质量问题
10. 生成报告（终端+文件）

### 步骤7: LLM 语义匹配分析

工具会生成一个临时分析文件 `/tmp/requirement-analysis-input-{id}.json`，包含：
- 需求描述和业务要点
- 代码分析结果（函数、数据模型、API、业务规则）

**执行此步骤时，你需要：**
1. 读取分析输入文件
2. 分析需求与代码的语义匹配关系
3. 将分析结果写入 `/tmp/requirement-analysis-result-{id}.json`

**输出格式：**
```json
{
  "requirementId": "1386876",
  "matches": [
    {
      "requirement": "悬浮窗添加支付上限字段",
      "implementation": "PayLimitDTO.payLimit 字段",
      "status": "implemented",
      "confidence": "high",
      "evidence": "EncounterListQueryOutputDTO 中新增了 payLimit 相关字段"
    }
  ],
  "unmatched": [
    {
      "requirement": "检查检验项目悬浮窗参数配置",
      "reason": "未找到对应的配置项代码",
      "suggestion": "可能在前端配置文件中"
    }
  ],
  "score": 75,
  "summary": "需求核心功能已实现，支付上限字段已添加到多个DTO中..."
}
```

### 输出结果
- 终端实时分析进度
- Markdown/Excel 报告文件

## 🔧 首次配置

首次使用需要配置仓库根目录：

\`\`\`bash
# 编辑配置文件
vim config/default.json

# 设置仓库根目录
"repos_root_dir": "/path/to/your/repos"
\`\`\`

## 📊 评分维度

| 维度 | 权重 | 说明 |
|------|------|------|
| **业务逻辑匹配度** | 35% | 业务规则、流程、约束、映射、边界情况匹配 |
| **功能覆盖度** | 20% | 动词、实体、字段关键词匹配 |
| **代码质量** | 20% | 基于扫描规则的代码质量评分 |
| **测试完整性** | 15% | 测试文件、覆盖率 |
| **代码规模** | 10% | 代码规模合理性 |

## 🛠️ 工具依赖

- \`../tfs2018-integration\` - TFS 数据获取
- \`../win-code-scanner\` - 代码扫描规则
- \`git\` - 本地代码变更提取

## 🔧 集合选择规则

当从 TFS 查询工作项时，如果工作项 ID 在多个集合中存在：

- **默认选择 WINNING-6.0 集合**
- 如需查询其他集合，请明确指定集合名称

## 📝 使用示例

\`\`\`bash
# 分析单个需求
node tools/main.mjs analyze 123456

# 指定仓库目录
node tools/main.mjs analyze 123456 --repos-dir /data/git-repos

# 生成 Excel 报告
node tools/main.mjs analyze 123456 --format excel
\`\`\`
