# 判定规则（rational-design-v1 第二章）

> 本文件定义问题点级与功能点级的判定方法。第二章写作时必须遵循本文件。

## 一、严重等级

| 等级 | 含义 | 典型特征 |
|------|------|---------|
| 🔴 不合理 | 必须改，且改设计 | 触及合规红线 / 结构性缺口导致同类工单反复发生 / 双链路·双入口·无校验等设计缺口 |
| 🟡 部分不合理 | 要改，随方案走 | 有可用方案但存在明显缺口（错误不可分类、缓存不失效、定位靠约定无校验） |
| 🟢 合理 | 保持监控 | 现状方案可用，问题为个案或合理业务演进 |

判定顺序：🔴 在前，严重者先写。

## 二、根因四分类（每个问题点必填）

| 根因 | 判定标准 | 处置去向 |
|------|---------|---------|
| 产品方向缺位 | 诉求合理但产品从未规划/未支持该能力（如：无线签名板对接、新 CA 厂商接入标准） | → 3.2 产品规划建议（待产品拍板） |
| 实现质量失守 | 设计本身成立，但实现层写错（缓存不失效、漏写日志、状态没同步等代码缺陷） | → 3.3 缺陷批量治理清单 |
| 设计本身缺陷 | 设计方案就存在结构性缺口：多链路并存、多入口并存、靠约定无校验、前端驱动写关键数据等 | → 3.1 设计优化方案 |
| 混合 | 多因叠加，**必须注明主导方**（如"混合，设计缺陷主导"、"混合，实现主导"） | 按主导方进对应通道 |

**写作纪律**：每个问题点的根因判定必须附依据（代码证据或工单模式），不允许只写标签。

## 三、2×2 象限（功能点级）

以功能点的 需求工单量（横轴）× 软质工单量（纵轴）定位：

| 象限 | 名称 | 解读 | 默认动作 |
|------|------|------|---------|
| 高需高软 | 结构问题区 | 新能力诉求与质量抱怨双高 → 该能力的设计撑不住业务演进 | 功能点级判定重点对象，进 3.1 |
| 低需高软 | 质量债区 | 诉求不多但质量问题密集 → 实现债/设计债已到期 | 进 3.1 或 3.3，视根因 |
| 高需低软 | 能力缺位区 | 用户一直要新能力但少质量抱怨 → 产品方向缺位为主 | 进 3.2 |
| 低需低软 | 健康区 | 稳定 | 保持监控 |

## 四、功能点级判定

综合该功能点全部问题点级结论：

- 任一 🔴 问题点触及合规（如电子签名"签名与文档状态绑定"类法规要求）→ 功能点级 **🔴 不合理**
- 无合规问题但存在设计缺陷主导的结构性缺口 → 🔴 或 🟡（按软质密度与缺口数量）
- 缺口均为 🟡 且有清晰修复路径 → 🟡 部分不合理

写法模板：
`**🔴 功能点级不合理（混合）**：<核心缺口一句话>——"<用户现象>"集中地；升功能点级🔴，进 3.1 方案N`

## 五、证据纪律

1. 需求工单标注 `(需)`、软质工单标注 `(软)`，如 `1750424(软) 1731466(软)`
2. **支持单只作现象参考，不作判定证据**；写法："另有支持单 N 条同类现象（不作判定证据，见 1.8）"
3. 代码证据格式：`文件名:行号`（如 `EmrSignServiceImpl.cancelEmrRecordSigned:172`）；同一问题点多处证据全列
4. 工单归并口径：同类现象可归并为一个问题点，但须在工单明细清单中可追溯
5. 数量校验：1.1 汇总表的 合计/需求/软质/支持单 数量必须与问题点全景、摘要数字一致

## 六、判定示例（摘自源报告）

**🔴 示例**（P06 状态-撤销签署后签名未同步清除）：
- 合规影响：撤销签署后 CA 签名残留，签名状态与病历状态不一致，触及电子签名"签名与文档状态绑定"的合规要求
- 不合理之处：双链路分离是设计缺口，撤销同步靠手工调用，任一路径漏调即残留签名；四套并行签名实现改一处漏三处
- 根因：混合（设计缺陷主导）→ 进 3.1 设计方案1

**🟡 示例**（P01 集成-CA签名接口调用报错）：
- 缺口：报错无后端诊断日志、无法区分"CA 网关问题/传参问题/证书问题"
- 证据：1750424(软) 1731466(软) 1728391(软)…
- 根因：混合 → 进 3.1（错误码分类+诊断日志）

**🟢 处理**：🟢 问题点只需在全景表列出并标注"保持监控"，不展开判定章节。
