# 报告模板（rational-design-v1）

> 四章节合订骨架与写作口径。写报告时按此结构组织，括号内为指导说明，输出时替换为实际内容。

```markdown
# {功能点/模块名} 功能点深挖报告

> **信息**：
> 模块 {模块编码-名称}（如 MZBL-08-QM 08CA签名）
> 四章节合订：工单分类 → 合理性判定 → 治理方案 → 需求分析（产品视角）

**目录**：
一、工单分类（有什么问题）
二、合理性判定（要不要改、为什么）
三、治理方案（怎么改：3.1 设计优化 / 3.2 产品规划 / 3.3 缺陷治理）
四、需求分析（改成什么样算合格）

---

## 摘要

（一段话交代选点依据：健康度盘点 → 为何该模块优先治理。然后给结论表：）

| 项 | 结论 |
|---|---|
| 工单构成 | {总数} 条 = 需求 {n} + 软质 {n} + 支持单 {n}；TOP 功能点：{A} {n} / {B} {n} / {C} {n}，前三占模块 {n}%； |
| 功能点 🔴 | {列出🔴功能点} |
| 根因分布 | 产品方向缺位 {n} 项 / 实现质量失守 {n} 项 / 设计本身缺陷 {n} 项 / 混合 {n} 项 |
| 治理去向 | 设计方案 / 产品规划建议 / 缺陷批量治理 |

---

## 一、工单分类

> 这一章回答「**有什么问题**」：把本模块全部工单按需求（医院要什么新能力）/ 软质（系统哪里出了质量问题）两条线分开读，再合成问题点全景表和交叉矩阵。

### 1.1 功能点一维汇总

| 功能点 | 合计 | 功能性(需求) | 软质 | 支持单 |
|---|---|---|---|---|
| {编码-名称} | {n} | {n} | {n} | {n} |
| … | | | | |
| （模块级未入功能点：baseline/new-fp） | {n} | {n} | {n} | {n} |
| **合计** | **{n}** | **{n}** | **{n}** | **{n}** |

（随后：问题点全景表——P01、P02…每个问题点含：编号+类型+名称+关联工单；需求×软质交叉矩阵）

---

## 二、合理性判定

> 这一章回答「**要不要改、为什么**」：每个问题点判严重等级（🔴/🟡/🟢）→ 定根因（产品还没做 / 代码写错了 / 设计本身有缺陷 / 混合）→ 定处置去向（3.1 设计方案 / 3.2 产品规划 / 3.3 缺陷治理）。

### 2.1 判定汇总（问题点级+功能点级）

| 功能点 | 需软工单量 | 2×2 象限 | 功能点级判定 |
|---|---|---|---|
| 🟠{编码-名称} | {n} | {象限名} | **🔴/🟡 功能点级判定**：<核心缺口>——"<现象>"集中地；升🔴，进 3.1 方案N / 🟡，随 3.1+3.2 |

### 2.2 🔴 判定（严重者在前）

**P{n} {类型}-{名称}——🔴 不合理（{根因}，{主导方}）**

- {合规/业务影响一句话}
- 不合理之处：{结构性缺口描述，挂代码证据 文件:行号}
- **下文**：进 3.1 方案N，要改设计（方案组 {P清单} 需软合计 {n} 条）。

### 2.3 🟡 判定

**P{n} {类型}-{名称}——🟡 部分不合理（{根因}）**。

{缺口描述，挂代码证据}

证据：{工单号(需)/(软) 列表}。另有支持单 {n} 条同类现象（不作判定证据，见1.8）。

**下文**：进 {3.1/3.2/3.3}，{处置一句话}。

---

## 三、治理方案

> 这一章回答「**怎么改**」：三类根因各走一条通道，每条通道都展开写清楚——设计本身有缺陷的给**详细改造方案**（3.1，本报告核心交付）；产品还没做的能力给**产品规划建议**（3.2，待产品拍板）；代码写错的给**缺陷批量治理清单**（3.3，照清单修 bug）。

| 场景 | 现状 | 方案后 |
|---|---|---|
```

## 衍生文档：功能点需求说明

> 用户要求登记 TFS 时，基于第四章衍生，模板要点：

```markdown
# 【结构治理】{产品}-{模块}-{功能点} 功能点需求说明

> **版本**：v1.0（{日期}）
> **来源**：{深挖报告文件名}
> **用途**：按功能点登记 TFS 需求。每条需求给出：需求名称 / 背景（含证据工单）/ 需求描述 / 业务规则 / 验收标准 / 优先级。
> **范围口径**：本期 = {3.1 方案N 改造点 R清单 + 3.3 治理项}；{3.2 产品规划项} 待产品拍板，仅作附录。

## 一、需求总览

| 需求编号 | 需求名称 | 功能点 | 优先级 | 来源 | 关联证据工单 |
|---|---|---|---|---|---|
| REQ-{模块缩写}-{功能点号}-{序号} | {名称} | {功能点} | 高/中/低 | R{n} / P{n} | {工单号列表} |

（随后：每个功能点一节，列工单明细——类型 | 工单 | 状态 | TFS 标题（已核实）| 关联问题点；末尾给公共设计约束）
```
