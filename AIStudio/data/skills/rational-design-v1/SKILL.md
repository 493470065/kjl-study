# rational-design-v1 — 功能点深挖与结构治理报告生成

## 技能定位

本技能回答四个递进的问题，产出一份**四章节合订**的功能点深挖报告：

| 章节 | 回答的问题 | 核心产出 |
|------|-----------|---------|
| 一、工单分类 | **有什么问题** | 功能点一维汇总表（需求/软质/支持单）、问题点全景表、交叉矩阵 |
| 二、合理性判定 | **要不要改、为什么** | 问题点级判定（🔴/🟡/🟢）+ 根因四分类 + 功能点级判定 + 处置去向 |
| 三、治理方案 | **怎么改** | 3.1 设计优化方案 / 3.2 产品规划建议 / 3.3 缺陷批量治理清单 |
| 四、需求分析 | **改成什么样算合格** | 业务流程时序图、R 需求项设计、验收标准 AC |

**与相邻技能的关系**：
- 上游：`consolidate-requirements-v1` 产出健康度基线 → 本技能对其中 🟠🔴 功能点做下钻
- 本技能第二章的问题点级判定是**根因导向**口径（严重度+根因分类+去向），与 `rationality-analysis-v1` 的五维评分（设计覆盖度导向）互补而非替代；如用户明确要五维评分，调用该技能
- 第四章的 R 需求项可直接衍生为 TFS 登记文档（Phase 2）

| 参数 | 说明 | 必填 | 默认 |
|------|------|:---:|------|
| 模块+功能点 | 如"门诊病历管理-08CA签名"或模块编码 MZBL-08-QM | ✅ | — |
| 工单数据来源 | TFS 查询 / 已有聚拢报告路径 | ✅ | 从 `E:\37结构性问题治理\` 下查找相关聚拢/盘点报告 |

## 工作流程

### Phase 0：输入采集（先做，缺什么问用户要什么）

1. **选点依据**：如用户只说"深挖"，先读《功能点健康度盘点.md》或聚拢报告第七章，按健康度🔴→🟠→🟡顺序提出候选功能点，与用户确认目标
2. **工单数据**：获取该功能点模块全部工单（需求+软质+支持单），逐条记录：工单号、类型、标题、状态。已有聚拢报告可直接用；没有则从 TFS 查询
3. **代码取证**（**强制前置**）：在代码仓库中定位该模块的核心实现文件。没有代码证据的判定是空判——第二章每一条🔴/🟡都必须落到"文件名:行号"级别的证据上

### Phase 1：工单分类 → 第一章

1. 按三条线分开读：**需求**（医院要什么新能力）/ **软质**（系统哪里出了质量问题）/ **支持单**（现场辅助现象）
2. 产出**功能点一维汇总表**：每个功能点的 合计/功能性(需求)/软质/支持单，并识别 TOP 功能点（前三占比）
3. 将工单按现象归并为**问题点**，编号 P01、P02…（编号分配后全文不再变更）；每个问题点标注类型（需求/数据/集成/状态/性能…）与关联工单号
4. 产出问题点全景表与 需求×软质 交叉矩阵

### Phase 2：合理性判定 → 第二章

按 `references/judgment-rules.md` 执行，要点：

1. **问题点级判定**：每个问题点判严重等级（🔴 不合理 / 🟡 部分不合理 / 🟢 合理），🔴 在前
2. **根因四分类**（每个问题点必填，判定依据写进报告）：
   - **产品方向缺位** — 产品还没做/没规划该能力
   - **实现质量失守** — 设计合理但代码写错/实现缺陷
   - **设计本身缺陷** — 设计方案就存在问题（双链路、双入口、无校验等结构性缺口）
   - **混合** — 多因叠加，注明主导方（如"混合，设计缺陷主导"）
3. **2×2 象限**：按功能点的 需求量×软质量 定位（高需高软=结构问题区 / 低需高软=质量债区 / 高需低软=能力缺位区 / 低需低软=健康区）
4. **功能点级判定**：汇总问题点级结论，判 🔴 不合理 / 🟡 部分不合理，写明根因与处置去向
5. **证据纪律**：需求与软质工单可作判定证据（标注"工单号(需)/(软)"）；**支持单只作现象参考、不作判定证据**；代码证据给"文件:行号"

### Phase 3：治理方案 → 第三章

三类根因各走一条通道，每条展开写清：

1. **3.1 设计优化方案**（根因=设计缺陷/混合）：先给"方案↔问题点对应表"，每个方案按固定结构展开：
   - **问题定位**：结构性缺口逐条列出（每条挂代码证据）
   - **优化对比表**：场景 | 现状 | 方案后
   - **用户故事**：作为<角色>，我<期望行为>
   - **测试用例**：①②③…覆盖关键路径+异常路径+存量兼容
2. **3.2 产品规划建议**（根因=产品方向缺位）：诉求场景+建议+不做的后果，标注"待产品拍板"
3. **3.3 缺陷批量治理清单**（根因=实现质量失守）：现象白话+为何是代码问题（代码证据）+修复策略+回归范围

### Phase 4：需求分析（产品视角）→ 第四章

1. **4.1 背景**：业务诉求（用户语言）+ 业务现状（问题清单，与第二章呼应）
2. **4.2 业务流程**：现状时序图（mermaid `sequenceDiagram`），多链路场景每个时序一张图，标注与问题点的关联
3. **4.3 产品分析概述**：方案 | 菜单名称 | 影响功能名称（列全受影响功能点编码）
4. **4.4 产品设计**：R1、R2…逐项展开，每项固定四要素——**对应功能点 / 改哪里（代码位置）/ 为何改（挂 P 问题点）/ 如何改（可落地的方案描述）**；最后给操作流程图（mermaid `flowchart`）
5. **4.5 验收标准**：AC1…ACn，每条可测试、可回归（挂 BR/证据工单场景"不复现"）

### Phase 5（可选，用户要求时）：衍生功能点需求说明

将 3.1 方案 + 3.3 治理清单转化为按功能点登记的 TFS 需求文档，按 `references/requirement-spec-template.md`：
- 需求总览表：REQ-{模块缩写}-{功能点号}-{序号} | 需求名称 | 功能点 | 优先级 | 来源(R#/3.3) | 关联证据工单
- 每条需求：背景（含证据工单）/ 需求描述 / 业务规则 / 验收标准
- 范围口径显式声明：本期范围 vs 待产品拍板项（只作附录）
- 公共设计约束（如"统一能力层，不带条线专用前缀"）单列，随相关需求落地
- ⚠️ 工单明细须 TFS 实查核对标题与状态后再列入（报告数量统计≠工单明细）

## 质量红线

1. **代码证据不得编造**：所有"文件名:行号"必须来自真实扫码；仓库不可读时标 ⏳待确认，不得虚构
2. **证据工单必须真实**：工单号来自 TFS 实查或用户提供的报告，不得凭空生成
3. **根因分类必须给依据**：不允许只写标签不写理由
4. **支持单不进判定**：只作现象佐证，报告中显式说明（如"另有支持单 5 条同类现象，不作判定证据"）
5. **数字前后一致**：摘要、1.1 表、判定表中的工单数、占比必须对得上
6. **方案必须可落地**：3.1/4.4 要写到"改哪个服务/哪个入口、事务边界怎么定、存量怎么兼容"，不写"加强校验""优化流程"这类空话
